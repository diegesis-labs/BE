# 개발 규칙

이 문서는 이 레포에서 코드를 쓰는 사람과 에이전트가 함께 지키는 규칙을 모아 둔 문서입니다. harness가 띄우는 에이전트 세션에는 이 문서가 매번 통째로 주어지므로, 여기에는 모든 작업에 해당하는 규칙만 적습니다. harness를 운영하는 절차는 [HARNESS.md](HARNESS.md)에 있고, 낯선 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에 있습니다.

## 1. 개발 환경 준비

패키지 매니저로 uv를 씁니다. 레포를 받은 뒤 아래 명령을 한 번 실행하면 `.venv` 폴더에 Python과 개발 도구가 설치됩니다.

```bash
uv sync
```

그리고 Docker Desktop을 설치하고 켜 둡니다. 검사 명령의 통합 테스트가 Docker로 데이터베이스를 띄우기 때문입니다(4.3절). 서버와 데이터베이스를 로컬에서 띄우는 방법은 [README](../README.md)에 있습니다.

검사 명령(2절)은 bash 스크립트이며, macOS와 Linux(CI)에서만 돌려 확인했습니다. Windows에서 검사를 돌리는 방법은 아직 확인하지 않았습니다.

로컬에서 컨테이너 이미지는 docker compose로 빌드하며, `docker build`를 직접 쓰지 않습니다. `docker build`의 결과가 로컬 이미지 저장소에 실리는지는 각자의 Docker builder 설정에 따라 다르기 때문입니다([DECISIONS.md](DECISIONS.md)의 D-41).

버전은 아래 파일에만 적으며, 다른 문서에는 버전을 적지 않습니다. 버전을 올릴 때에는 이 파일들을 고칩니다.

| 무엇의 버전 | 적힌 곳 |
| --- | --- |
| Python | `.python-version`. `Dockerfile`의 Python 베이스 이미지도 같은 버전이어야 하며, 테스트가 이것을 확인합니다. |
| Python 패키지 | `pyproject.toml`(하한)과 `uv.lock`(정확한 버전) |
| uv | `Dockerfile`이 복사해 오는 uv 이미지. CI가 설치하는 uv도 같은 버전이어야 하며, 테스트가 이것을 확인합니다. |
| PostgreSQL과 pgvector | `compose.yaml`의 `db` 서비스의 이미지. 통합 테스트도 이 값을 읽어서 씁니다. |
| GitHub Actions의 action | `.github/workflows/`의 각 파일 |

의존성을 추가할 때에는 `uv add <이름>`을, 개발할 때만 쓰는 도구를 추가할 때에는 `uv add --dev <이름>`을 씁니다. 새로 들이는 기술은 [ADR.md](ADR.md)가 정한 범위 안에 있어야 합니다.

## 2. 검사 명령

검사는 `scripts/check.sh` 하나로 돌립니다. 이 스크립트는 아래 네 가지를 순서대로 실행합니다.

| 순서 | 명령 | 확인하는 것 |
| --- | --- | --- |
| 1 | `uv run ruff check .` | 린트 규칙 위반 |
| 2 | `uv run ruff format --check .` | 서식 |
| 3 | `uv run pyright` | 타입 오류 |
| 4 | `uv run pytest` | 테스트 |

ruff는 `phases/` 아래를 검사하지 않습니다. 그곳의 파일은 step 지시와 리뷰 기록이며, 그 안의 코드 블록은 서식을 맞춰야 하는 코드가 아니기 때문입니다.

```bash
scripts/check.sh         # 첫 실패에서 멈춥니다. 커밋하기 전에 돌립니다.
scripts/check.sh --all   # 네 가지를 모두 돌리고 명령별 결과를 요약합니다.
```

`--all`을 붙이면 마지막에 아래와 같은 요약이 나옵니다.

```
=== 요약
ruff check: exit 0
ruff format --check: exit 0
pyright: exit 0
pytest: exit 0
```

검사 명령을 이 스크립트 한 곳에 모은 이유는 기준이 갈라지지 않게 하기 위해서입니다. 에이전트 세션이 턴을 끝낼 때 도는 훅, step의 완료 조건, 리뷰의 실측, PR을 올리기 전의 점검이 모두 이 스크립트를 부릅니다.

pytest가 테스트를 하나도 찾지 못하면 실패로 끝납니다. 이것을 통과로 바꾸지 않습니다. 테스트를 하나도 돌리지 않았는데 통과로 보이면, 검사가 꺼진 것을 알 수 없기 때문입니다. 같은 이유로, Docker가 꺼져 있어서 통합 테스트가 데이터베이스를 띄우지 못하면 pytest는 실패로 끝납니다.

이와 별도로 `scripts/compose-smoke.sh`가 있습니다. 이 스크립트는 docker compose로 데이터베이스, 마이그레이션, 서버를 실제로 띄운 뒤 가장 기본적인 동작을 확인하고 내립니다. 이미지를 빌드하느라 몇 분이 걸리므로 `scripts/check.sh`에는 넣지 않았습니다. 그 대신 `Dockerfile`, `compose.yaml`, `.dockerignore`, 마이그레이션을 바꾸는 step의 완료 조건과 CI에서 돌립니다.

```bash
scripts/compose-smoke.sh   # 확인이 하나라도 어긋나면 0이 아닌 코드로 끝납니다.
```

스모크는 `diegesis-smoke`라는 고정된 프로젝트 이름으로 띄우고 내리므로, 개발용으로 띄워 둔 compose의 컨테이너와 데이터를 건드리지 않습니다.

| 문서는 정해진 작성 규칙을 따릅니다. 한 가지 정보는 한 문서에만 적습니다. | [DECISIONS.md](DECISIONS.md)의 D-16부터 D-20까지 |

## 4. 테스트 규칙

### 4.1 테스트를 먼저 씁니다

`app/` 아래에 로직을 쓸 때에는 그 로직의 테스트를 먼저 씁니다. 순서는 다음과 같습니다.

1. 테스트를 씁니다.
2. 테스트가 실패하는 것을 직접 확인합니다. 이때 기대한 이유로 실패하는지도 봅니다.
3. 실패하는 테스트를 `test(범위): RED — 설명`이라는 메시지로 커밋합니다. 이 커밋을 RED 커밋이라고 부릅니다.
4. 구현해서 테스트를 통과시키고 커밋합니다.

RED 커밋을 따로 남기는 이유는, 테스트를 먼저 썼다는 사실을 나중에 확인할 방법이 그것뿐이기 때문입니다. 테스트와 구현이 한 커밋에 함께 들어 있으면, 구현을 먼저 쓰고 거기에 맞춰 쓴 테스트와 구별할 수 없습니다.

응답 시간처럼 수치를 재서 확인하는 작업에는 이 순서를 적용하지 않습니다.

### 4.2 테스트 파일의 위치

`tests/` 폴더는 `app/` 폴더와 같은 구조로 둡니다. 테스트 파일의 위치는 대상 파일의 경로로 정해집니다.

| 대상 파일 | 테스트 파일 |
| --- | --- |
| `app/books/service.py` | `tests/books/test_service.py` |
| `app/books/router.py` | `tests/books/test_router.py` |
| `app/adapters/pgvector.py` | `tests/adapters/test_pgvector.py` |
| `app/recommendation/service.py` | `tests/recommendation/test_service.py` 또는 `tests/recommendation/test_service_sampling.py` |

한 파일의 테스트가 길어지면 `test_<이름>_<주제>.py`의 형태로 나눌 수 있습니다. 기능 폴더마다 `service.py`가 있으므로, 다른 폴더에 있는 같은 이름의 테스트는 그 파일의 테스트로 보지 않습니다.

`app/` 밖에 있는 실행 환경의 파일은 `tests/infra/`에서 테스트합니다. `Dockerfile`, `.dockerignore`, `compose.yaml`, `scripts/compose-smoke.sh`, `.github/workflows/`의 파일, 그리고 `alembic.ini`와 마이그레이션 리비전의 템플릿(`migrations/script.py.mako`)이 여기에 해당합니다. 이 파일들의 내용 가운데 단언할 수 있는 것, 예를 들어 버전이 서로 맞는지, 빠지면 안 되는 항목이 있는지, 작업이 정해진 순서로 실행되는지를 테스트로 확인합니다.

여러 테스트가 함께 쓰는 도우미, 예를 들어 통합 테스트용 데이터베이스를 띄우는 코드는 `tests/support/`에 두고, 그 도우미의 테스트도 같은 폴더에 둡니다. 이 도우미는 `app/`의 파일을 대상으로 하지 않으므로 위 표의 대응 규칙을 따르지 않습니다.

아래 파일은 선언과 조립만 하므로 테스트를 먼저 쓰지 않아도 됩니다. 그 대신 이 파일들에는 판정하는 로직을 넣지 않습니다.

| 파일 | 하는 일 |
| --- | --- |
| `__init__.py` | 패키지 표시 |
| `app/main.py` | 라우터와 어댑터의 조립 |
| `models.py` | 테이블 선언 |
| `schemas.py` | 요청과 응답의 형식 선언 |
| `app/core/config.py` | 설정 클래스 |
| `app/core/ports.py` 또는 `app/core/ports/` | 포트 선언 |
| `app/core/database.py` | 데이터베이스 연결의 조립 |
| `app/__main__.py` | `python -m app`으로 서버를 실행하는 진입점 |

`router.py`는 이 목록에 없습니다. 로그인 상태와 허용 목록을 확인하는 관문이 라우터 층에 있고, 본문이 새는 자리가 바로 그곳이기 때문입니다. 가짜 어댑터를 끼우면 데이터베이스 없이도 라우터를 테스트할 수 있습니다.

### 4.3 테스트의 종류

| 종류 | 뜻 | 실제 PostgreSQL |
| --- | --- | --- |
| `unit` | 순수 로직, 그리고 가짜 어댑터를 끼운 `service`와 `router`를 검증합니다. | 쓰지 않습니다. |
| `integration` | `repository`와 어댑터가 실제 데이터베이스에서 동작하는지 검증합니다. | 씁니다. |

벡터 검색처럼 PostgreSQL과 pgvector의 동작에 기대는 코드는 다른 데이터베이스나 가짜로 대신하지 않고 `integration` 테스트로 검증합니다.

통합 테스트용 데이터베이스는 testcontainers로 띄웁니다([ADR-011](ADR.md#adr-011-통합-테스트용-데이터베이스)). 테스트를 실행하면 `tests/conftest.py`의 fixture가 데이터베이스 컨테이너를 무작위 포트로 띄우고, 마이그레이션을 끝까지 적용한 뒤 그 주소를 테스트에 넘깁니다. 그리고 테스트가 끝나면 컨테이너를 지웁니다. 이때 지키는 규칙은 다음과 같습니다.

- 컨테이너의 이미지는 `compose.yaml`의 `db` 서비스에서 읽습니다. 이미지의 이름과 버전을 테스트 코드에 따로 적지 않습니다.
- 통합 테스트는 개발자의 `.env`나 compose로 띄운 개발용 데이터베이스에 접속하지 않습니다. 마이그레이션을 되돌리는 테스트가 개발용 데이터를 지울 수 있기 때문입니다.
- Docker에 닿을 수 없으면 통합 테스트는 건너뛰지 않고 실패합니다. 건너뛰면 통합 테스트를 하나도 돌리지 않았는데도 검사가 통과한 것처럼 보이기 때문입니다.
- 통합 테스트에는 `integration` 표시(pytest marker)를 붙입니다.

### 4.4 검증에 관한 원칙

- **검증은 수치로 끝냅니다.** "동작하는 것 같다"는 결과가 아닙니다. 검사 명령의 종료 코드, 통과한 테스트의 수, 실제 응답을 근거로 삼습니다.
- **기준을 낮춰서 통과시키지 않습니다.** 테스트를 지우거나 건너뛰게 하는 것, 단언을 약하게 고치는 것, `# type: ignore`나 `# noqa`를 다는 것, ruff와 pyright의 설정을 느슨하게 바꾸는 것이 여기에 해당합니다. 기준을 지킬 수 없으면 다른 방법을 찾고, 그래도 안 되면 그 사실을 알립니다.
- **테스트는 틀린 구현을 걸러 내야 합니다.** 테스트를 쓸 때에는 "어떤 틀린 구현이 이 테스트를 통과하는가"를 함께 생각합니다. 결과의 개수나 존재만 확인하고 내용을 확인하지 않는 테스트는 틀린 구현도 통과시킵니다.
- **하지 않은 것을 했다고 적지 않습니다.** 돌리지 못한 검사는 "실행하지 못했습니다"라고 이유와 함께 적습니다.
- **사람이 직접 확인하는 것은 최소로 둡니다.** 단언으로 적을 수 있는 것은 테스트로 만듭니다. 사람이 한 번 확인한 것은 다음 변경에서 다시 깨져도 알 수 없지만, 테스트는 매번 확인하기 때문입니다.

## 5. 가드가 막는 것

이 레포의 `.claude/settings.json`에는 에이전트의 행동을 검사하는 훅이 걸려 있습니다. Claude Code로 이 레포에서 작업하면 누구에게나 적용됩니다. 훅이 막는 것의 범주는 다음과 같으며, 정확한 규칙은 각 스크립트에 있습니다.

| 가드 | 막는 것 | 규칙이 있는 곳 |
| --- | --- | --- |
| TDD 가드 | 대응하는 테스트 파일이 없는 `app/` 아래의 로직 파일을 쓰는 것 | `scripts/hooks/tdd-guard.sh` |
| 명령 가드 | 되돌릴 수 없는 명령. 재귀 강제 삭제, 강제 push, 작업 내용을 버리는 reset, 테이블이나 데이터베이스의 삭제, Docker 볼륨의 삭제가 여기에 해당합니다. | `scripts/hooks/bash-guard.sh` |
| 종료 검사 | 검사가 실패한 채로 에이전트 세션이 턴을 끝내는 것. 세 번까지 되돌린 뒤에는 경고를 남기고 놓아줍니다. | `scripts/hooks/stop-check.sh` |

가드가 막았을 때에는 가드를 고치거나 우회하지 않습니다. TDD 가드가 막았다면 테스트를 먼저 쓰고, 명령 가드가 막았다면 무엇을 하려 했는지 사람에게 알립니다. 어떤 파일이 테스트를 먼저 쓸 수 없는 파일이라고 판단되면, 사람이 `scripts/hooks/tdd-guard.sh`의 "개별 파일 예외"에 이유와 함께 추가합니다.

가드를 고쳤을 때에는 같은 폴더의 `*.test.sh`도 함께 고칩니다. 이 테스트들은 `scripts/check.sh`를 돌릴 때 함께 실행됩니다.

## 6. 커밋, 브랜치, PR

### 6.1 커밋

커밋 메시지는 `종류(범위): 설명`의 형태로 쓰며, 설명은 한국어로 씁니다. 범위는 생략할 수 있습니다.

| 종류 | 쓰는 때 |
| --- | --- |
| `feat` | 기능을 추가했을 때 |
| `fix` | 결함을 고쳤을 때 |
| `test` | 테스트만 추가하거나 고쳤을 때. RED 커밋이 여기에 해당합니다. |
| `docs` | 문서만 고쳤을 때 |
| `chore` | 설정, 도구, 그 밖의 정리 |

```
feat(3-books): step 1 — books-router
test(3-books): RED — 허용 목록 밖의 계정은 본문을 받지 못한다
fix(3-books): 1차 리뷰 SEC-1 — 챕터 경로에 허용 목록 확인을 건다
docs: 통합 테스트용 데이터베이스를 띄우는 방법 추가
```

harness가 만드는 커밋은 범위에 phase의 이름을 쓰며, 그 형식은 [HARNESS.md](HARNESS.md)에 있습니다. 사람의 지시로 에이전트가 만든 커밋에는 메시지 끝에 `Co-Authored-By` 줄을 붙입니다.

### 6.2 브랜치

`main` 브랜치에 직접 커밋하지 않습니다. 작업마다 브랜치를 따며, 이름은 아래와 같이 짓습니다.

| 작업 | 브랜치 이름 | 예 |
| --- | --- | --- |
| harness로 돌리는 phase | `feat-<phase 이름>` | `feat-3-books` |
| 그 밖의 작업 | `<종류>/<짧은 설명>` | `docs/api-error-codes`, `chore/harness-port` |

### 6.3 PR

`main`에는 PR로만 합칩니다. 코드가 `main`에 합쳐지면 자동으로 배포하기로 정했으므로([DECISIONS.md](DECISIONS.md)의 D-23), PR이 배포 앞의 마지막 관문입니다. 따라서 검사를 통과하지 못한 코드는 PR로 올리지 않습니다.

PR을 합칠 때에는 **merge commit** 방식을 씁니다. squash 방식은 쓰지 않습니다. squash는 브랜치의 커밋들을 하나로 뭉치므로, 테스트를 먼저 썼다는 증거인 RED 커밋이 `main`의 이력에서 사라지기 때문입니다.

`main`에는 직접 push하지 않습니다. 이 레포는 백엔드 담당자 혼자 관리하므로, PR을 합치기 전에 다른 사람의 승인을 받아야 한다는 조건은 두지 않습니다([DECISIONS.md](DECISIONS.md)의 D-35).

PR의 본문에는 무엇을 만들었는지, 어떤 검사를 통과했는지, 사람이 무엇을 직접 확인했는지를 적습니다. harness로 돌린 phase의 PR은 `scripts/harness-pr.sh`가 본문을 만들어 줍니다.
