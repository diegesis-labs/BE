# Epic 1: 로그인과 허용 목록

| 항목 | 값 |
| --- | --- |
| GitHub 이슈 | #9 |
| 마일스톤 | 2주차 |
| phase | `phases/1-login-allowlist/` |

## 목표

허용 목록에 있는 사람이 Google 계정으로 로그인하고, 보호된 모든 경로가 요청마다 로그인 상태, 허용 목록, 관리자 권한을 확인합니다. 이 Epic이 끝나면 프론트엔드는 실제 백엔드로 로그인하고, 로그아웃하고, 내 정보를 조회할 수 있습니다. 그리고 이후 Epic의 모든 경로는 이 관문 위에서 만들어집니다.

허용 목록은 관리 API 없이 데이터베이스에 SQL로 넣고 빼며, 서버를 다시 띄우지 않아도 다음 요청부터 반영됩니다. 그리고 로컬에서 실제 Google 계정으로 로그인이 끝까지 되는지 확인합니다.

## 입력

- Epic 0이 만든 설정 클래스(`app/core/config.py`), 데이터베이스 연결과 마이그레이션(`app/core/database.py`, `migrations/`), 공통 에러 형식(`app/core/errors.py`), testcontainers로 띄우는 통합 테스트용 데이터베이스(`tests/conftest.py`, `tests/support/`)가 있습니다.
- 이 Epic의 계약을 정한 문서가 `main`에 합쳐져 있습니다. 엔드포인트의 형식과 동작 순서는 [API.md](../../API.md)의 2.2절, 4.2절, 4.3절에, 테이블의 스키마는 [ARCHITECTURE.md](../../ARCHITECTURE.md#6-데이터-모델) 6절에 있습니다.
- MANUAL 점검에는 로컬의 돌아올 주소를 등록한 Google OAuth 클라이언트의 ID와 비밀값이 필요합니다([INFRA.md](../../INFRA.md#35-google-로그인-설정) 3.5절). 클라이언트를 어느 계정으로 만들지는 아직 정하지 않았지만, 로컬의 돌아올 주소만 등록되어 있으면 어느 계정의 클라이언트든 이 Epic의 점검에 쓸 수 있습니다.

## 끝나는 조건

harness phase 안에서 확인하는 것은 다음과 같습니다.

- `phases/1-login-allowlist/`의 모든 step이 완료되고, 리뷰와 처분이 닫히고, MANUAL 점검표가 모두 체크됩니다.
- [testcase.md](testcase.md)의 `unit`과 `integration` 케이스가 `scripts/check.sh`에서 모두 통과합니다.

PR을 연 뒤와 `main`에 합친 뒤에 확인하는 것은 다음과 같습니다.

1. PR에서 CI의 검사가 모두 통과합니다.
2. PR을 `main`에 합치면 이슈 #9가 닫힙니다.

## 못 박을 것 (Epic 전역)

- 허용 목록을 로그인할 때 한 번만 확인하지 않습니다. 보호된 경로의 요청마다 데이터베이스의 `allowed_emails`를 확인합니다. 이유는 SQL로 뺀 사람이 서버를 다시 띄우지 않아도 다음 요청부터 막혀야 하기 때문입니다(ADR-024).
- 허용 목록과 역할을 프로세스의 메모리나 로그인 상태에 담아 두지 않습니다. 이유는 위와 같습니다. 역할을 로그인 상태에 복사해 두면 SQL로 역할을 바꿔도 반영되지 않습니다.
- 쿠키의 값을 데이터베이스에 그대로 저장하지 않습니다. 이유는 데이터베이스의 내용이 새어도 로그인 상태를 가로챌 수 없어야 하기 때문입니다(ARCHITECTURE.md 6절).
- Google이 이메일을 확인하지 않은 계정(`email_verified`가 false)을 로그인시키지 않습니다. 이유는 확인되지 않은 이메일로 허용 목록을 통과할 수 있기 때문입니다(ADR-025).
- 이메일을 소문자로 바꾸지 않은 채 저장하거나 비교하지 않습니다. 이유는 대소문자 차이로 허용된 사람이 막히거나 뺀 사람이 통과할 수 있기 때문입니다(ADR-024).
- 허용 목록에 없는 계정의 `users` 행을 만들지 않습니다. 이유는 서비스를 쓸 수 없는 사람의 정보를 남기지 않기 위해서입니다(ARCHITECTURE.md 6절).
- Google에 `openid`, `email`, `profile` 말고는 요청하지 않습니다. 이유는 필요하지 않고, 다른 범위를 요청하면 사용자에게 경고 화면이 보이기 때문입니다(ADR-025).
- 돌아올 주소를 요청의 Host로 만들지 않습니다. 이유는 프론트엔드의 개발 서버가 백엔드로 요청을 넘길 때 Host를 바꾸기 때문입니다(ADR-025).
- `service`가 Google을 직접 부르지 않고 `IdentityProvider` 포트를 거칩니다. 이유는 테스트에서 가짜 어댑터를 끼우기 위해서입니다(ARCHITECTURE.md 8절).
- 테스트가 실제 Google에 요청하지 않습니다. 이유는 검사가 네트워크와 Google 계정에 기대면 CI에서 돌 수 없기 때문입니다.
- 허용 목록을 조회하거나 바꾸는 API를 만들지 않습니다. 이유는 허용 목록을 SQL로만 다루기로 했기 때문입니다(ADR-024).
- 로그인 실패의 원인을 돌려보내는 주소에 담지 않고, 로그에 쿠키의 값, Google의 `code`, 토큰, 클라이언트 비밀값을 남기지 않습니다. 이유는 실패의 원인은 공격자에게 단서가 되고, 이 값들은 로그만으로 로그인 상태를 가로챌 수 있게 하기 때문입니다(ADR-025).

## Story

### S1.1 사용자, 로그인 상태, 허용 목록의 저장

| Task | 내용 | 산출물 |
| --- | --- | --- |
| T1.1.1 | `allowed_emails`, `users`, `login_sessions` 테이블을 선언하고 마이그레이션을 만듭니다. | `app/auth/models.py`, `migrations/versions/` |
| T1.1.2 | 허용 목록 조회, 사용자의 등록과 갱신, 로그인 상태의 저장과 조회와 삭제를 하는 repository를 만듭니다. | `app/auth/repository.py` |

**대응**: ARCHITECTURE.md 6절, ADR-024

**못 박을 것**: 테이블의 이름, 컬럼, 타입, 제약은 ARCHITECTURE.md 6절의 그림과 설명을 그대로 따릅니다. README의 허용 목록 SQL이 이 스키마에 기대기 때문입니다. 만료된 로그인 상태는 조회 결과에 나오지 않습니다.

### S1.2 Google 로그인 어댑터

| Task | 내용 | 산출물 |
| --- | --- | --- |
| T1.2.1 | `IdentityProvider` 포트를 선언합니다. 포트는 인가 주소를 만드는 기능과, Google이 준 `code`를 확인된 신원(이메일, 이메일 확인 여부, 이름)으로 바꾸는 기능을 가집니다. | `app/core/ports.py` |
| T1.2.2 | Google 어댑터를 만들고, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `FRONTEND_URL`을 설정 클래스에 추가합니다. | `app/adapters/google.py`, `app/core/config.py` |

**대응**: ARCHITECTURE.md 8절, ADR-025, CONFIGURATION.md 3.1절과 3.3절, INFRA.md 3.5절

**못 박을 것**: 어댑터는 Google과 통신하다 생긴 예외를 그대로 밖으로 내보내지 않고, 로그인 실패를 뜻하는 예외 하나로 바꿉니다. Google과 통신할 라이브러리는 step을 설계할 때 고르고, 새 의존성이면 ADR에 기록합니다.

### S1.4 관문

| Task | 내용 | 산출물 |
| --- | --- | --- |
| T1.4.1 | 쿠키로 로그인 상태와 사용자를 찾고, 허용 목록과 역할을 확인하는 의존성 두 개를 만듭니다. 하나는 로그인한 사용자를 요구하고, 다른 하나는 관리자를 요구합니다. | `app/core/` 아래의 로그인 상태 확인 모듈 |
