# Epic 1: 로그인과 허용 목록

| 항목 | 값 |
| --- | --- |
| GitHub 이슈 | #9 |
| 마일스톤 | 2주차 |
| phase | `phases/1-login-allowlist/` |

## 목표

허용 목록에 있는 사람이 Google 계정으로 로그인하고, 보호된 모든 경로가 요청마다 로그인 상태, 허용 목록, 관리자 권한을 확인합니다. 이 Epic이 끝나면 프론트엔드는 실제 백엔드로 로그인하고, 로그아웃하고, 내 정보를 조회할 수 있습니다. 그리고 이후 Epic의 모든 경로는 이 관문 위에서 만들어집니다.

허용 목록은 관리 API 없이 데이터베이스에 SQL로 넣고 빼며, 서버를 다시 띄우지 않아도 다음 요청부터 반영됩니다. 그리고 백엔드 담당자가 프론트엔드 레포 없이도 로컬에서 실제 Google 계정으로 로그인과 로그아웃을 끝까지 확인할 수 있게 합니다. 이때 프론트엔드의 동작은 대역 서버와 Playwright 점검 스크립트가 흉내 냅니다.

## 입력

- Epic 0이 만든 설정 클래스(`app/core/config.py`), 데이터베이스 연결과 마이그레이션(`app/core/database.py`, `migrations/`), 공통 에러 형식(`app/core/errors.py`), testcontainers로 띄우는 통합 테스트용 데이터베이스(`tests/conftest.py`, `tests/support/`)가 있습니다.
- 이 Epic의 계약을 정한 문서가 `main`에 합쳐져 있습니다. 엔드포인트의 형식과 동작 순서는 [API.md](../../API.md)의 2.2절, 4.2절, 4.3절에, 테이블의 스키마는 [ARCHITECTURE.md](../../ARCHITECTURE.md#6-데이터-모델) 6절에 있습니다.
- MANUAL 점검(S1.7)에는 다음이 필요합니다.
  - 로컬의 돌아올 주소를 등록한 Google OAuth 클라이언트의 ID와 비밀값([INFRA.md](../../INFRA.md#35-google-로그인-설정) 3.5절). 클라이언트를 어느 계정으로 만들지는 아직 정하지 않았지만, 로컬의 돌아올 주소만 등록되어 있으면 어느 계정의 클라이언트든 이 Epic의 점검에 쓸 수 있습니다.
  - 실제 Google 계정 두 개. 하나는 허용 목록에 넣고, 다른 하나는 넣지 않습니다.
  - 점검하는 컴퓨터에서 켜 둔 Docker Desktop. 점검 스크립트는 compose로 띄운 서버와 데이터베이스를 상대로 돕니다.

## 끝나는 조건

이 Epic이 끝나면 아래의 엔드포인트와 테이블이 계약대로 동작합니다. 요청과 응답의 형식, 동작 순서, 스키마는 링크한 곳에만 있으며, 이 문서에는 옮겨 적지 않습니다(D-56).

| 엔드포인트 | 하는 일 | 계약 |
| --- | --- | --- |
| `GET /api/auth/google/login` | 로그인을 시작합니다. `state` 쿠키를 심고 브라우저를 Google로 보냅니다. | [API.md 4.2절](../../API.md#42-로그인과-로그아웃) |
| `GET /api/auth/google/callback` | Google이 돌려준 결과를 확인하고, 허용 목록에 있는 사람이면 로그인 상태를 만들고 쿠키를 심습니다. | [API.md 4.2절](../../API.md#42-로그인과-로그아웃) |
| `POST /api/auth/logout` | 로그인 상태와 쿠키를 지웁니다. | [API.md 4.2절](../../API.md#42-로그인과-로그아웃) |
| `GET /api/me` | 로그인한 사람의 정보와 역할을 돌려줍니다. | [API.md 4.3절](../../API.md#43-내-정보) |
| 관문 (보호된 모든 경로) | 요청마다 로그인 상태, 허용 목록, 관리자 권한을 확인하고, 통과하지 못하면 401이나 403으로 거절합니다. 엔드포인트가 아니라, 이후 Epic의 경로가 모두 거치는 의존성입니다. | [API.md 2.2절](../../API.md#22-로그인-상태) |

| 테이블 | 담는 것 | 스키마 |
| --- | --- | --- |
| `allowed_emails` | 허용 목록과 역할. SQL로만 넣고 뺍니다. | [ARCHITECTURE.md 6절](../../ARCHITECTURE.md#6-데이터-모델) |
| `users` | 허용 목록을 통과해 로그인한 적이 있는 사람 | [ARCHITECTURE.md 6절](../../ARCHITECTURE.md#6-데이터-모델) |
| `login_sessions` | 로그인 상태. 쿠키 값의 해시를 담습니다. | [ARCHITECTURE.md 6절](../../ARCHITECTURE.md#6-데이터-모델) |

이 밖에 이 Epic이 만드는 것은 다음 두 가지입니다.

- [README](../../../README.md#허용-목록에-사람-넣고-빼기)의 허용 목록 SQL이 위 스키마에서 동작합니다(S1.6).
- 로컬 로그인 점검 스크립트가 있습니다. 이 스크립트는 프론트엔드 대역 서버와 Playwright로 실제 Google 로그인과 로그아웃을 따라가며, 시점마다 세 테이블의 상태를 출력합니다(S1.7, [ADR-026](../../ADR.md#adr-026-로컬에서-실제-google-로그인을-점검하는-방법)).

harness phase 안에서 확인하는 것은 다음과 같습니다.

- `phases/1-login-allowlist/`의 모든 step이 완료되고, 리뷰와 처분이 닫히고, MANUAL 점검표가 모두 체크됩니다. 점검표에는 실제 Google 계정 두 개로 점검 스크립트를 돌린 결과가 남습니다. 그리고 로그인 전, 로그인 후, 로그아웃 전, 로그아웃 후의 테이블 상태가 [testcase.md](testcase.md#로컬-로그인-점검의-테이블-상태)의 표와 같은지 대조한 결과도 남습니다.
- [testcase.md](testcase.md)의 `unit`과 `integration` 케이스가 `scripts/check.sh`에서 모두 통과합니다.

PR을 연 뒤와 `main`에 합친 뒤에 확인하는 것은 다음과 같습니다.

1. PR에서 CI의 검사가 모두 통과합니다.
2. PR을 `main`에 합치면 이슈 #9가 닫힙니다.

## 못 박을 것 (Epic 전역)

- 허용 목록을 로그인할 때 한 번만 확인하지 않습니다. 보호된 경로의 요청마다 데이터베이스의 `allowed_emails`를 확인합니다. 이유는 SQL로 뺀 사람이 서버를 다시 띄우지 않아도 다음 요청부터 막혀야 하기 때문입니다(ADR-024).
- 허용 목록과 역할을 프로세스의 메모리나 로그인 상태에 담아 두지 않습니다. 이유는 위와 같습니다. 역할을 로그인 상태에 복사해 두면 SQL로 역할을 바꿔도 반영되지 않습니다.
- 쿠키의 값을 데이터베이스에 그대로 저장하지 않습니다. 이유는 데이터베이스의 내용이 새어도 로그인 상태를 가로챌 수 없어야 하기 때문입니다(ARCHITECTURE.md 6절).
- Google이 이메일을 확인하지 않은 계정(`email_verified`가 false)을 로그인시키지 않습니다. 이유는 확인되지 않은 이메일로 허용 목록을 통과할 수 있기 때문입니다(ADR-025).
- 이메일을 소문자로 바꾸지 않은 채 저장하거나 비교하지 않습니다. 이유는 대소문자 차이로 허용된 사람이 막히거나 뺀 사람이 통과할 수 있기 때문입니다(ADR-024).
- 허용 목록에 없는 계정의 `users` 행을 만들지 않습니다. 이유는 서비스를 쓸 수 없는 사람의 정보를 남기지 않기 위해서입니다(ARCHITECTURE.md 6절).
- Google에 `openid`, `email`, `profile` 말고는 요청하지 않습니다. 이유는 필요하지 않고, 다른 범위를 요청하면 사용자에게 경고 화면이 보이기 때문입니다(ADR-025).
- 돌아올 주소를 요청의 Host로 만들지 않습니다. 이유는 프론트엔드의 개발 서버가 백엔드로 요청을 넘길 때 Host를 바꾸기 때문입니다(ADR-025).
- `service`가 Google을 직접 부르지 않고 `IdentityProvider` 포트를 거칩니다. 이유는 테스트에서 가짜 어댑터를 끼우기 위해서입니다(ARCHITECTURE.md 8절).
- 테스트가 실제 Google에 요청하지 않습니다. 이유는 검사가 네트워크와 Google 계정에 기대면 CI에서 돌 수 없기 때문입니다. 실제 Google을 쓰는 것은 S1.7의 점검 스크립트뿐이며, 이 스크립트는 사람이 MANUAL 점검에서 실행합니다(ADR-026).
- 허용 목록을 조회하거나 바꾸는 API를 만들지 않습니다. 이유는 허용 목록을 SQL로만 다루기로 했기 때문입니다(ADR-024).
- 로그인 실패의 원인을 돌려보내는 주소에 담지 않고, 로그에 쿠키의 값, Google의 `code`, 토큰, 클라이언트 비밀값을 남기지 않습니다. 이유는 실패의 원인은 공격자에게 단서가 되고, 이 값들은 로그만으로 로그인 상태를 가로챌 수 있게 하기 때문입니다(ADR-025).

### S1.7 로컬 로그인 점검

백엔드 담당자가 프론트엔드 레포 없이 로컬에서 실제 Google 계정으로 로그인과 로그아웃을 끝까지 확인할 수 있게 합니다. 사람은 Google 화면에서 계정을 고르고 출력을 표와 대조하며, 나머지는 스크립트가 합니다.

| Task | 내용 | 산출물 |
| --- | --- | --- |
| T1.7.1 | 프론트엔드의 개발 서버를 흉내 내는 대역 서버를 만듭니다. 대역 서버는 `FRONTEND_URL`의 주소(로컬은 `http://localhost:5173`)에서 `/api`로 시작하는 요청을 백엔드로 넘깁니다. 이때 프론트엔드의 개발 서버처럼 Host를 백엔드의 주소로 바꿉니다. 백엔드의 응답은 리디렉션을 따라가지 않고, 상태 코드, `Location`, 모든 `Set-Cookie`를 그대로 돌려줍니다. 그 밖의 경로(`/`, `/login`)에는 지금의 주소를 보여 주는 빈 화면을 냅니다. | `scripts/login_check.py`, `tests/infra/test_login_check.py` |
| T1.7.2 | Playwright로 프론트엔드의 동작을 따라가는 점검 스크립트를 만들고, Playwright를 개발 의존성에 추가합니다. 점검할 두 계정의 이메일은 명령의 인자로 받습니다. 스크립트는 대역 서버를 띄우고 화면이 보이는 브라우저를 연 뒤, [testcase.md](testcase.md#로컬-로그인-점검의-테이블-상태)의 두 점검을 차례로 실행합니다. 프론트엔드가 하는 순서대로 로그인을 시작하고, `GET /api/me`와 `POST /api/auth/logout`은 브라우저 안에서 `credentials: 'include'`로 부릅니다. 시점마다 세 테이블의 상태와 브라우저의 상태(주소, 쿠키, `GET /api/me`의 응답)를 출력하고, 표와 다른 것이 있으면 0이 아닌 종료 코드로 끝납니다. | `scripts/login_check.py`, `pyproject.toml`, `uv.lock` |
| T1.7.3 | compose로 띄운 서버가 `.env`의 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `FRONTEND_URL`을 받게 합니다. 대역 서버는 서버가 쓰는 것과 같은 `FRONTEND_URL`에 뜹니다. 그리고 README에 점검을 준비하고 실행하는 방법을 적고, "알아 둘 것"에서 `.env`가 필요 없다는 문장을 고칩니다. | `compose.yaml`, `README.md` |

**대응**: ADR-026, API.md 4.2절과 4.3절(동작 순서 포함), ARCHITECTURE.md 6절, INFRA.md 3.5절, README의 "허용 목록에 사람 넣고 빼기"

**못 박을 것**:

- 스크립트는 Google의 화면에 아무것도 입력하지 않습니다. 계정을 고르고 비밀번호를 넣는 일은 사람이 화면이 보이는 브라우저에서 합니다. 그래서 Google 계정의 비밀번호를 코드, 파일, 환경 변수에 두지 않습니다.
- 브라우저는 실행할 때마다 새 프로필로 열고, Google의 로그인 상태가 담긴 프로필을 디스크에 남기지 않습니다. 이유는 점검마다 쿠키가 없는 상태에서 시작해야 하고, Google의 로그인 상태가 레포나 디스크에 남으면 안 되기 때문입니다.
- Google이 자동화된 브라우저라는 이유로 로그인을 거부하면, 그것을 피하는 옵션을 넣지 않고 사람에게 알립니다. 이유는 Google 계정의 보호 장치를 우회하는 일이기 때문입니다. 그때의 방법은 ADR-026의 재검토 조건에 따라 사람이 정합니다.
- 스크립트는 개발용 데이터베이스를 읽기만 하고 쓰지 않습니다. 점검 전의 상태가 표와 다르면 브라우저를 열지 않고, 상태를 맞추는 SQL을 보여 준 뒤 끝냅니다. 이유는 스크립트가 개발자의 데이터를 지우거나 바꾸면 안 되기 때문입니다.
- 쿠키의 값을 출력하거나 파일에 남기지 않습니다. `token_hash`는 쿠키 값의 SHA-256과 같은지만 출력합니다. 이유는 쿠키 값만 있으면 로그인 상태를 가로챌 수 있기 때문입니다.
- 스크립트는 `scripts/check.sh`와 CI에서 실행하지 않습니다. 이유는 실제 Google 계정과 사람의 입력이 필요하기 때문입니다. 다만 대역 서버가 요청을 넘기는 방식과 점검 전 상태의 확인은 Google 없이 확인할 수 있으므로, `scripts/check.sh`의 테스트로 확인합니다.
- Google의 설정값이 없는 CI에서도 compose 스모크가 계속 통과해야 합니다. 이유는 CI에 Google 클라이언트의 비밀값을 두지 않기 때문입니다.

**MANUAL 점검표**: `phases/1-login-allowlist/MANUAL.md`에는 TC-1.7.3과 TC-1.7.4를 옮기고, 다음을 넣습니다.

- 점검을 준비하는 순서와 명령. `.env`에 Google 클라이언트의 값을 넣고 compose로 서버를 띄우는 것, 허용할 계정을 README의 SQL로 허용 목록에 넣는 것, Playwright의 브라우저를 설치하는 것, 점검 스크립트를 실행하는 것입니다.
- **로그인 전, 로그인 후, 로그아웃 전, 로그아웃 후에 세 테이블이 어떤 상태여야 하는지.** [testcase.md](testcase.md#로컬-로그인-점검의-테이블-상태)의 "로컬 로그인 점검의 테이블 상태"에 있는 두 표를 그대로 옮깁니다. 표는 체크 항목이 아닌 안내이므로, 목록 기호 없이 체크 항목 위에 둡니다(`.claude/commands/harness.md`의 D-4).
- 체크 항목마다 관찰한 값에 스크립트가 출력한 시점별 실제 상태를 적게 하고, 표와 다른 것이 있으면 그 차이를 적게 합니다.
