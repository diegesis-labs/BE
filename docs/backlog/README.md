# Epic 지도

이 문서는 [PRD.md](../PRD.md)의 요구사항과 [ARCHITECTURE.md](../ARCHITECTURE.md)의 설계를 실행할 수 있는 단위로 나눈 목록입니다. 실행하는 절차는 [HARNESS.md](../HARNESS.md)에 있고, 낯선 용어의 뜻은 [GLOSSARY.md](../GLOSSARY.md)에 있습니다.

## 1. Epic 목록

Epic 하나는 GitHub 이슈 하나와 짝을 이룹니다. Epic의 진행 상황은 이슈로만 보고, Epic 문서는 에이전트와 리뷰가 근거로 삼는 곳입니다. Epic의 PR이 `main`에 합쳐지면 PR 본문의 `Closes #<번호>`가 이슈를 닫습니다. Story마다 이슈를 따로 만들지는 않습니다.

| 번호 | Epic | 목표 | GitHub 이슈 | 문서 |
| --- | --- | --- | --- | --- |
| 0 | project-setup | 비즈니스 로직 없이 개발 환경을 세팅하고, harness 워크플로우가 처음부터 `main` 병합과 이미지 push까지 동작하는지 확인한다. | #4 | [`epic-0/E0-project-setup.md`](epic-0/E0-project-setup.md) |

문서 칸에는 Epic 문서로 가는 링크를 겁니다.

버그를 고치는 작업은 `bugfix-<번호>`라는 이름으로 같은 표에 넣으며, 문서는 `docs/backlog/bugfix-<번호>/`에 둡니다.

## 2. Epic 문서의 형식

Epic 문서는 `docs/backlog/epic-<번호>/E<번호>-<이름>.md`에 씁니다. 아래 절을 이 순서와 이 이름으로 둡니다. 절의 이름을 바꾸면 안 됩니다. 리뷰가 "못 박을 것 (Epic 전역)"이라는 이름으로 그 절을 찾기 때문입니다.

```markdown
---
title: 책 목록과 챕터 본문
description: 허용된 사용자가 책 목록과 챕터 본문을 받는 Epic의 정의다.
---

# Epic 3: 책 목록과 챕터 본문

| 항목 | 값 |
| --- | --- |
| GitHub 이슈 | #12 |
| 마일스톤 | 3주차 |
| phase | `phases/3-books/` |

## 목표

허용된 사용자가 책 목록을 조회하고 챕터의 본문을 문장 단위로 받습니다.

## 입력

이 Epic이 시작할 때 이미 있어야 하는 것을 적습니다. 예를 들면 "Epic 1의 로그인 상태 확인"과 같습니다.

## 끝나는 조건

이 Epic이 끝났다고 말할 수 있는 조건을 확인할 수 있는 문장으로 적습니다.

## 범위 밖

이 Epic에서 하지 않는 것과, 그것을 어느 Epic이 하는지를 적습니다.

## 닫은 결정

이 Epic을 설계하면서 정한 것을 날짜와 함께 적습니다. 제품의 범위에 관한 결정이면 DECISIONS.md에, 기술 선택이면 ADR.md에 기록하고 여기에는 번호만 적습니다.

## 못 박을 것 (Epic 전역)

이 Epic의 모든 step이 지켜야 하는 제약을 적습니다. "X를 하지 않습니다. 이유는 Y입니다."의 형태로 씁니다.

## Story

### S3.1 책과 챕터의 저장

| Task | 내용 | 산출물 |
| --- | --- | --- |
| T3.1.1 | 책, 챕터, 문장의 테이블을 선언합니다. | `app/books/models.py`, 마이그레이션 |
| T3.1.2 | 책 목록과 챕터의 문장을 읽는 repository를 만듭니다. | `app/books/repository.py` |

**대응**: API.md 4.5절, ARCHITECTURE.md 6절

**못 박을 것**: 독자에게는 책의 최신 버전만 보입니다(AI_CONTRACT.md 6절).
```

Story의 번호는 `S<Epic 번호>.<순번>`으로, Task의 번호는 `T<Epic 번호>.<Story 순번>.<순번>`으로 붙입니다. **대응**에는 이 Story가 구현하는 문서의 자리를 적습니다. 이 레포의 요구사항에는 따로 번호가 없으므로, `API.md 4.5절`이나 `D-12`처럼 문서의 절 번호와 결정 번호로 가리킵니다.

## 3. 테스트 케이스의 형식

테스트 케이스는 Epic 문서와 같은 폴더의 `testcase.md`에 씁니다. 번호는 `TC-<Epic 번호>.<Story 순번>.<순번>`으로 붙입니다.

```markdown
---
title: Epic 3 테스트 케이스
description: Epic 3의 Story가 지켜야 하는 것을 확인하는 테스트 케이스의 목록이다.
---

# Epic 3 테스트 케이스

| TC | Story | 방식 | 케이스 | 합격 기준 | 대응 |
| --- | --- | --- | --- | --- | --- |
| TC-3.2.1 | S3.2 | unit | 허용 목록에 없는 계정이 챕터 본문을 요청합니다. | 403과 `NOT_ALLOWED`를 받고, 응답에 문장이 하나도 없습니다. **관문을 빼고 구현하면 실패해야 합니다.** | API.md 2.3절, D-06 |
| TC-3.1.2 | S3.1 | integration | 같은 책의 묶음을 두 번 적재한 뒤 챕터를 읽습니다. | 최신 버전의 문장만 돌아옵니다. **버전을 구분하지 않고 구현하면 실패해야 합니다.** | AI_CONTRACT.md 6절 |

## 이 Epic에서 판정하지 않는 것

- 본문이 화면에서 읽기 편하게 보이는지는 프론트엔드의 일입니다.
```

합격 기준에는 **어떤 틀린 구현이 실패해야 하는지**를 함께 적습니다. 이것을 반증 조건이라고 부르며, step 파일로 옮겨 적습니다. 반증 조건이 없으면 틀린 구현도 통과시키는 테스트가 만들어지기 쉽습니다.

"이 Epic에서 판정하지 않는 것" 절은 리뷰가 범위 밖의 것을 결함으로 올리지 않게 하는 경계입니다. 이 절의 이름도 바꾸면 안 됩니다.

### 3.1 방식

| 방식 | 뜻 | 확인하는 주체 |
| --- | --- | --- |
| `unit` | 순수 로직, 그리고 가짜 어댑터를 끼운 `service`와 `router`를 검증합니다. | pytest |
| `integration` | `repository`와 어댑터가 실제 PostgreSQL에서 동작하는지 검증합니다. | pytest |
| `manual` | 사람만 확인할 수 있는 것입니다. | 사람 |
| `measure` | 응답 시간처럼 수치를 재서 확인하는 것입니다. 추정으로 채우지 않습니다. | 사람 |

브라우저의 흐름을 따라가는 테스트는 프론트엔드 레포의 일이므로 여기에 두지 않습니다.

step의 완료 조건에는 `unit`과 `integration`만 넣습니다. 완료 조건은 실행할 수 있는 명령이어야 하는데, `manual`과 `measure`는 명령이 아니기 때문입니다. 이 둘을 step에 섞으면 step이 완료를 선언하지 못하거나, 에이전트가 확인하지 않은 것을 추정으로 채우게 됩니다.

### 3.2 `manual`은 꼭 필요할 때만 씁니다

`manual` 항목은 phase의 MANUAL 점검표로 옮겨지며, 사람이 모두 체크하기 전에는 phase가 끝나지 않습니다. 그러므로 사람만 확인할 수 있는 것에만 `manual`을 씁니다.

| `manual`로 적는 것 | `unit`이나 `integration`으로 적는 것 |
| --- | --- |
| 선곡된 곡이 그 장면에 어울리는지 | 중단한 곡이 후보에서 빠지는지 |
| 실제 Google 계정으로 로그인이 끝까지 되는지 | 허용 목록에 없는 계정이 403을 받는지 |
| 배포된 주소에서 프론트엔드와 쿠키를 주고받는지 | 에러 응답이 정해진 형식인지 |
| | 선곡 기록에 선곡 방식이 남는지 |

"명령을 실행해서 출력을 눈으로 확인한다"는 `manual`이 아닙니다. 그 명령과 기대하는 출력을 테스트로 적습니다. 자세한 기준은 [`.claude/commands/harness.md`](../../.claude/commands/harness.md)의 D-4에 있습니다.

## 4. Story를 step으로 옮기는 규칙

Epic 하나는 `phases/<번호>-<이름>/` 하나로 실행합니다. step 파일은 그 Epic을 시작하기 직전에 씁니다. 앞의 Epic이 만든 코드의 경로를 step 파일이 인용해야 하기 때문입니다.

- **한 step은 한 기능 폴더의 한 층만 다룹니다.** 층이 여럿인 Story는 안쪽부터 `models`와 `repository`, `service`, `router`와 `schemas`의 순서로 step을 나눕니다. 안쪽이 먼저인 이유는 바깥쪽이 안쪽의 약속을 읽고 써야 하기 때문입니다.
- **포트의 선언과 어댑터의 구현은 서로 다른 step으로 나눕니다.** `service`는 포트만 알면 만들 수 있고, 어댑터는 실제 기술이 있어야 검증할 수 있기 때문입니다.
- **모델을 바꾸는 step에는 마이그레이션을 함께 넣습니다.**
- **문서의 규격을 바꿔야 하는 Story는 문서를 고치는 step을 구현보다 앞에 둡니다.** [API.md](../API.md)나 [AI_CONTRACT.md](../AI_CONTRACT.md)가 여기에 해당합니다. 이 문서들은 다른 팀과 맺은 약속이므로, 규격을 바꿀 때에는 그 팀과 먼저 합의합니다.
- **`manual`과 `measure`만으로 끝나는 Epic은 `phases/`에 넣지 않습니다.** 사람이 재야 하는 것을 에이전트에게 맡기면, 재지 않은 수치를 추정으로 채우기 때문입니다. 이런 Epic은 사람이 점검표와 결과 기록으로 진행합니다.

step 파일의 형식과 설계 원칙은 [`.claude/commands/harness.md`](../../.claude/commands/harness.md)에 있습니다.
