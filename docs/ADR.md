# ADR

이 문서는 백엔드의 기술적 결정을 한 건씩 기록합니다. 각 기록은 어떤 상황에서 결정이 필요했는지, 어떤 후보들을 비교했는지, 무엇으로 정했고 왜 그렇게 정했는지, 그리고 어떤 상황이 되면 다시 검토해야 하는지를 담습니다. 결정의 결과로 만들어진 구조는 [ARCHITECTURE.md](ARCHITECTURE.md)에서, 낯선 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에서 확인할 수 있습니다.

결정을 바꿀 때에는 기존 기록을 지우지 않습니다. 그 대신 기존 기록의 상태를 "대체됨"으로 바꾸고, 새 번호로 새 기록을 추가합니다.

근거 가운데 사용자가 인터뷰에서 직접 밝힌 것이 아니라 문서 작성자가 판단한 것에는 "(작성자 판단)"이라고 표시했습니다.

## ADR-001: 언어와 프레임워크

### 맥락

백엔드 개발자는 한 명이고, 6주 안에 테스트 유저가 실제로 쓸 수 있는 서비스를 내놓아야 합니다. 또한 AI 레포는 Python으로 작성될 예정이며, 백엔드는 AI 레포가 만든 벡터 파일을 읽어서 검증하고 저장해야 합니다. 그리고 이 프로젝트는 포트폴리오로도 쓰입니다.

### 후보 비교

| 기준 | Python + FastAPI | Java/Kotlin + Spring Boot | TypeScript + NestJS | Python + Django |
| --- | --- | --- | --- | --- |
| AI 레포와 같은 언어인가 | 같다 | 다르다 | 다르다 | 같다 |
| 벡터 파일(Parquet, NumPy)을 다루기 쉬운가 | 쉽다 | 별도 라이브러리가 필요하다 | 별도 라이브러리가 필요하다 | 쉽다 |
| API 문서(OpenAPI)가 자동으로 만들어지는가 | 기본으로 만들어진다 | 추가 설정이 필요하다 | 추가 설정이 필요하다 | 추가 패키지가 필요하다 |
| 혼자 6주 안에 만들기에 가벼운가 | 가볍다 | 설정과 코드량이 많다 | 보통이다 | 관리자 화면 등 쓰지 않을 기능이 많다 |
| 프론트엔드와 타입을 공유할 수 있는가 | OpenAPI에서 자동 생성한다 | OpenAPI에서 자동 생성한다 | 직접 공유할 수 있다 | OpenAPI에서 자동 생성한다 |
| 2차에 AI 모델을 서버에 붙이기 쉬운가 | 쉽다 | 어렵다 | 어렵다 | 쉽다 |

### 결정

Python과 FastAPI를 씁니다. 요청과 응답의 형식 검사는 Pydantic으로 합니다.

### 근거

- 사용자가 Python과 FastAPI를 직접 선택했습니다.
- AI 레포와 언어가 같으므로 산출물 묶음을 읽고 검증하는 코드를 쉽게 작성할 수 있고, 필요하다면 규격을 정의한 코드를 두 레포가 함께 쓸 수도 있습니다. (작성자 판단)
- FastAPI는 코드에 적은 요청과 응답의 형식으로부터 OpenAPI 문서를 자동으로 만들어 주므로, 프론트엔드와 약속한 "API 스펙 공유" 방식을 추가 작업 없이 충족합니다. (작성자 판단)
- 2차 마일스톤에서 서버가 AI 모델을 직접 호출하게 되더라도 같은 언어 안에서 확장할 수 있습니다. (작성자 판단)

### 재검토 조건

팀에 백엔드 개발자가 늘어나고 그 사람들이 다른 언어에 훨씬 익숙하다면 다시 검토합니다. 다만 MVP 기간 안에는 바꾸지 않습니다.

## ADR-002: 데이터베이스와 벡터 검색

### 맥락

서비스는 사용자, 책, 곡, 기록 같은 일반 데이터와 함께, 장면과 음악 구간의 벡터를 저장해야 합니다. 그리고 책을 읽는 동안 "이 장면의 벡터와 가장 가까운 음악 구간"을 찾아야 하며, 이때 그 사용자가 중단한 곡은 결과에서 빠져야 합니다. 음악 목록의 규모는 AI팀이 정할 일이어서 아직 알 수 없습니다. 팀의 초기 메모(파이프라인 개선안 v2)에는 벡터 저장소 후보로 Qdrant와 pgvector가 함께 적혀 있었습니다.

### 후보 비교

| 기준 | A. PostgreSQL + pgvector | B. PostgreSQL + Qdrant | C. 적재할 때 후보를 미리 계산 |
| --- | --- | --- | --- |
| 방식 | 일반 데이터와 벡터를 데이터베이스 한 곳에 둔다 | 벡터만 전용 데이터베이스에 둔다 | 책을 적재할 때 장면마다 후보 곡을 계산해 저장한다 |
| 운영할 컨테이너 | API와 데이터베이스, 2개 | 3개 | 2개 |
| 중단한 곡을 빼는 방법 | 검색 쿼리 한 번에 함께 처리한다 | 두 데이터베이스 사이에서 곡 ID 목록을 주고받아야 한다 | 미리 계산한 후보가 모두 소진될 수 있다 |
| 음원을 추가했을 때 | 바로 검색에 반영된다 | 바로 검색에 반영된다 | 모든 책의 후보를 다시 계산해야 한다 |
| 무리 없이 감당하는 규모 | 벡터 수십만 개 | 벡터 수백만 개 이상 | 규모와 무관하다 |
| 데이터의 일관성 | 한 트랜잭션으로 보장된다 | 두 저장소를 직접 맞춰야 한다 | 한 트랜잭션으로 보장된다 |

### 결정

A안, 곧 PostgreSQL과 pgvector를 씁니다.

### 근거

- 사용자가 A안을 선택했습니다.
- 벡터와 중단 기록이 같은 데이터베이스에 있으므로, 중단한 곡을 처음부터 뺀 채로 후보 k개를 가져오는 검색을 쿼리 하나로 작성할 수 있습니다. 사용자가 이 동작을 직접 요구했습니다.
- 음악 목록이 수천 곡이라면 벡터는 수십만 개 수준이며, 이 규모는 pgvector로 충분히 다룰 수 있습니다. (작성자 판단)
- 혼자 운영해야 하므로 관리할 대상이 가장 적은 구성이 유리합니다. (작성자 판단)
- C안은 "읽을 때마다 나오는 음악이 달라진다"는 팀의 결정(10월 18일 회의)과 음원을 계속 추가해야 하는 상황에 맞지 않습니다. (작성자 판단)
- 벡터 검색은 `VectorSearch` 포트 뒤에 두므로(ADR-007), 나중에 B안으로 옮기더라도 어댑터만 바꾸면 됩니다.

### 재검토 조건

다음 중 하나에 해당하면 Qdrant로 옮기는 안을 다시 검토합니다.

- 음악 목록이 MTG-Jamendo 전체 수준(5만 곡 이상)으로 커져서 벡터가 수백만 개에 이를 때
- 선곡 요청 한 번의 응답 시간이 페이지 넘김을 방해할 만큼 길어질 때

## ADR-003: AI 모델을 실행하는 방식

### 맥락

장면을 나누고, 장면에 어울리는 음악을 묘사하는 캡션을 쓰고, 캡션과 음악을 임베딩으로 바꾸는 데에는 AI 모델이 필요하며, 이 모델들은 GPU가 있어야 빠르게 돌아갑니다. 그런데 MVP에서 읽을 수 있는 책은 팀이 미리 준비한 책으로 한정되고, 일반 사용자는 책을 올릴 수 없습니다. 또한 11월 17일 회의에서 모델 학습은 MVP 범위가 아니라고 정했습니다.

### 후보 비교

| 기준 | A. 오프라인 배치만 | B. 추론 서버를 항상 켜 둠 | C. 백엔드 프로세스 안에 모델을 탑재 |
| --- | --- | --- | --- |
| 책을 읽는 동안 필요한 것 | 벡터 검색뿐이다 | 벡터 검색뿐이다 | 벡터 검색뿐이다 |
| 새 책을 추가하는 방법 | AI팀이 분석한 결과 파일을 올린다 | 원본을 올리면 서버가 분석한다 | 원본을 올리면 서버가 분석한다 |
| 서버에 GPU가 필요한가 | 필요 없다 | 필요하다 | 필요하다 |
| 운영 비용과 부담 | 가장 낮다 | 높다 | 높고, 서버 이미지가 매우 커진다 |
| 추가로 만들어야 하는 것 | 없다 | 추론 서버, 작업 대기열 | 작업 대기열 |

### 결정

A안을 씁니다. AI 모델은 AI 레포가 오프라인 배치로만 실행하며, 백엔드 서버에서는 실행하지 않습니다.

### 근거

- 사용자가 "책은 고정 목록이고, 관리자가 올리는 것은 AI가 만든 산출물 묶음"이라고 결정했습니다. 따라서 사용자의 요청을 처리하는 동안에는 모델이 필요한 순간이 없습니다.
- 장면의 벡터와 음악 구간의 벡터가 모두 미리 만들어져 있으므로, 책을 읽는 동안에는 벡터끼리 비교하는 검색만 하면 됩니다.
- GPU 서버를 항상 켜 두는 비용과 운영 부담은 테스트 유저 10명 규모의 MVP에 맞지 않습니다. (작성자 판단)

### 재검토 조건

일반 사용자가 자신의 책을 올릴 수 있게 하거나, 관리자가 원본 책만 올려도 자동으로 분석되게 하려는 시점에 B안을 검토합니다. 이때를 대비해 적재 과정을 "묶음을 읽고 검증하는 단계"와 "저장하는 단계"로 나누어 두었으므로, 앞 단계만 "모델 서비스를 호출하는 단계"로 바꾸면 됩니다.

## ADR-004: AI 레포와 백엔드의 연동 방식

### 맥락

AI 레포가 만든 분석 결과(문장, 장면, 캡션, 벡터, 곡 정보)를 백엔드의 데이터베이스에 넣어야 합니다. 그리고 팀원이 새 책을 추가할 수 있어야 하므로 관리자용 업로드 기능이 필요합니다. 한편 AI 레포는 아직 비어 있어서, 결과물의 형식이 정해져 있지 않습니다.

### 후보 비교

| 기준 | A. 산출물 묶음 파일 + 관리자 업로드 API | B. AI 레포가 데이터베이스에 직접 저장 | C. 백엔드가 AI 모델 API를 호출 |
| --- | --- | --- | --- |
| 두 레포 사이의 약속 | 파일 규격 하나 | 데이터베이스 구조 전체 | 모델 API의 규격 |
| 데이터베이스 구조를 바꿀 때 | 백엔드만 고치면 된다 | 두 레포를 함께 고쳐야 한다 | 백엔드만 고치면 된다 |
| 잘못된 데이터를 막는 곳 | 백엔드가 적재 전에 검증한다 | 막는 곳이 없다 | 백엔드가 검증한다 |
| AI팀이 독립적으로 일할 수 있는가 | 그렇다 | 데이터베이스 접속 권한과 구조를 알아야 한다 | 추론 서버를 운영해야 한다 |
| MVP에서 필요한 추가 작업 | 규격 문서와 검증 코드 | 적다 | 추론 서버와 작업 대기열 |

### 결정

A안을 씁니다. AI 레포가 정해진 규격의 산출물 묶음(zip 파일)을 만들고, 팀원이 관리자 API로 올리면 백엔드가 검증한 다음 적재합니다. 다만 용량이 큰 음원 파일은 오브젝트 저장소에 직접 올리고, 묶음에는 파일 이름만 담습니다.

### 근거

- 사용자가 "AI가 산출물 파일을 만들고 백엔드가 적재한다"와 "관리자가 올리는 것은 AI가 만든 산출물 묶음"을 선택했습니다.
- 두 팀의 약속이 파일 규격 하나로 줄어들기 때문에, 각 팀이 상대의 내부 구조를 몰라도 일할 수 있습니다. (작성자 판단)
- 백엔드가 적재하기 전에 검증하므로, 문장 번호가 어긋나거나 벡터의 차원이 틀린 데이터가 서비스에 들어오는 일을 막을 수 있습니다. (작성자 판단)
- 음원 파일은 합치면 수 GB 이상이 될 수 있어서 API 요청 하나로 올리기에 적합하지 않습니다. (작성자 판단)

### 재검토 조건

산출물 묶음의 규격은 아직 백엔드의 제안이며 AI팀과 합의해야 합니다. 합의 과정에서 규격이 바뀌면 [AI_CONTRACT.md](AI_CONTRACT.md)를 고치고, 연동 방식 자체가 바뀌면 이 기록을 새로 씁니다.

## ADR-005: 프론트엔드와의 API 연동 방식

### 맥락

프론트엔드는 Vite와 React로 만든 SPA이며, 자체 서버가 없습니다. 프론트엔드 레포의 문서에는 백엔드와 합의해야 할 항목 다섯 가지(API 기본 경로와 로컬 포트, 인증 방식, 에러 응답 형식, API 스펙 공유 방식, 헬스체크 엔드포인트)가 남아 있습니다. 또한 프론트엔드의 API 호출 코드는 이미 기본 경로 `/api`, 로컬 백엔드 포트 `8080`, 쿠키를 함께 보내는 설정으로 작성되어 있습니다.

그리고 한 가지 더 정해야 할 것이 있습니다. 페이지를 나누는 일은 화면 크기와 글꼴을 아는 프론트엔드만 할 수 있는데, 페이지를 넘겼을 때 "어느 장면의 음악을 틀 것인가"를 어느 쪽이 판단할지입니다.

### 후보 비교: API 방식

| 기준 | REST + OpenAPI | GraphQL |
| --- | --- | --- |
| 프론트엔드의 현재 코드와 맞는가 | 그대로 맞는다 | GraphQL 클라이언트를 새로 도입해야 한다 |
| 타입 공유 | OpenAPI 문서에서 TypeScript 타입을 자동 생성한다 | 스키마에서 자동 생성한다 |
| 화면 수가 적은 MVP에 맞는가 | 맞는다 | 과하다 |
| 백엔드 구현 부담 | 낮다 | 스키마와 리졸버를 따로 작성해야 한다 |

### 후보 비교: 장면을 고르는 곳

| 기준 | 백엔드가 고른다 | 프론트엔드가 고른다 |
| --- | --- | --- |
| 프론트엔드가 보내는 것 | 화면에 보이는 문장 번호의 범위 | 고른 장면의 번호 |
| 우선순위 규칙을 바꿀 때 | 백엔드만 배포하면 된다 | 프론트엔드를 다시 배포해야 한다 |
| 평가 기록 | 장면 선택부터 선곡까지 한곳에 남는다 | 장면 선택 과정이 기록에서 빠진다 |
| 요청 횟수 | 페이지를 넘길 때마다 한 번 | 장면이 바뀔 때만 한 번 |

### 결정

- REST 방식으로 연동하고, FastAPI가 자동으로 만드는 OpenAPI 문서를 API 스펙으로 공유합니다.
- 모든 경로에 `/api` 접두사를 붙이고, 로컬 개발 포트는 `8080`으로 합니다.
- 책 본문은 문장 번호가 붙은 구조화 JSON으로 내려줍니다.
- 장면 선택은 백엔드가 합니다. 프론트엔드는 화면에 보이는 문장 번호의 범위만 보냅니다.
- 에러 응답 형식과 엔드포인트의 상세는 [API.md](API.md)에서 정의합니다.

### 근거

- 사용자가 구조화 JSON과 백엔드의 장면 선택을 선택했습니다.
- 테스트용 책의 원본이 사진 스캔본과 AI가 합성한 글이어서 EPUB 파일이 아니라 일반 텍스트이며, 장면의 경계도 문장 단위로 정해집니다. 그러므로 문장 번호를 공통 단위로 쓰면 "지금 페이지에 어떤 장면이 있는가"를 정확히 계산할 수 있습니다.
- 경로와 포트를 프론트엔드의 현재 설정에 맞추면 프론트엔드가 고칠 것이 없습니다. (작성자 판단)
- 장면 선택 규칙이 백엔드에 있으면 규칙을 조정할 때 한 곳만 고치면 되고, 평가 기록도 한곳에 모입니다. (작성자 판단)

### 재검토 조건

- 페이지를 넘길 때마다 요청을 보내는 방식이 체감 속도를 떨어뜨린다면, 장면의 경계를 프론트엔드에 미리 내려주는 방식을 검토합니다.
- 프론트엔드가 EPUB 뷰어 라이브러리를 쓰기로 한다면 본문 형식을 다시 정합니다.

## ADR-006: 로그인과 접근 제한

### 맥락

"중단한 곡은 그 사용자에게 다시 틀지 않는다"는 요구사항과 평가 기록을 위해서는 사용자를 구별해야 합니다. 그리고 테스트용 책에는 저작권이 있는 소설(『노르웨이의 숲』의 일부 챕터)이 포함되므로, 아무나 본문을 볼 수 있어서는 안 됩니다. 또한 프론트엔드는 자체 서버가 없는 SPA이며, 이미 쿠키를 함께 보내도록 설정되어 있습니다.

### 후보 비교: 사용자를 구별하는 방법

| 기준 | Google 로그인 + 허용 목록 | 초대 코드 + 닉네임 | 이메일과 비밀번호 가입 | 기기별 익명 ID |
| --- | --- | --- | --- | --- |
| 접근을 제한할 수 있는가 | 그렇다 | 그렇다 | 따로 만들어야 한다 | 아니다 |
| 기기를 바꿔도 기록이 이어지는가 | 그렇다 | 코드를 다시 넣으면 이어진다 | 그렇다 | 아니다 |
| 앱 밖의 설문과 연결하기 쉬운가 | 이메일로 연결한다 | 닉네임으로 연결한다 | 이메일로 연결한다 | 어렵다 |
| 구현 부담 | Google 연동이 필요하다 | 가장 가볍다 | 비밀번호 저장과 재설정이 필요하다 | 가장 가볍다 |
| 실제 서비스와 비슷한 경험인가 | 그렇다 | 아니다 | 그렇다 | 아니다 |

### 후보 비교: 로그인 상태를 주고받는 방법

| 기준 | 쿠키 | 토큰을 요청 헤더에 담기 |
| --- | --- | --- |
| 프론트엔드가 할 일 | 없다 (현재 설정 그대로) | 토큰을 저장하고 갱신하는 코드를 작성해야 한다 |
| 스크립트가 값을 훔쳐볼 수 있는가 | 없다 (HttpOnly 쿠키) | 브라우저 저장소에 두면 가능하다 |
| 프론트엔드와 백엔드의 도메인이 달라도 되는가 | 같은 도메인이어야 안정적이다 | 달라도 된다 |
| 강제로 로그아웃시킬 수 있는가 | 서버에서 지우면 된다 | 별도 장치가 필요하다 |

### 결정

- Google 계정으로 로그인하게 하고, 허용 목록에 이메일이 있는 사람만 서비스를 쓸 수 있게 합니다.
- 관리자 권한도 같은 허용 목록에서 역할로 구분합니다.
- 로그인 상태는 서버의 데이터베이스에 저장하고, 브라우저에는 스크립트가 읽을 수 없는 쿠키(HttpOnly)로 식별자만 심습니다.
- Google 로그인의 전 과정은 백엔드가 처리합니다.

### 근거

- 사용자가 Google 로그인, 허용 이메일 목록, 쿠키 방식을 각각 선택했습니다.
- 프론트엔드에 서버가 없으므로 Google과 비밀값을 주고받는 일은 백엔드가 맡아야 합니다.
- 로그인 상태를 서버에 저장하면 허용 목록에서 뺀 사람의 접근을 곧바로 끊을 수 있어서, 저작권이 있는 본문을 보호하기에 유리합니다. (작성자 판단)
- 로그인 상태를 PostgreSQL에 저장하면 별도의 저장소를 추가로 운영하지 않아도 됩니다. (작성자 판단)

### 이 결정이 요구하는 조건

쿠키 방식이 Safari를 포함한 모든 브라우저에서 안정적으로 동작하려면, 배포 환경에서 프론트엔드와 백엔드가 같은 도메인 아래에 있어야 합니다. 주소 하나를 함께 쓰는 구성과 `app.diegesis.example`, `api.diegesis.example`처럼 하위 주소를 나누어 쓰는 구성이 모두 이 조건을 충족합니다. 두 구성의 차이와 필수 조건은 [INFRA.md](INFRA.md)에 적어 두었습니다.

### 재검토 조건

- 프론트엔드와 백엔드를 같은 도메인 아래에 둘 수 없게 되면 토큰 방식을 검토합니다.
- 네이티브 앱으로 배포하는 2차 마일스톤에서 인증 방식을 다시 검토합니다.

## ADR-007: 코드 구조

### 맥락

백엔드 코드를 어떤 기준으로 폴더를 나눌지 정해야 합니다. 벡터 검색 도구, 음원 저장소, 로그인 서비스는 나중에 바뀔 가능성이 있으며, 특히 음원 저장소는 인프라가 정해지지 않아 지금은 무엇을 쓸지 알 수 없습니다.

### 후보 비교

| 기준 | 기능별 모듈 + 포트와 어댑터 | 계층별 폴더 | 전면적인 헥사고날 구조 |
| --- | --- | --- | --- |
| 폴더를 나누는 기준 | 기능 (로그인, 책, 선곡 등) | 역할 (라우터, 서비스, 저장소 등) | 도메인, 유스케이스, 어댑터 |
| 기능 하나를 고칠 때 | 폴더 하나만 보면 된다 | 여러 폴더를 오가야 한다 | 여러 폴더를 오가야 한다 |
| 기술을 교체하기 쉬운가 | 포트로 감싼 지점은 쉽다 | 어렵다 | 가장 쉽다 |
| 파일 수와 간접 계층 | 적당하다 | 가장 적다 | 가장 많다 |
| 프론트엔드 구조와의 대응 | 기능 단위라 서로 대응된다 | 대응되지 않는다 | 대응되지 않는다 |

### 결정

코드는 기능별 모듈로 나눕니다. 그리고 들어오는 쪽(HTTP 요청)과 나가는 쪽(데이터베이스, 저장소, 로그인 서비스, 묶음 파일)은 포트로 추상화하고, 실제 구현은 어댑터에 둡니다. 구체적인 폴더 구조와 포트 목록은 [ARCHITECTURE.md](ARCHITECTURE.md#8-코드-구조)에 있습니다.

### 근거

- 사용자가 기능별 모듈을 선택하면서, 들어오는 쪽과 나가는 쪽의 포트를 추상화해 코드의 재사용성을 확보하라고 요구했습니다.
- 전면적인 헥사고날 구조는 6주 MVP에 비해 파일과 간접 계층이 많아지므로, 실제로 교체될 가능성이 있는 지점에만 포트를 둡니다. (작성자 판단)
- 포트가 있으면 테스트할 때 가짜 어댑터를 끼워 넣을 수 있어서, 데이터베이스나 Google 없이도 핵심 규칙을 검증할 수 있습니다. (작성자 판단)

### 재검토 조건

기능 모듈 사이의 의존이 복잡하게 얽히기 시작하면 모듈의 경계를 다시 나눕니다.

## ADR-008: 임베딩 모델과 선곡 방식의 추상화

### 맥락

팀은 MuQ-MuLan을 기본 임베딩 모델로 쓰되, LAION-CLAP을 비교 대상으로 함께 준비하기로 했습니다. MuQ-MuLan의 가중치는 비상업 라이선스여서 나중에 모델을 바꿔야 할 수도 있습니다. 또한 리서치 문서들은 "무음, 무작위 선곡, 우리 선곡"을 서로 비교하는 평가를 제안하고 있습니다.

### 후보 비교

| 기준 | 모델은 등록 데이터, 선곡 방식은 공통 인터페이스 | 모델마다 테이블과 코드를 따로 둠 | 서버 설정값 하나로 고정 |
| --- | --- | --- | --- |
| 새 모델을 추가할 때 | 묶음을 올리면 된다 | 테이블과 코드를 추가해야 한다 | 가능하지만 한 번에 하나만 쓸 수 있다 |
| 여러 모델을 동시에 비교할 수 있는가 | 그렇다 | 그렇다 | 아니다 |
| 사용자마다 다른 방식을 쓸 수 있는가 | 그렇다 | 따로 만들어야 한다 | 아니다 |
| 구현 부담 | 보통이다 | 모델이 늘수록 커진다 | 가장 낮다 |

### 결정

- 임베딩 모델은 코드가 아니라 데이터베이스에 등록하는 데이터로 다룹니다. 벡터는 "어떤 모델이 만들었는지"와 함께 저장합니다. 그리고 처음 보는 모델은 산출물 묶음을 적재할 때 자동으로 등록합니다.
- 선곡 방식은 공통 인터페이스(`RecommendationStrategy`)의 구현체로 만듭니다. MVP에는 임베딩, 랜덤, 무음 세 가지를 둡니다.
- 사용자가 설정 화면에서 선곡 방식과 임베딩 모델을 직접 바꿀 수 있게 합니다.

### 근거

- 사용자가 선곡 방식과 임베딩 모델의 비교를 사용자 본인이 프론트엔드에서 직접 할 수 있게 하자고 제안했고, 임베딩 모델은 쉽게 추가할 수 있도록 추상화하라고 요구했습니다.
- 백엔드는 모델을 실행하지 않고 벡터만 저장하므로(ADR-003), 모델을 추가하는 일을 데이터 등록만으로 끝낼 수 있습니다.
- 직접 언급 장면의 지정 곡은 임베딩 방식에만 적용합니다. 랜덤과 무음은 비교의 기준선이므로 섞이지 않게 합니다. (작성자 판단)

### 재검토 조건

벡터의 차원이 매우 큰 모델(pgvector의 인덱스가 지원하는 한도를 넘는 모델)을 추가해야 할 때 저장 방식을 다시 검토합니다.

## ADR-009: 데이터베이스 접근 도구와 개발 도구

### 맥락

ADR-001과 ADR-002에 따라 Python에서 PostgreSQL과 pgvector를 다뤄야 합니다. 그리고 데이터베이스의 구조가 바뀔 때마다 그 이력을 관리해야 하며, 혼자 개발하더라도 코드 품질을 자동으로 점검할 도구가 필요합니다.

### 후보 비교: 데이터베이스 접근 도구

| 기준 | SQLAlchemy + Alembic | SQLModel | Tortoise ORM |
| --- | --- | --- | --- |
| pgvector와 함께 쓸 수 있는가 | pgvector의 Python 패키지가 지원한다 | SQLAlchemy를 통해 지원한다 | 구현 시 확인이 필요하다 |
| 복잡한 쿼리를 작성하기 쉬운가 | 쉽다 | SQLAlchemy로 내려가야 한다 | 어렵다 |
| 구조 변경 이력 관리 | Alembic이 표준이다 | Alembic을 쓴다 | 자체 도구를 쓴다 |
| 자료와 사례가 많은가 | 가장 많다 | 보통이다 | 적다 |

### 결정

| 영역 | 선택 |
| --- | --- |
| 데이터베이스 접근 | SQLAlchemy (비동기 방식, asyncpg 드라이버) |
| 구조 변경 이력 관리 | Alembic |
| 설정값 관리 | pydantic-settings |
| Google 로그인 연동 | Authlib |
| 패키지와 가상환경 관리 | uv |
| 코드 형식과 린트 | ruff |
| 타입 검사 | pyright |
| 테스트 | pytest |
| GitHub Actions의 workflow 검사 | actionlint |

각 도구의 버전은 프로젝트를 세팅하는 시점에 최신 안정 버전을 확인해서 고정합니다.

### 근거

이 결정의 근거는 모두 작성자의 판단입니다.

- 선곡 검색은 벡터 거리 계산, 조건, 중복 제거가 함께 들어가는 쿼리이므로, 쿼리를 세밀하게 작성할 수 있는 SQLAlchemy가 적합합니다.
- SQLModel은 테이블 정의와 응답 형식을 한 클래스로 합쳐 주지만, 이 프로젝트에서는 둘의 모양이 다른 경우가 많아서 이점이 작습니다.
- uv는 패키지 설치와 버전 고정을 도구 하나로 처리하며, ruff는 형식 정리와 린트를 한 도구로 처리합니다.
- 설정값을 pydantic-settings의 클래스 하나로 모으면, 사용자가 요구한 "설정값을 `.env`에서 쉽게 바꿀 수 있는 구조"가 됩니다.
- actionlint는 Epic 0에서 CI의 workflow를 만들며 더했습니다. workflow 파일의 문법 오류와 흔한 실수를 GitHub에 올리기 전에 테스트로 잡기 위해서입니다. 개발 의존성(`actionlint-py`)으로 설치하므로 개발자의 컴퓨터와 CI가 같은 버전을 씁니다.

### 재검토 조건

특정 도구가 프로젝트의 진행을 막는 문제를 일으킬 때 그 도구만 다시 검토합니다.

## ADR-010: 배포 방식

### 맥락

테스트 유저가 접속할 수 있도록 서비스를 배포해야 합니다. 그러나 어디에 배포할지는 프론트엔드와 함께 정해야 하는 부분이어서 아직 결정하지 않았습니다. 이 프로젝트는 포트폴리오용이며 창업 계획은 없으므로, 비용을 거의 들이지 않는 것이 중요합니다.

### 결정

- 백엔드는 Docker 컨테이너로 배포합니다.
- 로컬 개발 환경은 Docker Compose로 API 서버와 PostgreSQL을 함께 띄웁니다.
- 코드가 `main` 브랜치에 합쳐지면 자동으로 컨테이너 이미지를 만들어 배포하며, 만든 이미지는 Docker Hub에 저장합니다. 이 가운데 이미지를 만들어 Docker Hub에 올리는 단계까지는 Epic 0에서 만들었고, 배포 환경에 새 이미지를 반영하는 단계는 배포할 곳이 정해진 뒤에 만듭니다. 자세한 흐름은 [INFRA.md](INFRA.md#37-자동-배포)의 3.7절에 있습니다.
- 음원 파일은 비공개 오브젝트 저장소에 두고, 백엔드가 발급한 서명된 주소로만 받을 수 있게 합니다.
- 호스팅 서비스, 데이터베이스 호스팅, 음원 저장소 같은 구체적인 인프라는 정하지 않고, 결정해야 할 항목과 고려사항을 [INFRA.md](INFRA.md)에 정리합니다.

### 근거

- 사용자가 Docker 컨테이너로 배포한다는 것만 먼저 결정하고, 나머지는 프론트엔드와 상의한 뒤 정하겠다고 했습니다. 그리고 GCP 무료 계정을 옮겨 가며 쓰는 방식도 괜찮아 보인다고 했습니다.
- 컨테이너로 만들어 두면 어느 호스팅 서비스를 고르더라도 그대로 올릴 수 있고, 무료 계정을 옮길 때에도 다시 만들 것이 없습니다. (작성자 판단)
- 사용자가 `main` 브랜치에 합쳐진 코드를 자동으로 배포하고 이미지를 Docker Hub에 저장하기로 정했습니다. Docker Hub는 특정 클라우드에 속하지 않으므로, 어느 호스팅 서비스를 고르더라도 같은 이미지를 가져다 쓸 수 있습니다. (뒤 문장은 작성자 판단)
- 사용자가 음원 파일은 반드시 백엔드가 발급한 서명된 주소로만 접근하게 해야 한다고 정했습니다. 이 규칙은 음원의 라이선스나 AI팀과의 협의와 관계없이 적용합니다.
- 음원 저장소는 `ObjectStorage` 포트 뒤에 두므로(ADR-007), 저장소가 정해지지 않은 지금도 개발을 진행할 수 있습니다. (작성자 판단)

### 재검토 조건

인프라가 정해지면 이 기록의 상태를 "확정"으로 바꾸고, 선택한 인프라와 그 이유를 새 기록으로 추가합니다.

## ADR-011: 통합 테스트용 데이터베이스

### 맥락

[DEVELOPMENT.md](DEVELOPMENT.md)의 테스트 규칙은 벡터 검색처럼 PostgreSQL과 pgvector의 동작에 기대는 코드를 가짜로 대신하지 않고 실제 데이터베이스에서 검증하게 합니다. 그리고 모든 검사는 `scripts/check.sh` 하나로 돌리며, 에이전트 세션의 종료 검사, step의 완료 조건, CI가 모두 이 스크립트를 부릅니다. 그래서 통합 테스트용 데이터베이스를 띄우는 방법은 이 모든 곳에서 똑같이 동작해야 합니다. 또한 harness는 phase마다 worktree를 따로 만들기 때문에, 여러 worktree에서 검사가 동시에 돌 수 있습니다.

### 후보 비교

| 기준 | A. testcontainers | B. compose의 데이터베이스에 접속 | C. 통합 테스트는 CI에서만 |
| --- | --- | --- | --- |
| 방식 | 테스트가 시작될 때 데이터베이스 컨테이너를 무작위 포트로 띄우고, 끝나면 지운다 | 개발자가 먼저 띄워 둔 compose의 데이터베이스에 테스트가 접속한다 | `scripts/check.sh`에서는 통합 테스트를 빼고 CI에서만 돌린다 |
| 개발용 데이터 | 건드리지 않는다 | 테스트가 지우거나 바꿀 수 있다 | 건드리지 않는다 |
| worktree 여러 개가 동시에 돌 때 | 서로 다른 컨테이너를 쓰므로 부딪히지 않는다 | 포트와 데이터가 부딪힌다 | 부딪히지 않는다 |
| 로컬과 CI의 명령 | `scripts/check.sh` 하나로 같다 | CI에 데이터베이스를 띄우는 설정을 따로 둬야 한다 | 서로 다르다 |
| 무인 step이 통합 테스트를 돌리는가 | 돌린다 | 데이터베이스가 떠 있을 때만 돌린다 | 돌리지 않는다 |
| 필요한 것 | 검사를 돌리는 곳마다 Docker | 검사 전에 데이터베이스를 띄우는 절차 | 없다 |

### 결정

A안, 곧 testcontainers를 씁니다. 컨테이너의 이미지는 `compose.yaml`의 데이터베이스 서비스와 같은 것을 쓰며, 이미지의 이름은 `compose.yaml`에서 읽습니다. 그리고 Docker에 닿을 수 없으면 통합 테스트는 건너뛰지 않고 실패합니다.

### 근거

- 사용자가 A안을 선택했습니다.
- 테스트가 개발용 데이터베이스에 접속하지 않으므로, 마이그레이션을 되돌리는 테스트가 개발용 데이터를 지울 수 없습니다. (작성자 판단)
- 로컬, 무인 step, CI가 모두 같은 명령으로 같은 검사를 돌리므로 기준이 갈라지지 않습니다. (작성자 판단)
- Docker가 없을 때 통합 테스트를 건너뛰게 하면, 통합 테스트를 하나도 돌리지 않았는데도 검사가 통과한 것처럼 보입니다. 이것은 검사가 꺼진 것을 숨기므로 실패로 다룹니다. (작성자 판단)

### 재검토 조건

- Docker를 쓸 수 없는 환경에서 검사를 돌려야 할 때 다시 검토합니다.
- 컨테이너를 띄우는 시간 때문에 검사가 지나치게 느려질 때 다시 검토합니다.
