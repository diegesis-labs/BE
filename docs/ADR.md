# ADR

이 문서는 백엔드의 기술적 결정을 한 건씩 기록합니다. 각 기록은 어떤 상황에서 결정이 필요했는지, 어떤 후보들을 비교했는지, 무엇으로 정했고 왜 그렇게 정했는지, 그리고 어떤 상황이 되면 다시 검토해야 하는지를 담습니다. 결정의 결과로 만들어진 구조는 [ARCHITECTURE.md](ARCHITECTURE.md)에서, 낯선 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에서 확인할 수 있습니다.

결정을 바꿀 때에는 기존 기록을 지우지 않습니다. 그 대신 기존 기록의 상태를 "대체됨"으로 바꾸고, 새 번호로 새 기록을 추가합니다.

근거 가운데 사용자가 인터뷰에서 직접 밝힌 것이 아니라 문서 작성자가 판단한 것에는 "(작성자 판단)"이라고 표시했습니다.

## ADR-001: 언어와 프레임워크

### 맥락

백엔드 개발자는 한 명이고, 6주 안에 테스트 유저가 실제로 쓸 수 있는 서비스를 내놓아야 합니다. 또한 AI 레포는 Python으로 작성될 예정이며, 백엔드는 AI 레포가 만든 벡터 파일을 읽어서 검증하고 저장해야 합니다. 그리고 이 프로젝트는 포트폴리오로도 쓰입니다.

### 후보 비교

| 기준 | Python + FastAPI | Java/Kotlin + Spring Boot | TypeScript + NestJS | Python + Django |
| --- | --- | --- | --- | --- |
| AI 레포와 같은 언어인가 | 같다 | 다르다 | 다르다 | 같다 |
| 벡터 파일(Parquet, NumPy)을 다루기 쉬운가 | 쉽다 | 별도 라이브러리가 필요하다 | 별도 라이브러리가 필요하다 | 쉽다 |
| API 문서(OpenAPI)가 자동으로 만들어지는가 | 기본으로 만들어진다 | 추가 설정이 필요하다 | 추가 설정이 필요하다 | 추가 패키지가 필요하다 |
| 혼자 6주 안에 만들기에 가벼운가 | 가볍다 | 설정과 코드량이 많다 | 보통이다 | 관리자 화면 등 쓰지 않을 기능이 많다 |
| 프론트엔드와 타입을 공유할 수 있는가 | OpenAPI에서 자동 생성한다 | OpenAPI에서 자동 생성한다 | 직접 공유할 수 있다 | OpenAPI에서 자동 생성한다 |
| 2차에 AI 모델을 서버에 붙이기 쉬운가 | 쉽다 | 어렵다 | 어렵다 | 쉽다 |

### 결정

Python과 FastAPI를 씁니다. 요청과 응답의 형식 검사는 Pydantic으로 합니다.

### 근거

- 사용자가 Python과 FastAPI를 직접 선택했습니다.
- AI 레포와 언어가 같으므로 산출물 묶음을 읽고 검증하는 코드를 쉽게 작성할 수 있고, 필요하다면 규격을 정의한 코드를 두 레포가 함께 쓸 수도 있습니다. (작성자 판단)
- FastAPI는 코드에 적은 요청과 응답의 형식으로부터 OpenAPI 문서를 자동으로 만들어 주므로, 프론트엔드와 약속한 "API 스펙 공유" 방식을 추가 작업 없이 충족합니다. (작성자 판단)
- 2차 마일스톤에서 서버가 AI 모델을 직접 호출하게 되더라도 같은 언어 안에서 확장할 수 있습니다. (작성자 판단)

### 재검토 조건

팀에 백엔드 개발자가 늘어나고 그 사람들이 다른 언어에 훨씬 익숙하다면 다시 검토합니다. 다만 MVP 기간 안에는 바꾸지 않습니다.

## ADR-002: 데이터베이스와 벡터 검색

### 맥락

서비스는 사용자, 책, 곡, 기록 같은 일반 데이터와 함께, 장면과 음악 구간의 벡터를 저장해야 합니다. 그리고 책을 읽는 동안 "이 장면의 벡터와 가장 가까운 음악 구간"을 찾아야 하며, 이때 그 사용자가 중단한 곡은 결과에서 빠져야 합니다. 음악 목록의 규모는 AI팀이 정할 일이어서 아직 알 수 없습니다. 팀의 초기 메모(파이프라인 개선안 v2)에는 벡터 저장소 후보로 Qdrant와 pgvector가 함께 적혀 있었습니다.

### 후보 비교

| 기준 | A. PostgreSQL + pgvector | B. PostgreSQL + Qdrant | C. 적재할 때 후보를 미리 계산 |
| --- | --- | --- | --- |
| 방식 | 일반 데이터와 벡터를 데이터베이스 한 곳에 둔다 | 벡터만 전용 데이터베이스에 둔다 | 책을 적재할 때 장면마다 후보 곡을 계산해 저장한다 |
| 운영할 컨테이너 | API와 데이터베이스, 2개 | 3개 | 2개 |
| 중단한 곡을 빼는 방법 | 검색 쿼리 한 번에 함께 처리한다 | 두 데이터베이스 사이에서 곡 ID 목록을 주고받아야 한다 | 미리 계산한 후보가 모두 소진될 수 있다 |
| 음원을 추가했을 때 | 바로 검색에 반영된다 | 바로 검색에 반영된다 | 모든 책의 후보를 다시 계산해야 한다 |
| 무리 없이 감당하는 규모 | 벡터 수십만 개 | 벡터 수백만 개 이상 | 규모와 무관하다 |
| 데이터의 일관성 | 한 트랜잭션으로 보장된다 | 두 저장소를 직접 맞춰야 한다 | 한 트랜잭션으로 보장된다 |

### 결정

A안, 곧 PostgreSQL과 pgvector를 씁니다.

### 근거

- 사용자가 A안을 선택했습니다.
- 벡터와 중단 기록이 같은 데이터베이스에 있으므로, 중단한 곡을 처음부터 뺀 채로 후보 k개를 가져오는 검색을 쿼리 하나로 작성할 수 있습니다. 사용자가 이 동작을 직접 요구했습니다.
- 음악 목록이 수천 곡이라면 벡터는 수십만 개 수준이며, 이 규모는 pgvector로 충분히 다룰 수 있습니다. (작성자 판단)
- 혼자 운영해야 하므로 관리할 대상이 가장 적은 구성이 유리합니다. (작성자 판단)
- C안은 "읽을 때마다 나오는 음악이 달라진다"는 팀의 결정(10월 18일 회의)과 음원을 계속 추가해야 하는 상황에 맞지 않습니다. (작성자 판단)
- 벡터 검색은 `VectorSearch` 포트 뒤에 두므로(ADR-007), 나중에 B안으로 옮기더라도 어댑터만 바꾸면 됩니다.

### 재검토 조건

다음 중 하나에 해당하면 Qdrant로 옮기는 안을 다시 검토합니다.

- 음악 목록이 MTG-Jamendo 전체 수준(5만 곡 이상)으로 커져서 벡터가 수백만 개에 이를 때
- 선곡 요청 한 번의 응답 시간이 페이지 넘김을 방해할 만큼 길어질 때

## ADR-003: AI 모델을 실행하는 방식

### 맥락

장면을 나누고, 장면에 어울리는 음악을 묘사하는 캡션을 쓰고, 캡션과 음악을 임베딩으로 바꾸는 데에는 AI 모델이 필요하며, 이 모델들은 GPU가 있어야 빠르게 돌아갑니다. 그런데 MVP에서 읽을 수 있는 책은 팀이 미리 준비한 책으로 한정되고, 일반 사용자는 책을 올릴 수 없습니다. 또한 11월 17일 회의에서 모델 학습은 MVP 범위가 아니라고 정했습니다.

### 후보 비교

| 기준 | A. 오프라인 배치만 | B. 추론 서버를 항상 켜 둠 | C. 백엔드 프로세스 안에 모델을 탑재 |
| --- | --- | --- | --- |
| 책을 읽는 동안 필요한 것 | 벡터 검색뿐이다 | 벡터 검색뿐이다 | 벡터 검색뿐이다 |
| 새 책을 추가하는 방법 | AI팀이 분석한 결과 파일을 올린다 | 원본을 올리면 서버가 분석한다 | 원본을 올리면 서버가 분석한다 |
| 서버에 GPU가 필요한가 | 필요 없다 | 필요하다 | 필요하다 |
| 운영 비용과 부담 | 가장 낮다 | 높다 | 높고, 서버 이미지가 매우 커진다 |
| 추가로 만들어야 하는 것 | 없다 | 추론 서버, 작업 대기열 | 작업 대기열 |

### 결정

A안을 씁니다. AI 모델은 AI 레포가 오프라인 배치로만 실행하며, 백엔드 서버에서는 실행하지 않습니다.

### 근거

- 사용자가 "책은 고정 목록이고, 관리자가 올리는 것은 AI가 만든 산출물 묶음"이라고 결정했습니다. 따라서 사용자의 요청을 처리하는 동안에는 모델이 필요한 순간이 없습니다.
- 장면의 벡터와 음악 구간의 벡터가 모두 미리 만들어져 있으므로, 책을 읽는 동안에는 벡터끼리 비교하는 검색만 하면 됩니다.
- GPU 서버를 항상 켜 두는 비용과 운영 부담은 테스트 유저 10명 규모의 MVP에 맞지 않습니다. (작성자 판단)

### 재검토 조건

일반 사용자가 자신의 책을 올릴 수 있게 하거나, 관리자가 원본 책만 올려도 자동으로 분석되게 하려는 시점에 B안을 검토합니다. 이때를 대비해 적재 과정을 "묶음을 읽고 검증하는 단계"와 "저장하는 단계"로 나누어 두었으므로, 앞 단계만 "모델 서비스를 호출하는 단계"로 바꾸면 됩니다.

## ADR-004: AI 레포와 백엔드의 연동 방식

### 맥락

AI 레포가 만든 분석 결과(문장, 장면, 캡션, 벡터, 곡 정보)를 백엔드의 데이터베이스에 넣어야 합니다. 그리고 팀원이 새 책을 추가할 수 있어야 하므로 관리자용 업로드 기능이 필요합니다. 한편 AI 레포는 아직 비어 있어서, 결과물의 형식이 정해져 있지 않습니다.

### 후보 비교

| 기준 | A. 산출물 묶음 파일 + 관리자 업로드 API | B. AI 레포가 데이터베이스에 직접 저장 | C. 백엔드가 AI 모델 API를 호출 |
| --- | --- | --- | --- |
| 두 레포 사이의 약속 | 파일 규격 하나 | 데이터베이스 구조 전체 | 모델 API의 규격 |
| 데이터베이스 구조를 바꿀 때 | 백엔드만 고치면 된다 | 두 레포를 함께 고쳐야 한다 | 백엔드만 고치면 된다 |
| 잘못된 데이터를 막는 곳 | 백엔드가 적재 전에 검증한다 | 막는 곳이 없다 | 백엔드가 검증한다 |
| AI팀이 독립적으로 일할 수 있는가 | 그렇다 | 데이터베이스 접속 권한과 구조를 알아야 한다 | 추론 서버를 운영해야 한다 |
| MVP에서 필요한 추가 작업 | 규격 문서와 검증 코드 | 적다 | 추론 서버와 작업 대기열 |

### 결정

A안을 씁니다. AI 레포가 정해진 규격의 산출물 묶음(zip 파일)을 만들고, 팀원이 관리자 API로 올리면 백엔드가 검증한 다음 적재합니다. 다만 용량이 큰 음원 파일은 오브젝트 저장소에 직접 올리고, 묶음에는 파일 이름만 담습니다.

### 근거

- 사용자가 "AI가 산출물 파일을 만들고 백엔드가 적재한다"와 "관리자가 올리는 것은 AI가 만든 산출물 묶음"을 선택했습니다.
- 두 팀의 약속이 파일 규격 하나로 줄어들기 때문에, 각 팀이 상대의 내부 구조를 몰라도 일할 수 있습니다. (작성자 판단)
- 백엔드가 적재하기 전에 검증하므로, 문장 번호가 어긋나거나 벡터의 차원이 틀린 데이터가 서비스에 들어오는 일을 막을 수 있습니다. (작성자 판단)
- 음원 파일은 합치면 수 GB 이상이 될 수 있어서 API 요청 하나로 올리기에 적합하지 않습니다. (작성자 판단)

### 재검토 조건

산출물 묶음의 규격은 아직 백엔드의 제안이며 AI팀과 합의해야 합니다. 합의 과정에서 규격이 바뀌면 [AI_CONTRACT.md](AI_CONTRACT.md)를 고치고, 연동 방식 자체가 바뀌면 이 기록을 새로 씁니다.

## ADR-005: 프론트엔드와의 API 연동 방식

### 맥락

프론트엔드는 Vite와 React로 만든 SPA이며, 자체 서버가 없습니다. 프론트엔드 레포의 문서에는 백엔드와 합의해야 할 항목 다섯 가지(API 기본 경로와 로컬 포트, 인증 방식, 에러 응답 형식, API 스펙 공유 방식, 헬스체크 엔드포인트)가 남아 있습니다. 또한 프론트엔드의 API 호출 코드는 이미 기본 경로 `/api`, 로컬 백엔드 포트 `8080`, 쿠키를 함께 보내는 설정으로 작성되어 있습니다.

그리고 한 가지 더 정해야 할 것이 있습니다. 페이지를 나누는 일은 화면 크기와 글꼴을 아는 프론트엔드만 할 수 있는데, 페이지를 넘겼을 때 "어느 장면의 음악을 틀 것인가"를 어느 쪽이 판단할지입니다.

### 후보 비교: API 방식

| 기준 | REST + OpenAPI | GraphQL |
| --- | --- | --- |
| 프론트엔드의 현재 코드와 맞는가 | 그대로 맞는다 | GraphQL 클라이언트를 새로 도입해야 한다 |
| 타입 공유 | OpenAPI 문서에서 TypeScript 타입을 자동 생성한다 | 스키마에서 자동 생성한다 |
| 화면 수가 적은 MVP에 맞는가 | 맞는다 | 과하다 |
| 백엔드 구현 부담 | 낮다 | 스키마와 리졸버를 따로 작성해야 한다 |

### 후보 비교: 장면을 고르는 곳

| 기준 | 백엔드가 고른다 | 프론트엔드가 고른다 |
| --- | --- | --- |
| 프론트엔드가 보내는 것 | 화면에 보이는 문장 번호의 범위 | 고른 장면의 번호 |
| 우선순위 규칙을 바꿀 때 | 백엔드만 배포하면 된다 | 프론트엔드를 다시 배포해야 한다 |
| 평가 기록 | 장면 선택부터 선곡까지 한곳에 남는다 | 장면 선택 과정이 기록에서 빠진다 |
| 요청 횟수 | 페이지를 넘길 때마다 한 번 | 장면이 바뀔 때만 한 번 |

### 결정

- REST 방식으로 연동하고, FastAPI가 자동으로 만드는 OpenAPI 문서를 API 스펙으로 공유합니다.
- 모든 경로에 `/api` 접두사를 붙이고, 로컬 개발 포트는 `8080`으로 합니다.
- 책 본문은 문장 번호가 붙은 구조화 JSON으로 내려줍니다.
- 장면 선택은 백엔드가 합니다. 프론트엔드는 화면에 보이는 문장 번호의 범위만 보냅니다.
- 에러 응답 형식과 엔드포인트의 상세는 [API.md](API.md)에서 정의합니다.

### 근거

- 사용자가 구조화 JSON과 백엔드의 장면 선택을 선택했습니다.
- 테스트용 책의 원본이 사진 스캔본과 AI가 합성한 글이어서 EPUB 파일이 아니라 일반 텍스트이며, 장면의 경계도 문장 단위로 정해집니다. 그러므로 문장 번호를 공통 단위로 쓰면 "지금 페이지에 어떤 장면이 있는가"를 정확히 계산할 수 있습니다.
- 경로와 포트를 프론트엔드의 현재 설정에 맞추면 프론트엔드가 고칠 것이 없습니다. (작성자 판단)
- 장면 선택 규칙이 백엔드에 있으면 규칙을 조정할 때 한 곳만 고치면 되고, 평가 기록도 한곳에 모입니다. (작성자 판단)

### 재검토 조건

- 페이지를 넘길 때마다 요청을 보내는 방식이 체감 속도를 떨어뜨린다면, 장면의 경계를 프론트엔드에 미리 내려주는 방식을 검토합니다.
- 프론트엔드가 EPUB 뷰어 라이브러리를 쓰기로 한다면 본문 형식을 다시 정합니다.

## ADR-006: 로그인과 접근 제한

### 맥락

"중단한 곡은 그 사용자에게 다시 틀지 않는다"는 요구사항과 평가 기록을 위해서는 사용자를 구별해야 합니다. 그리고 테스트용 책에는 저작권이 있는 소설(『노르웨이의 숲』의 일부 챕터)이 포함되므로, 아무나 본문을 볼 수 있어서는 안 됩니다. 또한 프론트엔드는 자체 서버가 없는 SPA이며, 이미 쿠키를 함께 보내도록 설정되어 있습니다.

### 후보 비교: 사용자를 구별하는 방법

| 기준 | Google 로그인 + 허용 목록 | 초대 코드 + 닉네임 | 이메일과 비밀번호 가입 | 기기별 익명 ID |
| --- | --- | --- | --- | --- |
| 접근을 제한할 수 있는가 | 그렇다 | 그렇다 | 따로 만들어야 한다 | 아니다 |
| 기기를 바꿔도 기록이 이어지는가 | 그렇다 | 코드를 다시 넣으면 이어진다 | 그렇다 | 아니다 |
| 앱 밖의 설문과 연결하기 쉬운가 | 이메일로 연결한다 | 닉네임으로 연결한다 | 이메일로 연결한다 | 어렵다 |
| 구현 부담 | Google 연동이 필요하다 | 가장 가볍다 | 비밀번호 저장과 재설정이 필요하다 | 가장 가볍다 |
| 실제 서비스와 비슷한 경험인가 | 그렇다 | 아니다 | 그렇다 | 아니다 |

### 후보 비교: 로그인 상태를 주고받는 방법

| 기준 | 쿠키 | 토큰을 요청 헤더에 담기 |
| --- | --- | --- |
| 프론트엔드가 할 일 | 없다 (현재 설정 그대로) | 토큰을 저장하고 갱신하는 코드를 작성해야 한다 |
| 스크립트가 값을 훔쳐볼 수 있는가 | 없다 (HttpOnly 쿠키) | 브라우저 저장소에 두면 가능하다 |
| 프론트엔드와 백엔드의 도메인이 달라도 되는가 | 같은 도메인이어야 안정적이다 | 달라도 된다 |
| 강제로 로그아웃시킬 수 있는가 | 서버에서 지우면 된다 | 별도 장치가 필요하다 |

### 결정

- Google 계정으로 로그인하게 하고, 허용 목록에 이메일이 있는 사람만 서비스를 쓸 수 있게 합니다.
- 관리자 권한도 같은 허용 목록에서 역할로 구분합니다.
- 로그인 상태는 서버의 데이터베이스에 저장하고, 브라우저에는 스크립트가 읽을 수 없는 쿠키(HttpOnly)로 식별자만 심습니다.
- Google 로그인의 전 과정은 백엔드가 처리합니다.

### 근거

- 사용자가 Google 로그인, 허용 이메일 목록, 쿠키 방식을 각각 선택했습니다.
- 프론트엔드에 서버가 없으므로 Google과 비밀값을 주고받는 일은 백엔드가 맡아야 합니다.
- 로그인 상태를 서버에 저장하면 허용 목록에서 뺀 사람의 접근을 곧바로 끊을 수 있어서, 저작권이 있는 본문을 보호하기에 유리합니다. (작성자 판단)
- 로그인 상태를 PostgreSQL에 저장하면 별도의 저장소를 추가로 운영하지 않아도 됩니다. (작성자 판단)

### 이 결정이 요구하는 조건

쿠키 방식이 Safari를 포함한 모든 브라우저에서 안정적으로 동작하려면, 배포 환경에서 프론트엔드와 백엔드가 같은 도메인 아래에 있어야 합니다. 주소 하나를 함께 쓰는 구성과 `app.diegesis.example`, `api.diegesis.example`처럼 하위 주소를 나누어 쓰는 구성이 모두 이 조건을 충족합니다. 두 구성의 차이와 필수 조건은 [INFRA.md](INFRA.md)에 적어 두었습니다.

### 재검토 조건

- 프론트엔드와 백엔드를 같은 도메인 아래에 둘 수 없게 되면 토큰 방식을 검토합니다.
- 네이티브 앱으로 배포하는 2차 마일스톤에서 인증 방식을 다시 검토합니다.

## ADR-007: 코드 구조

### 맥락

백엔드 코드를 어떤 기준으로 폴더를 나눌지 정해야 합니다. 벡터 검색 도구, 음원 저장소, 로그인 서비스는 나중에 바뀔 가능성이 있으며, 특히 음원 저장소는 인프라가 정해지지 않아 지금은 무엇을 쓸지 알 수 없습니다.

### 후보 비교

| 기준 | 기능별 모듈 + 포트와 어댑터 | 계층별 폴더 | 전면적인 헥사고날 구조 |
| --- | --- | --- | --- |
| 폴더를 나누는 기준 | 기능 (로그인, 책, 선곡 등) | 역할 (라우터, 서비스, 저장소 등) | 도메인, 유스케이스, 어댑터 |
| 기능 하나를 고칠 때 | 폴더 하나만 보면 된다 | 여러 폴더를 오가야 한다 | 여러 폴더를 오가야 한다 |
| 기술을 교체하기 쉬운가 | 포트로 감싼 지점은 쉽다 | 어렵다 | 가장 쉽다 |
| 파일 수와 간접 계층 | 적당하다 | 가장 적다 | 가장 많다 |
| 프론트엔드 구조와의 대응 | 기능 단위라 서로 대응된다 | 대응되지 않는다 | 대응되지 않는다 |

### 결정

코드는 기능별 모듈로 나눕니다. 그리고 들어오는 쪽(HTTP 요청)과 나가는 쪽(데이터베이스, 저장소, 로그인 서비스, 묶음 파일)은 포트로 추상화하고, 실제 구현은 어댑터에 둡니다. 구체적인 폴더 구조와 포트 목록은 [ARCHITECTURE.md](ARCHITECTURE.md#8-코드-구조)에 있습니다.

### 근거

- 사용자가 기능별 모듈을 선택하면서, 들어오는 쪽과 나가는 쪽의 포트를 추상화해 코드의 재사용성을 확보하라고 요구했습니다.
- 전면적인 헥사고날 구조는 6주 MVP에 비해 파일과 간접 계층이 많아지므로, 실제로 교체될 가능성이 있는 지점에만 포트를 둡니다. (작성자 판단)
- 포트가 있으면 테스트할 때 가짜 어댑터를 끼워 넣을 수 있어서, 데이터베이스나 Google 없이도 핵심 규칙을 검증할 수 있습니다. (작성자 판단)

### 재검토 조건

기능 모듈 사이의 의존이 복잡하게 얽히기 시작하면 모듈의 경계를 다시 나눕니다.

## ADR-008: 임베딩 모델과 선곡 방식의 추상화

### 맥락

팀은 MuQ-MuLan을 기본 임베딩 모델로 쓰되, LAION-CLAP을 비교 대상으로 함께 준비하기로 했습니다. MuQ-MuLan의 가중치는 비상업 라이선스여서 나중에 모델을 바꿔야 할 수도 있습니다. 또한 리서치 문서들은 "무음, 무작위 선곡, 우리 선곡"을 서로 비교하는 평가를 제안하고 있습니다.

### 후보 비교

| 기준 | 모델은 등록 데이터, 선곡 방식은 공통 인터페이스 | 모델마다 테이블과 코드를 따로 둠 | 서버 설정값 하나로 고정 |
| --- | --- | --- | --- |
| 새 모델을 추가할 때 | 묶음을 올리면 된다 | 테이블과 코드를 추가해야 한다 | 가능하지만 한 번에 하나만 쓸 수 있다 |
| 여러 모델을 동시에 비교할 수 있는가 | 그렇다 | 그렇다 | 아니다 |
| 사용자마다 다른 방식을 쓸 수 있는가 | 그렇다 | 따로 만들어야 한다 | 아니다 |
| 구현 부담 | 보통이다 | 모델이 늘수록 커진다 | 가장 낮다 |

### 결정

- 임베딩 모델은 코드가 아니라 데이터베이스에 등록하는 데이터로 다룹니다. 벡터는 "어떤 모델이 만들었는지"와 함께 저장합니다. 그리고 처음 보는 모델은 산출물 묶음을 적재할 때 자동으로 등록합니다.
- 선곡 방식은 공통 인터페이스(`RecommendationStrategy`)의 구현체로 만듭니다. MVP에는 임베딩, 랜덤, 무음 세 가지를 둡니다.
- 사용자가 설정 화면에서 선곡 방식과 임베딩 모델을 직접 바꿀 수 있게 합니다.

### 근거

- 사용자가 선곡 방식과 임베딩 모델의 비교를 사용자 본인이 프론트엔드에서 직접 할 수 있게 하자고 제안했고, 임베딩 모델은 쉽게 추가할 수 있도록 추상화하라고 요구했습니다.
- 백엔드는 모델을 실행하지 않고 벡터만 저장하므로(ADR-003), 모델을 추가하는 일을 데이터 등록만으로 끝낼 수 있습니다.
- 직접 언급 장면의 지정 곡은 임베딩 방식에만 적용합니다. 랜덤과 무음은 비교의 기준선이므로 섞이지 않게 합니다. (작성자 판단)

### 재검토 조건

벡터의 차원이 매우 큰 모델(pgvector의 인덱스가 지원하는 한도를 넘는 모델)을 추가해야 할 때 저장 방식을 다시 검토합니다.

## ADR-009: 데이터베이스 접근 도구와 개발 도구

### 맥락

ADR-001과 ADR-002에 따라 Python에서 PostgreSQL과 pgvector를 다뤄야 합니다. 그리고 데이터베이스의 구조가 바뀔 때마다 그 이력을 관리해야 하며, 혼자 개발하더라도 코드 품질을 자동으로 점검할 도구가 필요합니다.

### 후보 비교: 데이터베이스 접근 도구

| 기준 | SQLAlchemy + Alembic | SQLModel | Tortoise ORM |
| --- | --- | --- | --- |
| pgvector와 함께 쓸 수 있는가 | pgvector의 Python 패키지가 지원한다 | SQLAlchemy를 통해 지원한다 | 구현 시 확인이 필요하다 |
| 복잡한 쿼리를 작성하기 쉬운가 | 쉽다 | SQLAlchemy로 내려가야 한다 | 어렵다 |
| 구조 변경 이력 관리 | Alembic이 표준이다 | Alembic을 쓴다 | 자체 도구를 쓴다 |
| 자료와 사례가 많은가 | 가장 많다 | 보통이다 | 적다 |

### 결정

| 영역 | 선택 |
| --- | --- |
| 데이터베이스 접근 | SQLAlchemy (비동기 방식, asyncpg 드라이버) |
| 구조 변경 이력 관리 | Alembic |
| 설정값 관리 | pydantic-settings |
| Google 로그인 연동 | Authlib |
| 패키지와 가상환경 관리 | uv |
| 코드 형식과 린트 | ruff |
| 타입 검사 | pyright |
| 테스트 | pytest |
| GitHub Actions의 workflow 검사 | actionlint |

각 도구의 버전은 프로젝트를 세팅하는 시점에 최신 안정 버전을 확인해서 고정합니다.

### 근거

이 결정의 근거는 모두 작성자의 판단입니다.

- 선곡 검색은 벡터 거리 계산, 조건, 중복 제거가 함께 들어가는 쿼리이므로, 쿼리를 세밀하게 작성할 수 있는 SQLAlchemy가 적합합니다.
- SQLModel은 테이블 정의와 응답 형식을 한 클래스로 합쳐 주지만, 이 프로젝트에서는 둘의 모양이 다른 경우가 많아서 이점이 작습니다.
- uv는 패키지 설치와 버전 고정을 도구 하나로 처리하며, ruff는 형식 정리와 린트를 한 도구로 처리합니다.
- 설정값을 pydantic-settings의 클래스 하나로 모으면, 사용자가 요구한 "설정값을 `.env`에서 쉽게 바꿀 수 있는 구조"가 됩니다.
- actionlint는 Epic 0에서 CI의 workflow를 만들며 더했습니다. workflow 파일의 문법 오류와 흔한 실수를 GitHub에 올리기 전에 테스트로 잡기 위해서입니다. 개발 의존성(`actionlint-py`)으로 설치하므로 개발자의 컴퓨터와 CI가 같은 버전을 씁니다.

### 재검토 조건

특정 도구가 프로젝트의 진행을 막는 문제를 일으킬 때 그 도구만 다시 검토합니다.

## ADR-010: 배포 방식

### 맥락

테스트 유저가 접속할 수 있도록 서비스를 배포해야 합니다. 그러나 어디에 배포할지는 프론트엔드와 함께 정해야 하는 부분이어서 아직 결정하지 않았습니다. 이 프로젝트는 포트폴리오용이며 창업 계획은 없으므로, 비용을 거의 들이지 않는 것이 중요합니다.

### 결정

- 백엔드는 Docker 컨테이너로 배포합니다.
- 로컬 개발 환경은 Docker Compose로 API 서버와 PostgreSQL을 함께 띄웁니다.
- 코드가 `main` 브랜치에 합쳐지면 자동으로 컨테이너 이미지를 만들어 배포하며, 만든 이미지는 Docker Hub에 저장합니다. 이 가운데 이미지를 만들어 Docker Hub에 올리는 단계까지는 Epic 0에서 만들었고, 배포 환경에 새 이미지를 반영하는 단계는 배포할 곳이 정해진 뒤에 만듭니다. 자세한 흐름은 [INFRA.md](INFRA.md#37-자동-배포)의 3.7절에 있습니다.
- 음원 파일은 비공개 오브젝트 저장소에 두고, 백엔드가 발급한 서명된 주소로만 받을 수 있게 합니다.
- 호스팅 서비스, 데이터베이스 호스팅, 음원 저장소 같은 구체적인 인프라는 정하지 않고, 결정해야 할 항목과 고려사항을 [INFRA.md](INFRA.md)에 정리합니다.

### 근거

- 사용자가 Docker 컨테이너로 배포한다는 것만 먼저 결정하고, 나머지는 프론트엔드와 상의한 뒤 정하겠다고 했습니다. 그리고 GCP 무료 계정을 옮겨 가며 쓰는 방식도 괜찮아 보인다고 했습니다.
- 컨테이너로 만들어 두면 어느 호스팅 서비스를 고르더라도 그대로 올릴 수 있고, 무료 계정을 옮길 때에도 다시 만들 것이 없습니다. (작성자 판단)
- 사용자가 `main` 브랜치에 합쳐진 코드를 자동으로 배포하고 이미지를 Docker Hub에 저장하기로 정했습니다. Docker Hub는 특정 클라우드에 속하지 않으므로, 어느 호스팅 서비스를 고르더라도 같은 이미지를 가져다 쓸 수 있습니다. (뒤 문장은 작성자 판단)
- 사용자가 음원 파일은 반드시 백엔드가 발급한 서명된 주소로만 접근하게 해야 한다고 정했습니다. 이 규칙은 음원의 라이선스나 AI팀과의 협의와 관계없이 적용합니다.
- 음원 저장소는 `ObjectStorage` 포트 뒤에 두므로(ADR-007), 저장소가 정해지지 않은 지금도 개발을 진행할 수 있습니다. (작성자 판단)

### 재검토 조건

인프라가 정해지면 이 기록의 상태를 "확정"으로 바꾸고, 선택한 인프라와 그 이유를 새 기록으로 추가합니다.

## ADR-011: 통합 테스트용 데이터베이스

### 맥락

[DEVELOPMENT.md](DEVELOPMENT.md)의 테스트 규칙은 벡터 검색처럼 PostgreSQL과 pgvector의 동작에 기대는 코드를 가짜로 대신하지 않고 실제 데이터베이스에서 검증하게 합니다. 그리고 모든 검사는 `scripts/check.sh` 하나로 돌리며, 에이전트 세션의 종료 검사, step의 완료 조건, CI가 모두 이 스크립트를 부릅니다. 그래서 통합 테스트용 데이터베이스를 띄우는 방법은 이 모든 곳에서 똑같이 동작해야 합니다. 또한 harness는 phase마다 worktree를 따로 만들기 때문에, 여러 worktree에서 검사가 동시에 돌 수 있습니다.

### 후보 비교

| 기준 | A. testcontainers | B. compose의 데이터베이스에 접속 | C. 통합 테스트는 CI에서만 |
| --- | --- | --- | --- |
| 방식 | 테스트가 시작될 때 데이터베이스 컨테이너를 무작위 포트로 띄우고, 끝나면 지운다 | 개발자가 먼저 띄워 둔 compose의 데이터베이스에 테스트가 접속한다 | `scripts/check.sh`에서는 통합 테스트를 빼고 CI에서만 돌린다 |
| 개발용 데이터 | 건드리지 않는다 | 테스트가 지우거나 바꿀 수 있다 | 건드리지 않는다 |
| worktree 여러 개가 동시에 돌 때 | 서로 다른 컨테이너를 쓰므로 부딪히지 않는다 | 포트와 데이터가 부딪힌다 | 부딪히지 않는다 |
| 로컬과 CI의 명령 | `scripts/check.sh` 하나로 같다 | CI에 데이터베이스를 띄우는 설정을 따로 둬야 한다 | 서로 다르다 |
| 무인 step이 통합 테스트를 돌리는가 | 돌린다 | 데이터베이스가 떠 있을 때만 돌린다 | 돌리지 않는다 |
| 필요한 것 | 검사를 돌리는 곳마다 Docker | 검사 전에 데이터베이스를 띄우는 절차 | 없다 |

### 결정

A안, 곧 testcontainers를 씁니다. 컨테이너의 이미지는 `compose.yaml`의 데이터베이스 서비스와 같은 것을 쓰며, 이미지의 이름은 `compose.yaml`에서 읽습니다. 그리고 Docker에 닿을 수 없으면 통합 테스트는 건너뛰지 않고 실패합니다.

### 근거

- 사용자가 A안을 선택했습니다.
- 테스트가 개발용 데이터베이스에 접속하지 않으므로, 마이그레이션을 되돌리는 테스트가 개발용 데이터를 지울 수 없습니다. (작성자 판단)
- 로컬, 무인 step, CI가 모두 같은 명령으로 같은 검사를 돌리므로 기준이 갈라지지 않습니다. (작성자 판단)
- Docker가 없을 때 통합 테스트를 건너뛰게 하면, 통합 테스트를 하나도 돌리지 않았는데도 검사가 통과한 것처럼 보입니다. 이것은 검사가 꺼진 것을 숨기므로 실패로 다룹니다. (작성자 판단)

### 재검토 조건

- Docker를 쓸 수 없는 환경에서 검사를 돌려야 할 때 다시 검토합니다.
- 컨테이너를 띄우는 시간 때문에 검사가 지나치게 느려질 때 다시 검토합니다.

## ADR-012: 책 본문의 저장 방식

### 맥락

책 본문은 문장 번호가 붙은 구조화된 JSON으로 프론트엔드에 내려줍니다(ADR-005). 이때 백엔드는 언제나 챕터 하나를 통째로 읽어서 넘기며, 문장의 내용으로 검색하거나 문장 하나만 고치는 일은 없습니다. 그리고 장면을 고르거나 읽은 위치를 저장할 때에도 문장의 내용이 아니라 문장 번호의 범위만 씁니다.

처음 설계(2026-11-22)에서는 문장마다 한 행을 두는 `sentences` 테이블에 본문을 저장했습니다. 그런데 사용자가 문장을 한 행씩 저장하는 방식이 비효율적이라고 지적하면서 본문을 오브젝트 저장소에 두는 안을 제안해서, 2026-11-24에 저장 방식을 다시 검토했습니다.

### 후보 비교

| 기준 | A. 챕터마다 JSON 하나를 PostgreSQL에 저장 | B. 챕터마다 JSON 파일을 오브젝트 저장소에 저장 | C. 문장마다 한 행 (처음 설계) |
| --- | --- | --- | --- |
| 저장하는 단위 | 챕터 | 챕터 | 문장 |
| 챕터 하나를 읽을 때 | 행 하나를 읽는다 | 데이터베이스에서 파일 위치를 찾은 뒤 저장소에서 파일을 읽는다 | 수백 행을 읽어 문단별로 다시 묶는다 |
| 적재를 전부 성공시키거나 전부 실패시키는 일 | 트랜잭션 하나로 보장된다 | 저장소와 데이터베이스를 따로 맞춰야 하고, 적재가 실패하면 쓰이지 않는 파일이 남는다 | 트랜잭션 하나로 보장된다 |
| 저작권 있는 본문의 보호 | 로그인을 확인하는 API로만 나간다 | 백엔드가 파일을 읽어 전달하면 A와 같다. 서명된 주소로 넘기면 주소가 만료되기 전에는 누구나 열 수 있다 | A와 같다 |
| 테스트에 필요한 것 | 데이터베이스 | 데이터베이스와 저장소 어댑터 | 데이터베이스 |
| 잘 맞는 상황 | 글뿐인 책이 몇 권에서 수십 권일 때 | 본문에 이미지가 들어가거나 책이 수백 권 이상일 때 | 문장 단위로 검색하거나 고쳐야 할 때 |

### 결정

A안을 씁니다. 챕터 하나의 본문을 문단과 문장으로 묶은 JSON 하나로 만들어 `chapters` 테이블에 저장합니다. 문장 번호는 그 JSON 안에 들어가며, 테이블에는 챕터의 첫 문장 번호와 마지막 문장 번호만 컬럼으로 둡니다. 따라서 `sentences` 테이블은 두지 않습니다. 한편 산출물 묶음의 `sentences.jsonl` 형식은 그대로 두고, 백엔드가 적재할 때 문장들을 챕터별로 묶습니다.

### 근거

- 사용자가 A안을 선택했습니다.
- 저장하는 단위를 실제로 읽는 단위인 챕터에 맞춥니다. 처음 설계의 문제는 성능이 아니었습니다. 소설 한 권은 많아야 1만 문장 남짓이어서, 문장마다 행을 두더라도 PostgreSQL에게는 작은 양이기 때문입니다. (작성자 판단)
- 적재를 전부 성공시키거나 전부 실패시키는 보장을 트랜잭션 하나로 유지할 수 있습니다. (작성자 판단)
- 본문은 책 한 권에 몇 MB뿐이어서, 데이터베이스 밖으로 빼더라도 MVP에서 얻는 이득이 작습니다. (작성자 판단)
- 본문을 읽고 쓰는 코드는 `books` 모듈의 `repository`에만 있으므로, 나중에 B안으로 옮기더라도 바꿀 곳이 거기에 그칩니다. (작성자 판단)
- 이 결정의 결과로 챕터를 문장 번호의 범위로 다루게 됩니다. 그래서 적재할 때 한 챕터의 문장 번호가 끊기지 않고 이어지는지를 검사합니다([AI_CONTRACT.md](AI_CONTRACT.md#5-백엔드가-검증하는-것) 5절).

### 재검토 조건

- 본문에 이미지가 들어가거나 EPUB 파일을 다뤄야 할 때 B안을 검토합니다. 2차 마일스톤에서 원본 책을 올리는 기능을 만들 때가 여기에 해당합니다.
- 책이 수백 권으로 늘어서 데이터베이스의 용량이나 백업이 부담될 때 B안을 검토합니다.
- 문장 단위로 검색하거나 고쳐야 하는 기능이 생길 때 다시 검토합니다.

## ADR-013: 다시 올린 산출물의 보존 방식

### 맥락

선곡 기록은 그때의 장면(`scene_id`), 곡(`track_id`), 구간(`segment_id`)을 가리키며, 후보 목록에도 구간 ID가 들어갑니다. 그리고 MVP의 목적이 평가 자료를 모으는 것이므로, 같은 책이나 곡을 다시 올리더라도 이 기록이 사라지거나 다른 대상을 가리켜서는 안 됩니다. 한편 중단 기록과 좋아요는 곡에 달립니다.

처음 설계(2026-11-22)에서는 책은 새 버전으로 쌓고, 곡은 곡 ID를 기준으로 갱신하며 지우지 않기로 했습니다(작성자 판단). 그러나 곡의 구간을 새로 나눴을 때 옛 구간을 어떻게 처리할지는 정하지 않았습니다. 2026-11-24에 사용자가 "책처럼 곡도 구간을 새로 나눌 수 있다"고 지적해서, 이 빈틈을 다시 검토했습니다. 또한 같은 날 사용자가 본문은 그대로이고 장면만 바뀐 경우에도 새 버전이 생기는지 물어서, 그 동작도 함께 정했습니다.

### 후보 비교: 곡의 구간을 새로 나눴을 때

| 기준 | A. 옛 구간을 비활성화 | B. 음악도 버전 테이블을 둠 | C. 선곡 기록에 구간의 위치를 복사 |
| --- | --- | --- | --- |
| 과거 기록이 가리키는 구간 | 남는다 | 남는다 | 기록에 시작과 끝의 위치만 남는다 |
| 후보 목록의 구간 ID | 의미가 유지된다 | 의미가 유지된다 | 사라진 구간을 가리킨다 |
| 늘어나는 것 | 컬럼 하나와 검증 규칙 하나 | 버전 테이블, 그리고 곡마다 지금 버전을 관리하는 규칙 | 선곡 기록의 컬럼 두 개 |
| 같은 구간 ID를 다른 위치에 다시 쓸 때 | 적재를 실패시켜 막는다 | 버전으로 구분된다 | 막지 못한다 |

### 결정

- **책:** `book.id`가 같은 묶음을 다시 올리면 무엇이 바뀌었든 새 버전으로 쌓습니다. 본문은 그대로이고 장면만 바뀌었더라도 마찬가지입니다. 독자에게는 최신 버전만 보입니다.
- **곡:** 곡 ID를 기준으로 처음 보는 곡은 추가하고 이미 있는 곡은 갱신합니다. 그리고 곡은 지우지 않습니다.
- **구간:** A안을 씁니다. 곡의 구간을 새로 나눈 묶음을 올리면, 그 곡의 옛 구간 가운데 새 묶음에 없는 것은 비활성화하여 검색에서만 뺍니다. 그리고 이미 있는 구간 ID에 다른 곡이나 다른 시간 범위를 담아 올리면 적재를 실패시킵니다.

### 근거

- 사용자가 구간의 처리 방법으로 A안을 선택했습니다.
- 책은 본문과 장면이 한 묶음으로 함께 바뀌어야 하므로 버전으로 묶습니다. 반면에 음악은 음원 파일이 그대로이고 나누는 방식만 바뀌므로, "기록이 가리키는 행은 지우지 않는다"는 원칙만으로 B안과 같은 보장을 얻을 수 있습니다. (작성자 판단)
- 곡 ID가 바뀌지 않으므로, 구간을 새로 나누더라도 그 곡의 중단 기록과 좋아요는 그대로 이어집니다.
- 장면만 바뀌어도 본문을 다시 저장하므로 본문이 버전 수만큼 중복됩니다. 그러나 버전마다 몇 MB 수준이므로 MVP에서는 받아들입니다. 이를 피하려고 본문의 버전과 장면의 버전을 나누면, 어느 장면이 어느 본문 위에 놓였는지를 관리하는 테이블과 규칙이 늘어납니다. (작성자 판단)

### 재검토 조건

- 책을 자주 다시 올려서 본문의 중복이 부담될 때, 본문의 버전과 장면의 버전을 나누는 방안을 검토합니다.
- 같은 곡 ID로 음원 파일 자체를 바꿔야 하는 일이 생길 때 다시 검토합니다. 옛 구간의 시간 범위는 바꾸기 전의 음원 파일을 기준으로 하기 때문입니다.

## ADR-014: CI 검사와 컨테이너 이미지

### 맥락

코드가 `main` 브랜치에 합쳐지면 자동으로 컨테이너 이미지를 만들어 배포하기로 했습니다(ADR-010). 그리고 `main`에는 PR로만 합치므로, PR이 배포 앞의 관문입니다([DECISIONS.md](DECISIONS.md)의 D-28). 그래서 CI가 언제 검사를 돌리고 언제 이미지를 올릴지, 그리고 이미지를 어디에 어떤 형태로 둘지를 정해야 했습니다.

이 결정은 Epic 0을 설계하면서(2026-11-23) 정했고, 처음에는 DECISIONS.md의 D-36과 D-37에 기록했습니다. 그 뒤 기술적 결정은 이 문서에 둔다는 기준에 따라 2026-11-24에 이 기록으로 옮겼습니다.

### 결정

- 검사(`scripts/check.sh`)와 compose 스모크는 `main`을 향한 PR과 `main`의 push에서 돌립니다. 그리고 컨테이너 이미지를 Docker Hub에 올리는 일은 `main`의 push에서 검사와 스모크가 모두 통과한 뒤에만 합니다.
- Docker Hub의 저장소는 공개로 두고, `linux/amd64` 이미지만 올립니다.
- 팀원은 Docker Hub의 이미지를 받지 않고, 레포에서 compose로 빌드합니다.
- 계정과 저장소의 이름, 토큰은 코드에 적지 않고 GitHub의 secrets와 variables에 둡니다.

### 근거

- 사용자가 Epic 0을 설계하면서 정했습니다.
- 병합한 뒤에만 검사하면, 검사가 실패하더라도 그 코드는 이미 `main`에 들어간 뒤입니다. 그러므로 PR에서도 검사를 돌려야 PR이 배포 앞의 관문 역할을 합니다.
- Docker Hub의 이미지를 받는 곳은 배포 환경뿐이며, 로컬에서는 compose가 각 컴퓨터의 CPU 아키텍처로 직접 빌드합니다. 그래서 `linux/amd64` 이미지만 올립니다.
- 레포가 공개이고 이미지에는 비밀값을 넣지 않으므로, 저장소를 공개로 둡니다.

### 재검토 조건

- 배포 환경의 서버가 `arm64`라면 그 CPU 아키텍처의 이미지도 올리도록 바꿉니다.
- 레포를 비공개로 바꾸거나, 이미지에 공개할 수 없는 것이 들어가야 할 때 저장소의 공개 여부를 다시 검토합니다. (작성자 판단)

## ADR-015: 로컬 실행 구성과 헬스체크

### 맥락

Epic 0에서는 로컬의 compose로 데이터베이스, 마이그레이션, 서버를 함께 띄우고, CI의 compose 스모크로 그 구성이 실제로 뜨는지를 확인하게 했습니다(ADR-010, ADR-014). 이때 헬스체크가 무엇까지 확인할지, 마이그레이션을 언제 실행할지, 그리고 컨테이너 이미지를 어떤 명령으로 빌드할지를 정해야 했습니다.

이 결정은 Epic 0을 설계하면서(2026-11-23) 정했고, 처음에는 DECISIONS.md의 D-39, D-40, D-41에 기록했습니다. 그 뒤 기술적 결정은 이 문서에 둔다는 기준에 따라 2026-11-24에 이 기록으로 옮겼습니다.

### 결정

- `GET /api/health`는 서버 프로세스가 살아 있는지만 확인하고, 데이터베이스는 확인하지 않습니다. 서버와 데이터베이스의 연결은 compose 스모크가 서버 이미지로 마이그레이션을 실행해서 확인합니다.
- 로컬의 compose에서는 마이그레이션을 서버와 같은 이미지로 띄우는 일회성 서비스(`migrate`)로 실행하고, 서버는 그 서비스가 성공한 뒤에 띄웁니다.
- 로컬과 compose 스모크에서 컨테이너 이미지는 compose로 빌드하며, `docker build`를 직접 쓰지 않습니다.

### 근거

- 사용자가 Epic 0을 설계하면서 세 가지를 모두 정했습니다.
- 컨테이너가 모두 떠 있고 헬스체크가 응답하더라도, 서버가 데이터베이스에 연결된다는 보장은 없습니다. 반면에 서버 이미지로 실행한 마이그레이션이 성공하면, 같은 이미지와 같은 설정으로 데이터베이스에 연결된다는 것이 확인됩니다.
- 서버가 시작할 때마다 마이그레이션을 실행하면, 배포 환경에서 서버가 여러 개 뜰 때 마이그레이션이 동시에 실행될 수 있습니다.
- `docker build`의 결과가 로컬 이미지 저장소에 실리는지는 각자의 Docker builder 설정에 따라 다르지만, compose는 builder 설정과 관계없이 이미지를 싣습니다. 백엔드 담당자의 Mac에서 `docker build`, `docker build --load`, `docker compose build`를 모두 확인한 뒤 compose 하나로 정했습니다.

### 재검토 조건

- 배포 환경이 준비 상태 확인을 요구하면, 데이터베이스까지 확인하는 엔드포인트를 따로 만듭니다.
- 배포할 곳이 정해지면, 배포 환경에서 마이그레이션을 실행하는 시점을 정합니다. 지금은 로컬에서 실행하는 방법만 정했습니다.

## ADR-016: 책 묶음에서 챕터와 문단을 나타내는 방식

### 맥락

AI 레포가 장면을 찾는 과정에서는 문장을 나누고, 문장 몇 개씩의 구간을 비교해 트리거 문장을 찾고, 장면마다 캡션과 벡터를 만듭니다. 이 과정은 처음부터 끝까지 문장 인덱스만 쓰며, 챕터나 문단은 쓰지 않습니다. 그러나 백엔드는 원문을 따로 받지 않으므로, 독자에게 보여 줄 본문의 챕터와 문단 구분도 책 묶음으로만 받을 수 있습니다. 그리고 리더에는 두 구분이 모두 필요합니다. 문단 구분이 없으면 본문이 한 덩어리로 보이고 대사가 줄마다 떨어지지 않으며, 챕터는 제목과 목차, 그리고 본문을 요청하는 단위가 되기 때문입니다.

처음 규격(2026-11-22)에서는 `sentences.jsonl`의 문장마다 `chapter_no`와 `paragraph_no`를 붙이고, `manifest.json`의 `chapters`에 챕터의 번호와 제목을 따로 적었습니다. 2026-11-24에 사용자가 텍스트를 준비할 때 챕터와 문단을 굳이 나눠야 하는지 검토를 요청해서, 이 표현 방식을 다시 검토했습니다. 검토에서 드러난 문제는 다음 두 가지입니다.

- 챕터 정보가 `chapters` 목록과 문장마다의 `chapter_no` 두 곳에 있어서, 둘이 맞는지 확인하는 검증 규칙이 세 개 필요했습니다. 그런데 백엔드는 적재할 때 이 정보를 결국 챕터의 첫 문장부터 마지막 문장까지의 범위로 바꿔서 씁니다([ADR-012](#adr-012-책-본문의-저장-방식)).
- `paragraph_no`는 장면 선택이나 위치 계산 어디에서도 쓰이지 않았으며, 담긴 정보는 "이 문장에서 새 문단이 시작되는가"뿐이었습니다. 그런데도 챕터마다 0부터 다시 센다는 규칙 때문에 챕터의 경계와 맞춰 보는 검사가 필요했습니다.

### 후보 비교

| 기준 | A. 문장마다 소속 번호를 붙인다 (처음 규격) | B. 챕터는 첫 문장으로, 문단은 시작 여부로 나타낸다 | C. 챕터와 문단을 묶음에서 뺀다 |
| --- | --- | --- | --- |
| 챕터를 나타내는 것 | `chapters` 목록, 그리고 문장마다의 `chapter_no` | `chapters` 목록에 적은 챕터마다의 첫 문장 인덱스 | 없다 |
| 문단을 나타내는 것 | 챕터마다 0부터 세는 `paragraph_no` | 문장마다의 `is_paragraph_start` | 없다 |
| 챕터에 관한 검증 | 목록에 있는 번호인지, 챕터마다 문장이 있는지, 끊기지 않고 순서대로인지 | 첫 문장 인덱스가 0에서 시작해 커지는지. 끊김과 뒤바뀜은 구조상 생기지 않는다 | 없다 |
| 문단에 관한 검증 | 챕터마다 0부터 시작하고 줄어들지 않는지 | 필수 필드와 타입의 검사뿐이다 | 없다 |
| 백엔드가 적재할 때 할 일 | 문장의 소속 번호를 챕터의 범위로 바꾼다 | 받은 첫 문장 인덱스를 그대로 범위로 쓴다 | 책 전체를 한 덩어리로 저장한다 |
| 리더에서 | 문단과 챕터를 보여 줄 수 있다 | A와 같다 | 문단도 챕터의 제목도 보여 줄 수 없다 |

### 결정

B안을 씁니다.

- `manifest.json`의 `book.chapters`에 챕터마다 `chapter_no`, `title`, `first_sentence_idx`를 적습니다. 챕터의 마지막 문장은 다음 챕터의 첫 문장 바로 앞 문장이며, 마지막 챕터는 책의 마지막 문장까지 이어집니다.
- `chapter_no`는 묶음 안에서 1부터 1씩 셉니다. 원본 책의 일부 챕터만 담더라도 마찬가지이며, 원본의 장 이름은 `title`에 적습니다.
- `sentences.jsonl`에는 `chapter_no`와 `paragraph_no`를 두지 않고, 그 대신 문단의 시작을 나타내는 `is_paragraph_start`를 둡니다. 챕터의 첫 문장은 이 값과 관계없이 문단의 시작으로 봅니다.
- 프론트엔드에 내려주는 챕터 본문의 모양, 곧 문단의 목록이고 각 문단이 문장의 목록인 모양은 그대로 둡니다. 백엔드가 적재할 때 이 모양으로 묶어서 저장합니다.
- 위치 알림 요청과 `reading_progress`의 `chapter_no`는 그대로 둡니다.
- 이 결정은 ADR-012 가운데 "산출물 묶음의 `sentences.jsonl` 형식은 그대로 둔다"는 부분을 대체합니다. 본문을 챕터마다 JSON 하나로 저장한다는 ADR-012의 결정은 그대로입니다.

### 근거

- 사용자가 B안을 선택했습니다. 그리고 위치 알림의 `chapter_no`도 문장 인덱스만으로 알아낼 수 있어서 함께 빼는 안을 검토했지만, 사용자가 위치 쪽은 바꾸지 않기로 했습니다.
- AI 레포가 넘기는 정보의 양은 A안과 같으며, 같은 정보가 두 곳에 있어서 생기던 검증만 사라집니다. (작성자 판단)
- 백엔드가 챕터를 다루는 방식인 문장 인덱스의 범위를 묶음이 그대로 담습니다. (작성자 판단)
- AI 레포는 원문의 줄바꿈으로 문단을 먼저 나눈 다음 그 안에서 문장을 나누면 되므로, 문단의 시작 여부를 적는 데 드는 수고가 거의 없습니다. (작성자 판단)
- 이 규격은 아직 AI팀과 합의하기 전의 초안이어서, 지금 바꾸는 비용이 가장 작습니다. (작성자 판단)

### 재검토 조건

- 챕터 안의 절이나 소제목처럼 한 단계 더 깊은 구조를 보여 줘야 할 때 다시 검토합니다.
- EPUB 파일을 다뤄야 할 때 다시 검토합니다. EPUB 파일에는 챕터와 문단의 구조가 이미 들어 있기 때문입니다.

## ADR-017: 번호와 인덱스의 구분

### 맥락

문서와 필드 이름에서 "번호"라는 말이 1부터 세는 값과 0부터 세는 값에 함께 쓰였습니다. 예를 들어 챕터 번호(`chapter_no`)는 1부터 셌지만, 문장 번호와 문단 번호(`paragraph_no`)는 0부터 셌습니다. 그리고 문장의 위치를 가리키는 필드는 `start_sentence`나 `first_sentence`처럼 어느 쪽인지를 알려 주는 표시가 없었습니다. 책의 버전(`version`), 규격의 버전(`schema_version`), 적재 오류가 난 줄(`line`)도 몇부터 세는지가 이름에도 설명에도 없었습니다. 이름만 보고 어느 쪽인지 알 수 없으면, 범위의 경계를 계산할 때 하나씩 어긋나는 실수가 생기기 쉽습니다. 2026-11-24에 ADR-016을 정하면서 사용자가 둘을 이름으로 구분하고, 이 규칙을 설계 문서 전체에 일관되게 적용하도록 요청했습니다.

### 결정

- 이 규칙은 API, 산출물 묶음, 데이터베이스의 필드에 담는 순번에 적용합니다.
- 1부터 세는 순번은 "번호"라고 부르고, 필드 이름 끝에 `_no`를 붙입니다. 예를 들면 `chapter_no`, `version_no`, `schema_version_no`, `line_no`입니다.
- 0부터 세는 순번은 "인덱스"라고 부르고, 필드 이름 끝에 `_idx`를 붙입니다. 예를 들면 `first_sentence_idx`, `last_sentence_idx`, `start_sentence_idx`, `end_sentence_idx`, `paragraph_idx`입니다. 다만 목록의 항목이 자기 자신의 인덱스를 담을 때에는 `idx`라고만 씁니다.
- 그래서 지금까지 "문장 번호"라고 부르던 것을 "문장 인덱스"라고 부릅니다. 이 결정보다 앞선 기록(ADR-004, ADR-005, ADR-012)에 나오는 "문장 번호"는 문장 인덱스를 뜻합니다.
- 위치 알림 요청과 읽은 위치의 필드도 같은 규칙을 따르며, 필드의 이름만 바뀌고 뜻은 그대로입니다.

### 근거

- 사용자가 요청했습니다.
- 밀리초 단위의 값에 `_ms`를 붙이는 기존 규칙([API.md 2.1절](API.md#21-요청과-응답의-형식))처럼, 값을 읽는 방법을 이름에 드러냅니다. (작성자 판단)

### 재검토 조건

- 프론트엔드나 AI 레포의 코드가 이미 다른 이름 규칙을 쓰고 있어서 그쪽에 맞춰야 할 때 다시 검토합니다.

## ADR-018: 평가 라벨을 받는 방식

### 맥락

AI팀이 평가 방식을 정했습니다. 선곡은 지금처럼 장면의 캡션을 임베딩해서 가장 가까운 음악 구간을 찾습니다. 그리고 고른 곡이 장면에 맞았는지는 장면과 구간에 각각 붙인 라벨을 비교해서 채점합니다. 주 지표는 장면과 구간의 V-A 거리이고, 보조 지표는 태그가 일치하는 비율과 GEMS 차원이 일치하는 비율입니다. 그래서 장면과 구간은 임베딩, V-A, 태그, GEMS 차원이라는 같은 네 속성을 가져야 합니다.

그런데 지금까지의 규격에는 장면과 구간에 임베딩만 있었습니다. 태그는 곡 단위(`tracks.tags`)에만 있었고, V-A와 GEMS 차원은 어디에도 없었습니다. 2026-11-24에 사용자가 이 빈 곳을 가장 단순한 방법으로 채우도록 요청했습니다.

### 후보 비교

| 기준 | A. 장면과 구간의 줄에 필드로 담음 | B. 라벨 파일을 따로 둠 | C. 라벨 테이블을 따로 두고 태그와 GEMS를 행으로 나눔 |
| --- | --- | --- | --- |
| 묶음에 늘어나는 것 | 필드 네 개 | 파일 두 개와 ID를 잇는 검증 | 필드 네 개 |
| 데이터베이스에 늘어나는 것 | 컬럼 네 개씩 | 컬럼 네 개씩 | 테이블 서너 개와 조인 |
| 라벨만 다시 올릴 수 있는가 | 묶음 전체를 다시 올린다 | 그렇다 | 묶음 전체를 다시 올린다 |
| 태그로 검색하거나 거를 수 있는가 | JSON 컬럼을 읽어야 한다 | JSON 컬럼을 읽어야 한다 | 쉽다 |

### 결정

- A안을 씁니다. `segments.jsonl`과 `scenes.jsonl`의 각 줄에 `valence`, `arousal`, `tags`, `gems`를 담고, `track_segments`와 `scenes` 테이블에 같은 이름의 컬럼을 둡니다. 장면과 구간이 같은 이름과 같은 규칙을 씁니다.
- 네 필드는 값까지 모두 필수입니다. `valence`와 `arousal`은 -1에서 1 사이의 실수이고, `tags`와 `gems`는 하나 이상의 값을 가진 목록입니다.
- `gems`는 GEMS의 아홉 차원 가운데에서만 고를 수 있고, 백엔드가 이를 검사합니다. `tags`에 쓰는 낱말은 AI 레포가 정하며, 백엔드는 검사하지 않습니다.
- 백엔드는 라벨을 저장하고, 평가 자료를 내보낼 때 선곡 기록과 함께 내보냅니다. 곡을 고를 때에는 라벨을 쓰지 않습니다.
- 곡 단위의 태그(`tracks.tags`)는 없앱니다. 그리고 백엔드가 읽지 않는 곡의 출처 필드(`source`, `source_url`)도 함께 없앱니다.
- 정확한 규칙은 [AI_CONTRACT.md 2절](AI_CONTRACT.md#라벨에-대한-규칙)에 있습니다.

### 근거

- 사용자가 네 속성을 장면과 구간에 붙이도록 요청했고, 값까지 모두 필수로 받기로 정했습니다. 그리고 보강할 때 단순함을 가장 앞에 두라고 요청했습니다.
- 라벨은 평가할 때에만 읽으므로, 태그나 GEMS 차원으로 검색하는 일이 없습니다. 따라서 C안처럼 행으로 나눌 이유가 없습니다. (작성자 판단)
- 라벨은 장면이나 구간과 일대일로 붙으므로, 같은 줄에 담으면 ID를 잇는 검증이 필요 없습니다. (작성자 판단)
- GEMS 차원은 아홉 개로 정해져 있어서 검사할 수 있고, 검사하면 철자가 틀린 값이 평가 자료에 섞이는 일을 막습니다. 반면에 태그의 어휘와 태그를 GEMS 차원으로 바꾸는 변환표는 AI팀이 아직 다듬는 중이므로 백엔드가 고정하지 않습니다. (작성자 판단)
- 라벨을 누가 만들었는지나 사람이 검토했는지는 받지 않습니다. 지표를 계산하는 데 필요한 것은 네 값뿐입니다. (작성자 판단)

### 이 결정이 요구하는 조건

값까지 필수이므로, 음악 구간의 V-A를 구하는 방법이 정해지기 전에는 음악 묶음을 올릴 수 없습니다. 태그가 없는 음원도 태그와 GEMS 차원을 채워야 합니다. 이 항목들은 [AI_CONTRACT.md 7절](AI_CONTRACT.md#7-ai팀과-합의할-것)에 합의할 것으로 적어 두었습니다.

### 재검토 조건

- 라벨을 선곡에 쓰게 될 때 다시 검토합니다. 예를 들어 V-A로 먼저 거른 뒤 임베딩으로 고르는 선곡 방식을 추가할 때입니다.
- GEMS 차원의 목록을 바꾸거나 다른 분류 틀로 옮길 때 다시 검토합니다.
- 라벨만 자주 고쳐서 묶음 전체를 다시 올리는 일이 부담될 때 B안을 검토합니다.

## ADR-019: 정확 검색과 동기 적재

### 맥락

2026-11-24에 사용자가 평가 라벨을 보강하면서, 지금 필요하지 않은데 나중을 대비해 넣어 둔 장치를 함께 걷어내도록 요청했습니다. 해당하는 장치는 두 가지였습니다.

- **근사 벡터 인덱스:** 임베딩 모델이 등록될 때마다 그 모델 전용 검색 인덱스를 만들기로 했습니다. 그런데 근사 인덱스는 중단한 곡을 조건으로 걸러 낸 뒤에 k개보다 적은 결과를 돌려줄 수 있어서, 반복 스캔 옵션을 쓰고 k개가 채워지는지를 테스트로 확인해야 했습니다.
- **적재 작업의 상태 조회:** 묶음을 올리면 적재 작업의 ID만 먼저 응답하고, 결과는 `import_jobs` 테이블에 남겨 `GET /api/admin/bundles/{id}`로 조회하게 했습니다. 2차 마일스톤에서 서버가 AI 모델을 호출하게 될 때를 대비한 것이었습니다.

### 후보 비교: 벡터 검색

| 기준 | A. 인덱스 없는 정확 검색 | B. 모델마다 근사 인덱스 |
| --- | --- | --- |
| 걸러 낸 뒤에도 k개를 채우는가 | 언제나 채운다 | 반복 스캔 옵션과 확인 테스트가 필요하다 |
| 모델을 등록할 때 할 일 | 없다 | 묶음이 준 모델 이름으로 인덱스를 만든다 |
| 빠르게 감당하는 규모 | 벡터 수만 개 | 벡터 수십만 개 이상 |

### 후보 비교: 묶음 적재

| 기준 | A. 요청 안에서 끝내고 결과를 응답 | B. 작업으로 기록하고 상태를 조회 |
| --- | --- | --- |
| 필요한 것 | 엔드포인트 하나 | 엔드포인트 둘, 테이블 하나, 상태 관리 |
| 결과를 아는 방법 | 응답을 본다 | 상태를 다시 조회한다 |
| 적재가 오래 걸릴 때 | 요청이 그만큼 오래 열려 있다 | 요청은 곧바로 끝난다 |

### 결정

- 벡터 검색은 A안을 씁니다. 벡터 인덱스를 만들지 않고 정확하게 검색합니다.
- 묶음 적재도 A안을 씁니다. `POST /api/admin/bundles`가 검증과 적재를 마친 뒤 성공 또는 오류 목록을 응답합니다. `import_jobs` 테이블과 상태 조회 엔드포인트는 두지 않습니다.
- 임베딩 모델을 등록 데이터로 다루는 것([ADR-008](#adr-008-임베딩-모델과-선곡-방식의-추상화))과, 적재를 "읽고 검증하는 단계"와 "저장하는 단계"로 나누는 것([ADR-003](#adr-003-ai-모델을-실행하는-방식))은 그대로입니다.

### 근거

- 사용자가 두 장치를 걷어내기로 정했습니다.
- 음악 목록이 수천 곡이면 구간의 벡터는 수만 개 수준이고, 이 규모에서는 정확 검색으로도 페이지 넘김을 방해하지 않을 것으로 예상합니다. (작성자 판단)
- 정확 검색은 "중단한 곡을 뺀 채로 k개를 가져온다"는 요구([ADR-002](#adr-002-데이터베이스와-벡터-검색))를 추가 장치 없이 지킵니다. (작성자 판단)
- 묶음을 올리는 사람은 팀원 몇 명이고, 올린 직후에 결과를 확인합니다. 그래서 결과를 응답으로 바로 받는 쪽이 더 단순합니다. (작성자 판단)
- 2차 마일스톤의 방식은 그때 정합니다. 지금 비동기 구조를 미리 만들어 두어도, 그때의 요구에 맞는다는 보장이 없습니다. (작성자 판단)

### 재검토 조건

- [ADR-002](#adr-002-데이터베이스와-벡터-검색)의 재검토 조건에 해당할 때, 곧 음악 목록이 크게 늘거나 선곡 응답이 페이지 넘김을 방해할 만큼 느려질 때 근사 인덱스를 검토합니다.
- 묶음 적재가 배포 환경의 요청 시간 제한에 걸릴 때 B안을 검토합니다.
- 서버가 AI 모델을 호출해 분석하게 될 때 적재 방식을 다시 정합니다.

## ADR-020: 위치 알림은 후보 K개를 돌려주고 프론트엔드가 재생할 곡을 고른다

### 맥락

2026-11-24에 프론트엔드와의 회의에서 싫어요 버튼을 두고, 싫어요를 누르면 음악을 멈추지 않고 그 장면의 다른 곡을 틀기로 했습니다([DECISIONS.md](DECISIONS.md)의 D-46). 그런데 지금까지의 설계에서는 위치 알림 한 번에 백엔드가 후보 k개 가운데 한 구간을 샘플링해서 곡 하나만 응답했습니다. 이 구조에서 싫어요 직후에 다른 곡을 틀려면 프론트엔드가 백엔드에 다시 물어야 합니다.

회의록의 Decisions 절은 "위치 알림의 결과로 음원 하나가 아니라 k개를 돌려주고, 프론트엔드가 랜덤 샘플링으로 튼다"고 정했습니다. 그러나 같은 회의록의 일정표에는 "샘플링은 백엔드의 위치 알림 안에서 하고, 밀리면 uniform만 남긴다"는 칸이 고쳐지지 않은 채 남아 있어서, 어느 쪽을 따를지를 확인해야 했습니다. 또한 같은 회의에서 구간이 끝나면 음악을 멈추기로 하면서(D-48), "곡이 끝나면 같은 장면의 새 곡을 요청한다"는 뜻의 요청 필드 `trigger: track_ended`를 쓸 곳이 없어졌습니다.

### 후보 비교

| 기준 | A. 백엔드는 K개를 장면과 가까운 순서로 주고, 프론트엔드가 무작위로 고른다 | B. 백엔드가 K개를 샘플링으로 줄 세워 주고, 프론트엔드는 순서대로 튼다 | C. 백엔드가 한 곡씩 준다 (이전 설계) |
| --- | --- | --- | --- |
| 싫어요 뒤에 다음 곡을 트는 방법 | 프론트엔드가 곧바로 튼다 | 프론트엔드가 곧바로 튼다 | 프론트엔드가 위치 알림을 다시 보낸다 |
| 샘플링하는 곳 | 프론트엔드 | 백엔드 | 백엔드 |
| 가까운 후보에 더 높은 확률을 주는 샘플링 | 없다 | 둘 수 있다 | 둘 수 있다 |
| 실제로 재생된 곡을 아는 방법 | 재생 시작 이벤트 | 목록의 순서와 재생 시작 이벤트 | 응답 그 자체 |
| 응답 하나에 담기는 것 | 후보 K개와 서명된 주소 K개 | A와 같다 | 곡 하나와 서명된 주소 하나 |

### 결정

- A안을 씁니다. 위치 알림의 `play` 응답은 후보 목록(`candidates`)을 담고, 후보마다 `recommendation_id`, `selection_reason`, `track`(서명된 주소 포함)을 둡니다. 후보는 최대 `RECOMMENDATION_TOP_K`개이며, 장면과 가까운 순서로 둡니다. 그 가운데 무엇을 틀지는 프론트엔드가 무작위로 고릅니다.
- 지정 곡이 있으면, 그 곡의 활성 구간 가운데 사용자가 싫어요하지 않은 것에서 장면과 가장 가까운 구간을 `selection_reason`이 `designated`인 후보로 맨 앞에 둡니다. 프론트엔드는 이 후보를 먼저 틉니다. 지정 곡의 후보도 k개 안에 셉니다.
- 선곡 기록(`recommendations`)은 후보 하나당 한 행입니다. 응답 하나에 담긴 후보들은 `candidate_list_id`로 묶고, 목록 안의 순서는 `rank_idx`에 둡니다. 후보 목록을 JSON으로 담던 `candidates` 컬럼은 없앱니다. 후보 가운데 실제로 재생된 것은 `started` 이벤트로 압니다.
- 응답의 `action`은 `play`와 `keep` 두 가지입니다. 자동 재생 쉬는 시간(D-47)과 무음 방식([ADR-021](#adr-021-선곡-방식의-추상화를-없애고-설정에는-임베딩-모델만-둔다))이 없어져서 `silence`를 응답할 경우가 없으므로 없앱니다. 후보가 하나도 없으면 빈 목록을 응답하고, 프론트엔드는 이를 후보를 모두 넘긴 목록과 똑같이 다룹니다.
- 요청의 `trigger` 필드를 없앱니다. `current_recommendation_id`가 가리키는 후보의 장면이 이번 장면과 같으면 `keep`을, 그 밖의 경우에는 새 후보 목록을 응답합니다.
- 백엔드의 샘플링 설정(`RECOMMENDATION_SAMPLING`, `RECOMMENDATION_SAMPLING_TEMPERATURE`)을 없앱니다.
- 형식과 프론트엔드의 재생 규칙은 [API.md 4.7절](API.md#47-위치-알림)에 있습니다.

### 근거

- 사용자가 A안을 선택했습니다. 회의록의 Decisions 절에 적힌 결정과 같습니다.
- 싫어요 뒤에 서버를 다시 거치지 않으므로 곡이 곧바로 바뀝니다. (작성자 판단)
- 후보마다 선곡 기록이 있으므로, 반응 기록이 실제로 들은 후보에 정확히 붙습니다. 그리고 평가할 때 "함께 나온 후보"와 "실제로 재생된 후보"를 모두 볼 수 있습니다. (작성자 판단)
- 서명된 주소는 서버 안에서 계산만으로 만들 수 있으므로, K개를 발급해도 위치 알림이 크게 느려지지 않습니다. (작성자 판단)
- 장면은 여전히 백엔드가 고르므로 [ADR-005](#adr-005-프론트엔드와의-api-연동-방식)와 어긋나지 않습니다.
- `silence`와 `trigger`는 쓰는 곳이 사라진 장치이므로, 나중을 대비해 남겨 두지 않습니다. [ADR-019](#adr-019-정확-검색과-동기-적재)와 같은 기준입니다. (작성자 판단)

### 재검토 조건

- 장면과 가까운 후보를 더 자주 틀어야 한다는 평가 결과가 나오면 B안을 검토합니다.
- 응답의 크기나 서명된 주소의 발급 때문에 위치 알림이 느려지면 k를 줄이거나 다시 검토합니다.
- 구간이 끝난 뒤의 재생 방식을 바꿀 때(D-48의 재검토) 다시 검토합니다.

## ADR-021: 선곡 방식의 추상화를 없애고 설정에는 임베딩 모델만 둔다

### 맥락

2026-11-24에 선곡 방식을 장면에 맞춘 선곡(임베딩) 하나로 고정하고, 사용자는 임베딩 모델만 고르기로 했습니다([DECISIONS.md](DECISIONS.md)의 D-49). 그런데 [ADR-008](#adr-008-임베딩-모델과-선곡-방식의-추상화)은 선곡 방식을 공통 인터페이스(`RecommendationStrategy`)의 구현체로 만들고, 임베딩, 랜덤, 무음의 세 가지를 두기로 했습니다. 그래서 `user_settings`와 `recommendations`의 컬럼, 설정 API, 설정값 `DEFAULT_STRATEGY`에 선곡 방식이 들어 있었습니다.

### 후보 비교

| 기준 | A. 인터페이스와 `strategy` 필드를 없앤다 | B. 인터페이스는 두고 구현체를 임베딩 하나만 둔다 |
| --- | --- | --- |
| 코드 | 후보를 고르는 로직 하나 | 인터페이스와 구현체 하나 |
| API와 데이터 | 선곡 방식이 없다 | `strategy`가 언제나 `embedding`이다 |
| 새 방식을 추가할 때 | 그때 인터페이스를 만든다 | 구현체만 더한다 |

### 결정

- A안을 씁니다. `RecommendationStrategy` 포트와 랜덤, 무음 구현을 두지 않습니다. 그리고 `user_settings.strategy`, `recommendations.strategy`, 설정 API의 `strategy`, 설정값 `DEFAULT_STRATEGY`를 없앱니다.
- `GET /api/me/settings`는 `embedding_model`과, 등록된 모델의 이름 목록인 `available_embedding_models`를 응답합니다. `PUT /api/me/settings`는 `embedding_model`만 받으며, 등록되지 않은 모델이면 `400 VALIDATION_ERROR`를 응답합니다([API.md 4.4절](API.md#44-선곡-설정)).
- 임베딩 모델을 등록 데이터로 다룬다는 ADR-008의 결정은 그대로입니다. 이 결정은 ADR-008 가운데 선곡 방식에 관한 부분을 대체합니다.

### 근거

- 사용자가 선곡 방식을 하나로 고정하기로 했습니다(D-49).
- 구현이 하나뿐인 인터페이스는 쓰이지 않는 장치입니다. [ADR-019](#adr-019-정확-검색과-동기-적재)에서처럼 지금 필요하지 않은 장치는 두지 않습니다. (작성자 판단)
- 모델의 목록을 설정 응답에 담으면, 프론트엔드가 모델의 이름을 코드에 적어 두지 않고도 새로 등록된 모델을 보여 줄 수 있습니다. 그리고 엔드포인트를 따로 만들지 않아도 됩니다. (작성자 판단)

### 재검토 조건

- 평가 라벨(V-A)로 먼저 거르는 방식처럼 두 번째 선곡 방식을 추가할 때, 인터페이스를 다시 둘지 검토합니다.
- 무음이나 무작위 선곡과의 비교를 다시 하기로 할 때 다시 검토합니다.

## ADR-022: 싫어요는 구간 단위로 기록한다

### 맥락

2026-11-24에 싫어요를 누른 구간은 그 사용자에게 다시 나오지 않게 하기로 했습니다([DECISIONS.md](DECISIONS.md)의 D-46). 지금까지의 설계는 사용자가 중단한 곡을 `track_blocks(user_id, track_id)`에 담고, 그 곡의 모든 구간을 검색에서 뺐습니다. 그리고 [ADR-013](#adr-013-다시-올린-산출물의-보존-방식)은 "곡 ID가 바뀌지 않으므로, 구간을 새로 나누더라도 그 곡의 중단 기록과 좋아요는 그대로 이어진다"를 근거의 하나로 들었습니다. 구간 단위로 바꾸면 이 근거가 더는 맞지 않습니다.

### 후보 비교

| 기준 | A. 싫어요를 누른 구간만 기록한다 | B. A에 더해, 다시 나눈 새 구간 가운데 시간 범위가 겹치는 것도 뺀다 |
| --- | --- | --- |
| 테이블 | `segment_blocks(user_id, segment_id)` | A와 같다 |
| 곡의 구간을 다시 나눴을 때 | 새 구간은 제외되지 않는다 | 시간 범위가 겹치는 새 구간도 제외된다 |
| 검색에서 거르는 조건 | 구간 ID | 곡 ID와 시간 범위의 비교 |

### 결정

- A안을 씁니다. `track_blocks`를 `segment_blocks(user_id, segment_id)`로 바꾸고, 벡터 검색과 지정 곡의 구간을 고를 때 이 구간들을 뺍니다.
- 좋아요(`track_likes`)는 곡 단위로 그대로 둡니다.
- 이 결정은 ADR-013의 근거 가운데 "중단 기록이 그대로 이어진다"는 부분을 대체합니다. 좋아요가 그대로 이어진다는 부분은 그대로입니다.

### 근거

- 사용자가 구간 단위의 영구 제외를 선택했습니다(D-46).
- 1차 MVP에서는 곡의 구간을 다시 나눌 일이 드뭅니다. 그리고 다시 나누더라도 싫어요를 누른 부분이 새 구간으로 한 번 더 나올 수 있을 뿐이므로, 시간 범위를 비교하는 규칙을 더할 만큼의 이득이 없습니다. (작성자 판단)
- 좋아요는 "이 곡이 좋다"는 표시이고 프론트엔드가 곡 정보 옆에 보여 주므로, 곡 단위가 자연스럽습니다. (작성자 판단)

### 재검토 조건

- 곡의 구간을 자주 다시 나누게 되어, 싫어요를 누른 부분이 다시 나온다는 문제가 생길 때 B안을 검토합니다.
- 싫어요의 제외 범위를 곡 전체로 넓히기로 할 때 다시 검토합니다.

## ADR-023: 배포 인프라

### 맥락

[ADR-010](#adr-010-배포-방식)은 Docker 컨테이너로 배포한다는 것만 정하고, 구체적인 인프라는 프론트엔드와 상의한 뒤 정하기로 했습니다. 그리고 인프라가 정해지면 ADR-010을 "확정"으로 바꾸고 새 기록을 추가하기로 했습니다.

2026-11-24에 프론트엔드와의 회의에서 인프라를 정했습니다. 그런데 회의록은 "프론트엔드와 백엔드는 모두 GCP"라고 적으면서, 배포를 연결하는 Epic의 프론트엔드 작업에는 Vercel의 설정 파일(`vercel.json`)에 `/api`를 넘기는 규칙을 더한다고 적었습니다. 그래서 프론트엔드를 어디에 올릴지와, 쿠키 로그인에 필요한 같은 도메인 조건([ADR-006](#adr-006-로그인과-접근-제한))을 어떻게 맞출지를 함께 정했습니다.

### 후보 비교: 같은 도메인 조건을 맞추는 구성

| 기준 | A. 프론트엔드도 GCP, 호스팅이 `/api`를 백엔드로 넘김 | B. 프론트엔드는 Vercel, `vercel.json`이 `/api`를 백엔드로 넘김 | C. 둘 다 GCP, 하위 주소를 나눔 |
| --- | --- | --- | --- |
| 프론트엔드를 올리는 곳 | GCP | Vercel | GCP |
| 백엔드의 CORS 설정 | 필요 없다 | 필요 없다 | 필요하다 |
| 프론트엔드의 API 주소 | 지금의 `/api` 그대로 | 지금의 `/api` 그대로 | 전체 주소를 설정값으로 받아야 한다 |
| 회의록과의 관계 | "모두 GCP"를 따른다 | `vercel.json` 항목을 따른다 | "모두 GCP"를 따른다 |

### 결정

- 프론트엔드와 백엔드는 GCP에 올립니다.
- 같은 도메인 조건은 A안으로 맞춥니다. 프론트엔드를 호스팅하는 GCP 서비스가 `/api`로 시작하는 요청을 백엔드로 넘겨줍니다.
- 음원 저장소는 Cloudflare R2를 씁니다. 저장소를 비공개로 두고 서명된 주소로만 음원을 받게 한다는 ADR-010의 결정은 그대로입니다.
- 도메인은 Cloudflare에서 삽니다.
- 백엔드를 올릴 GCP 서비스, PostgreSQL을 둘 곳, 비밀값의 보관, 배포할 때 마이그레이션을 실행하는 시점은 아직 정하지 않았으며, [INFRA.md](INFRA.md#3-정해야-할-항목과-고려사항) 3절에 정리합니다.

### 근거

- 회의에서 프론트엔드와 백엔드를 GCP에, 음원을 R2에 두고 도메인을 Cloudflare에서 사기로 정했습니다. 그리고 사용자가 같은 도메인 조건을 A안으로 맞추기로 선택했습니다.
- A안에서는 브라우저가 보기에 주소가 하나이므로 CORS 설정이 필요 없고, 프론트엔드가 지금 쓰는 `/api` 경로를 그대로 쓸 수 있습니다. (작성자 판단)
- R2는 S3와 같은 방식의 서명된 주소를 지원하며, 저장소에서 밖으로 나가는 전송량에 요금을 매기지 않습니다. 독자가 곡을 들을 때마다 음원이 전송되므로, 전송 요금이 없는 것이 비용에 유리합니다. (작성자 판단)
- 음원 저장소는 `ObjectStorage` 포트 뒤에 있으므로([ADR-007](#adr-007-코드-구조)), R2를 위한 어댑터만 더하면 됩니다. (작성자 판단)

### 재검토 조건

- 프론트엔드의 호스팅이 `/api` 요청을 백엔드로 넘겨줄 수 없게 되면, 하위 주소를 나누는 구성(C안)으로 바꾸고 CORS를 설정합니다.
- 묶음 적재가 호스팅이나 백엔드 서비스의 요청 크기나 시간 제한에 걸리면([INFRA.md 3.1절](INFRA.md#31-백엔드를-gcp의-어느-서비스에-올릴-것인가)) 적재 경로를 다시 정합니다. 이때 ADR-019의 재검토 조건을 함께 봅니다.
- GCP의 무료 크레딧이 끝나서 비용이 생기면 다시 검토합니다.

## ADR-024: 허용 목록의 관리와 확인

### 맥락

테스트용 책에 저작권이 있는 소설이 들어 있으므로 허용 목록에 있는 사람만 서비스를 써야 합니다([DECISIONS.md](DECISIONS.md)의 D-06, [ADR-006](#adr-006-로그인과-접근-제한)). 지금까지의 계약에는 관리자가 허용 목록을 조회하고, 추가하고, 빼는 API 세 개가 있었습니다. 그리고 회의에서는 Google 콘솔의 테스터 목록에도 테스터를 따로 등록하기로 했습니다(D-53).

그런데 Google 문서에 따르면, 앱이 이름, 이메일, 프로필(openid, email, profile)만 요청하면 동의 화면이 "테스트" 상태여도 테스터 목록에 없는 사람이 로그인할 수 있습니다([Manage App Audience](https://support.google.com/cloud/answer/15549945?hl=en)). 이 백엔드는 이 세 범위만 요청하므로, Google 콘솔의 테스터 목록은 접근을 막지 못합니다. 그러므로 백엔드의 허용 목록이 유일한 관문입니다.

허용 목록은 실사용 테스트 직전에 열 명 남짓을 한 번 넣고 팀원 몇 명을 더하는 정도로만 바뀌며, 다루는 사람은 백엔드 담당자입니다.

### 후보 비교

| 기준 | A. 관리 API (`/api/admin/allowed-emails`) | B. 환경 변수 | C. 데이터베이스에 두고 SQL로 다룸 |
| --- | --- | --- | --- |
| 목록을 바꾸는 방법 | 관리자 화면이나 API 호출 | 환경 변수를 고치고 서버를 다시 띄움 | 데이터베이스에 SQL을 실행 |
| 바꾼 뒤 서버를 다시 띄워야 하는가 | 아니다 | 그렇다 | 아니다 |
| 만들 것 | 테이블, 엔드포인트 세 개와 테스트, 프론트엔드의 관리자 화면 | 설정값 두 개 | 테이블 |
| 바꾸는 데 필요한 권한 | 관리자 계정 | 배포 환경의 설정 권한 | 데이터베이스 접속 권한 |

### 결정

- C안을 씁니다. 허용 목록은 `allowed_emails` 테이블에 두고, 관리 API는 만들지 않습니다. 넣고 빼는 SQL은 [README](../README.md)의 "허용 목록에 사람 넣고 빼기"에 있습니다.
- 서버가 시작할 때 허용 목록에 관리자를 넣어 주던 설정값 `BOOTSTRAP_ADMIN_EMAILS`를 없앱니다. 첫 관리자도 SQL로 넣습니다.
- 관문은 보호된 경로의 요청마다 데이터베이스의 `allowed_emails`를 확인하며, 허용 목록을 프로세스의 메모리에 담아 두지 않습니다. 그래서 SQL로 목록이나 역할을 바꾸면 서버를 다시 띄우지 않아도 다음 요청부터 반영됩니다.
- 이메일은 소문자로만 저장하고, Google에서 받은 이메일도 소문자로 바꿔서 비교합니다. 테이블에는 이를 강제하는 제약을 둡니다. 스키마는 [ARCHITECTURE.md 6절](ARCHITECTURE.md#6-데이터-모델)에 있습니다.

### 근거

- 사용자가 관리 API 없이 데이터베이스에 직접 넣는 방식을 선택했고, 목록을 바꿀 때 서버를 다시 띄우지 않아야 한다고 요구했습니다.
- 목록이 바뀌는 일이 드물고 다루는 사람이 한 명이므로, 엔드포인트 세 개와 관리자 화면을 만드는 비용에 비해 얻는 것이 적습니다. (작성자 판단)
- 허용 목록의 원천이 데이터베이스 하나뿐이어야, 설정값과 테이블의 내용이 어긋나서 지운 사람이 다시 들어오는 일이 없습니다. (작성자 판단)
- 요청마다 확인하면 목록에서 뺀 사람의 로그인 상태가 남아 있더라도 다음 요청부터 막히므로, 로그인 상태를 끊는 기능을 따로 두지 않아도 됩니다. (작성자 판단)
- SQL로 넣은 값과 Google이 주는 값의 대소문자가 다르면, 허용된 사람이 막히거나 지운 사람이 다시 통과할 수 있습니다. 그래서 저장과 비교를 모두 소문자로 맞춥니다. (작성자 판단)

### 재검토 조건

- 허용 목록을 자주 바꿔야 하거나 백엔드 담당자가 아닌 사람이 다뤄야 하면 관리 API를 추가합니다. 엔드포인트를 더하는 변경이므로 기존 계약을 깨지 않습니다.
- 요청마다 확인하는 질의가 응답 시간에 영향을 줄 만큼 느려지면, 짧은 수명의 캐시를 검토합니다. 이때 목록에서 뺀 사람이 막히기까지의 지연을 함께 정합니다.

## ADR-025: Google 로그인 흐름의 세부

### 맥락

[ADR-006](#adr-006-로그인과-접근-제한)은 Google 로그인의 전 과정을 백엔드가 처리하고, 로그인 상태를 서버에 저장하며, 브라우저에는 HttpOnly 쿠키만 심기로 정했습니다. 로그인을 만드는 Epic 1을 설계하면서 그 세부를 정해야 했습니다. 이때 다음 사실을 고려했습니다.

- 로컬에서는 프론트엔드의 개발 서버가 `/api` 요청을 백엔드로 넘겨주며, 이때 요청의 Host를 백엔드의 주소로 바꿉니다(`changeOrigin: true`). 운영 환경에서는 프론트엔드의 호스팅이 `/api` 요청을 넘겨줍니다([ADR-023](#adr-023-배포-인프라)).
- 로컬은 HTTP이고 운영 환경은 HTTPS입니다.
- 지금까지의 계약은 로그인에 성공한 경우와 허용 목록에 없는 경우만 정했고, 사용자가 동의 화면에서 취소하는 것처럼 로그인이 실패한 경우를 정하지 않았습니다.

### 결정

- **돌아올 주소**: Google이 로그인 결과를 돌려보낼 주소는 설정값 `FRONTEND_URL` 뒤에 `/api/auth/google/callback`을 붙여 만듭니다. 요청의 Host로 만들지 않습니다.
- **요청하는 범위**: `openid`, `email`, `profile`만 요청합니다.
- **`state`**: 로그인을 시작할 때 임의의 값을 만들어 짧은 수명의 HttpOnly 쿠키(`diegesis_oauth_state`)에 담고, 결과를 받을 때 Google이 돌려준 `state`와 비교합니다.
- **실패 처리**: 로그인이 실패하면 쿠키를 심지 않고 프론트엔드의 `/login?error=LOGIN_FAILED`로 보냅니다. 사용자가 동의 화면에서 취소했을 때, `state`가 없거나 맞지 않을 때, Google과 코드를 교환하지 못했을 때, Google이 이메일을 확인하지 않은 계정일 때가 여기에 해당합니다. 허용 목록에 없는 계정은 실패와 구분해서 `/login?error=NOT_ALLOWED`로 보냅니다.
- **로그아웃**: 쿠키가 없거나 이미 무효인 상태로 로그아웃을 요청해도 204를 응답합니다.
- **쿠키의 속성**: 로그인 상태의 쿠키에는 `HttpOnly`, `SameSite=Lax`, `Path=/`를 붙이고, 로그인 상태의 유지 시간을 `Max-Age`로 줍니다. `Secure`는 `APP_ENV`가 `production`일 때에만 붙입니다.
- 각 엔드포인트의 형식과 동작 순서는 [API.md 4.2절](API.md#42-로그인과-로그아웃)에 있습니다.

### 근거

- 프론트엔드의 개발 서버가 Host를 바꾸므로, 요청의 Host로 주소를 만들면 로컬에서 돌아올 주소가 `localhost:8080`이 됩니다. 그러면 로컬의 로그인 흐름이 운영 환경과 달라집니다. 로컬과 운영 환경 모두 프론트엔드의 주소로 돌아오게 하면 같은 흐름을 확인할 수 있고, 설정값을 따로 추가하지 않아도 됩니다. (작성자 판단)
- 세 범위만 요청하면 테스트 중인 앱이라는 경고 화면이 사용자에게 보이지 않습니다([Manage App Audience](https://support.google.com/cloud/answer/15549945?hl=en)). 그리고 사용자를 구별하고 이름을 보여 주는 데 이것으로 충분합니다. (작성자 판단)
- `state`를 쿠키에 두면 로그인을 시작하는 데 데이터베이스가 필요 없습니다. Google이 결과를 돌려보내는 요청은 최상위 화면 이동이므로 `SameSite=Lax` 쿠키가 함께 옵니다. (작성자 판단)
- 실패와 허용 목록 밖을 나누면, 프론트엔드가 "다시 시도하세요"와 "테스트 참가자가 아닙니다"를 구분해서 안내할 수 있습니다. 실패의 자세한 원인은 서버의 로그에만 남깁니다. (작성자 판단)
- 로그아웃은 프론트엔드가 상태를 확인하지 않고 부를 수 있어야 하므로, 여러 번 불러도 결과가 같게 합니다. (작성자 판단)
- 로컬은 HTTP이므로 `Secure`를 붙이면 브라우저에 따라 쿠키가 저장되지 않습니다. 운영 환경은 HTTPS이므로 `Secure`를 붙입니다. (작성자 판단)

### 재검토 조건

- 프론트엔드와 백엔드가 같은 주소를 함께 쓰지 않게 되면([ADR-023](#adr-023-배포-인프라)의 재검토 조건), 돌아올 주소와 쿠키의 속성을 다시 정합니다.
- 로그인 뒤에 첫 화면이 아닌 원래 보던 화면으로 돌아가게 하기로 하면, 돌아갈 화면을 안전하게 전달하는 방법을 정합니다.

## ADR-026: 로컬에서 실제 Google 로그인을 점검하는 방법

### 맥락

Epic 1이 끝나면 백엔드 담당자가 로컬에서 실제 Google 계정으로 로그인과 로그아웃이 끝까지 되는지 확인해야 합니다. 로그인 흐름의 분기는 가짜 `IdentityProvider`를 끼운 테스트가 확인하지만, 실제 Google과 주고받는 부분은 실제 계정으로만 확인할 수 있습니다. 이때 다음 사실을 고려했습니다.

- Google은 로그인 결과를 프론트엔드의 주소(`{FRONTEND_URL}/api/auth/google/callback`)로 돌려보냅니다. 로컬에서는 프론트엔드의 개발 서버가 이 요청을 받아, Host를 바꿔 백엔드로 넘깁니다([ADR-025](#adr-025-google-로그인-흐름의-세부)).
- 백엔드 담당자는 프론트엔드 레포를 띄우지 않고 점검할 수 있어야 합니다.
- 로그인과 로그아웃이 `users`와 `login_sessions`에 남기는 것을 시점마다 확인해야 합니다.
- Google 계정의 비밀번호는 사람만 다뤄야 합니다.

### 후보 비교

| 기준 | A. 프론트엔드 레포의 개발 서버를 띄우고 사람이 브라우저로 따라감 | B. `FRONTEND_URL`을 백엔드의 주소로 두고 사람이 브라우저로 따라감 | C. 프론트엔드 대역 서버와 Playwright 점검 스크립트 |
| --- | --- | --- | --- |
| 프론트엔드 레포가 필요한가 | 필요하다 | 필요 없다 | 필요 없다 |
| 운영 환경과 같은 경로를 지나는가 (프론트엔드의 주소로 돌아오고, Host가 바뀐다) | 지난다 | 지나지 않는다 | 지난다 |
| Google 콘솔에 돌아올 주소를 더 등록해야 하는가 | 아니다 | 그렇다 | 아니다 |
| 시점마다 테이블 상태를 보는 방법 | 사람이 SQL을 실행한다 | 사람이 SQL을 실행한다 | 스크립트가 출력한다 |
| 사람이 하는 일 | 전부 | 전부 | Google 화면에서 계정을 고르고, 출력을 기대 상태와 대조한다 |
| 만들 것 | 없다 | 없다 | 대역 서버, 점검 스크립트, 개발 의존성 하나 |

### 결정

- C안을 씁니다. 점검 스크립트가 `FRONTEND_URL`의 주소에 대역 서버를 띄웁니다. 그리고 Playwright(Python)로 화면이 보이는 브라우저를 열어, 프론트엔드가 하는 순서대로 로그인 시작, `GET /api/me`, 로그아웃을 부릅니다. 대역 서버는 프론트엔드의 개발 서버처럼 `/api` 요청을 Host를 바꿔 백엔드로 넘깁니다.
- Google 화면의 입력은 사람이 합니다. 스크립트는 비밀번호를 다루지 않고, 브라우저는 실행할 때마다 새 프로필로 엽니다.
- 스크립트는 compose로 띄운 개발용 데이터베이스를 읽기만 하며, 시점마다 `allowed_emails`, `users`, `login_sessions`의 상태를 출력합니다.
- 스크립트는 `scripts/check.sh`와 CI에서 실행하지 않습니다. phase의 MANUAL 점검에서 사람이 실행합니다. 다만 대역 서버가 요청을 넘기는 방식은 Google 없이 확인할 수 있으므로 검사의 테스트로 확인합니다.
- Playwright는 개발 의존성으로 둡니다. 서버의 이미지는 개발 의존성을 설치하지 않으므로 Playwright가 들어가지 않습니다. 브라우저는 점검하는 사람이 처음에 한 번 설치합니다.
- 점검의 세부와 시점별 기대 상태는 [Epic 1 문서](backlog/epic-1/E1-login-allowlist.md)의 S1.7과 [테스트 케이스](backlog/epic-1/testcase.md#로컬-로그인-점검의-테이블-상태)에 있습니다.

### 근거

- 사용자(백엔드 담당자)가 정한 것입니다. 로컬에서 프론트엔드의 동작을 흉내 내어 Google 로그인을 확인하고, 이것을 Playwright로 자동화하며, 결과는 MANUAL 점검에서 직접 확인합니다. 그리고 MANUAL 점검표에 로그인 전후와 로그아웃 전후의 테이블 상태를 넣습니다.
- 대역 서버가 프론트엔드의 개발 서버처럼 Host를 바꿔 넘기면, 돌아올 주소를 요청의 Host로 만드는 결함이 로컬에서도 드러납니다. B안은 이 경로를 지나지 않으므로 그 결함을 놓칩니다. (작성자 판단)
- 시점마다 사람이 SQL로 테이블을 보면, 빠뜨리거나 시점을 놓치기 쉽습니다. 스크립트가 매번 같은 순서로 출력하면, 사람은 같은 기준으로 대조할 수 있습니다. (작성자 판단)
- Google 계정의 비밀번호와 Google의 로그인 상태가 담긴 브라우저 프로필은 코드나 디스크에 남기지 않아야 합니다. 그래서 입력은 사람이 하고, 프로필은 남기지 않습니다. (작성자 판단)
- Playwright는 Python 패키지로 받을 수 있으므로, 이 레포의 도구(uv, ruff, pyright)로 함께 관리할 수 있습니다. (작성자 판단)

### 재검토 조건

- Google이 Playwright가 연 브라우저에서의 로그인을 막으면, 사람이 직접 연 브라우저에 연결하는 방식 등을 다시 정합니다. 자동화를 탐지하는 장치를 피하는 옵션은 쓰지 않습니다.
- 프론트엔드 레포가 실제 백엔드와 함께 도는 브라우저 테스트를 갖추면, 이 점검을 그쪽으로 넘길지 정합니다.

## ADR-027: 로그인 흐름과 로그인 상태의 보안 보강

### 맥락

Epic 1의 계약([ADR-024](#adr-024-허용-목록의-관리와-확인), [ADR-025](#adr-025-google-로그인-흐름의-세부), [API.md 4.2절](API.md#42-로그인과-로그아웃))을 업계의 기준에 비추어 다시 검토했습니다. 기준으로 삼은 문서는 OAuth 2.0 Security Best Current Practice([RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)), [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html), OWASP의 [Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)와 [CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)입니다. 검토에서 다음 빈틈이 나왔습니다.

- Google이 돌려준 `code`의 탈취와 주입을 막는 장치가 `state` 하나뿐입니다. PKCE도, OpenID Connect의 `nonce`도 쓰지 않습니다.
- ID 토큰에서 대상(`aud`)만 확인하고, 발급자(`iss`), 만료 시각(`exp`), `nonce`는 확인하지 않습니다.
- `Secure`를 `APP_ENV`가 `production`일 때에만 붙입니다. 그런데 `APP_ENV`의 기본값이 `local`이므로, 배포 설정에서 이 값을 빠뜨리면 운영 환경의 쿠키가 아무 경고 없이 HTTP로도 전송됩니다.
- 다른 사이트에서 오는 요청 위조(CSRF)를 막는 장치가 `SameSite=Lax` 하나뿐입니다. OWASP는 SameSite를 보조 방어로만 봅니다.
- 사용자를 이메일로만 식별합니다. Google에서는 한 이메일 주소가 시간이 지나 다른 Google 계정에 붙을 수 있습니다. 예를 들어 지운 Workspace 계정과 같은 주소로 새 계정을 만들 수 있습니다. 그러면 새 계정의 주인이 기존 `users` 행과 기록을 넘겨받습니다.
- 허용 목록에서 뺀 사람의 로그인 상태가 남아 있다가, 그 사람을 다시 넣으면 옛 쿠키가 다시 통과합니다.
- 쿠키 값과 `state`를 무엇으로 얼마나 길게 만드는지, `state`를 어떻게 비교하는지 정하지 않았습니다.
- 다시 로그인해도 같은 브라우저의 옛 로그인 상태가 지워지지 않고, 만료된 행은 지우지 않아 계속 쌓입니다.
- 쿠키 이름에 `__Host-` 접두사가 없어서, 같은 사이트의 다른 서브도메인이 같은 이름의 쿠키를 심어 덮어쓸 수 있습니다(cookie tossing).

이 계약은 harness의 에이전트가 사람 없이 구현합니다. 그래서 문서가 정하지 않은 보안 요구는 구현에서도 빠지기 쉽고, 문서와 테스트 케이스로 막아야 합니다.

### 후보 비교

`Secure`를 붙이는 조건은 다음 두 후보를 비교했습니다.

| 기준 | A. `APP_ENV`를 필수로 바꾸고, `FRONTEND_URL`이 https인데 `local`이면 서버를 시작하지 않음 | B. `FRONTEND_URL`의 스킴으로 정하고 `APP_ENV`를 없앰 |
| --- | --- | --- |
| 배포 설정에서 값을 하나 빠뜨렸을 때 | 서버가 시작되지 않는다 | 빠뜨릴 값이 없다. `FRONTEND_URL`은 이미 필수다 |
| 설정값의 수 | 그대로 | 하나 줄어든다 |
| 실제 주소와 쿠키 속성이 어긋날 수 있는가 | 두 값이 따로 있으므로 어긋날 수 있다 | 같은 값에서 나오므로 어긋나지 않는다 |

CSRF를 막는 장치는 다음 세 후보를 비교했습니다.

| 기준 | A. CSRF 토큰 (double submit) | B. `Origin` 확인 (없으면 `Referer`) | C. Fetch Metadata (`Sec-Fetch-Site`) |
| --- | --- | --- | --- |
| 프론트엔드가 할 일 | 토큰을 읽어 요청마다 헤더에 붙인다 | 없다. 브라우저가 붙인다 | 없다. 브라우저가 붙인다 |
| 비교할 기준 | 쿠키와 헤더의 토큰 | 설정값 `FRONTEND_URL` 하나 | 브라우저가 판정한 값 |
| 지원하는 브라우저 | 모두 | 모두 | 오래된 브라우저는 보내지 않는다 |

로그인 상태의 수명은 `LOGIN_SESSION_TTL_HOURS`(기본 14일)를 줄이지 않는다는 전제에서 다음 두 후보를 비교했습니다.

| 기준 | A. 절대 만료와 정리 규칙 | B. A에 유휴 만료를 더함 |
| --- | --- | --- |
| 만료 시각 | 로그인할 때 정하고 늘리지 않는다 | A와 같고, 정해진 시간 넘게 쓰지 않아도 만료된다 |
| 추가하는 것 | 없다 | `last_used_at` 컬럼, 설정값 하나, 관문의 쓰기 |
| 로그아웃하지 않고 버려진 기기 | 최대 TTL 동안 유효하다 | 유휴 시간이 지나면 만료된다 |
| 사용자의 불편 | TTL마다 다시 로그인한다 | 유휴 시간 넘게 쉬면 다시 로그인한다 |

### 결정

**로그인 흐름**

- 로그인을 시작할 때 `state`, `nonce`, `code_verifier`를 하나씩 만듭니다. 인가 주소에는 `state`, `nonce`, 그리고 `code_verifier`의 SHA-256을 base64url로 바꾼 `code_challenge`를 `code_challenge_method=S256`과 함께 붙입니다(PKCE). `plain` 방식은 쓰지 않습니다.
- 세 값은 `diegesis_oauth_state` 쿠키 하나에 `{state}.{nonce}.{code_verifier}`의 형태로 담습니다. 세 값은 base64url 문자만 쓰므로 `.`으로 나눌 수 있습니다.
- 결과를 받을 때에는 쿠키를 정확히 세 부분으로 나눕니다. 쿠키나 쿼리의 `state`가 비어 있거나, 두 값이 다르면 실패입니다. 비교는 `hmac.compare_digest`로 합니다. `nonce`도 같은 방법으로 비교합니다.
- `code`를 교환할 때 `code_verifier`를 함께 보냅니다.
- ID 토큰은 Google의 토큰 엔드포인트가 TLS로 돌려준 응답에서만 받습니다. 브라우저나 쿼리로 ID 토큰을 받는 경로는 만들지 않습니다. 그래서 서명은 확인하지 않아도 됩니다([OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)의 3.1.3.7절 6항).
- 대신 ID 토큰의 클레임은 모두 확인합니다. `iss`는 `https://accounts.google.com`이나 `accounts.google.com`이고, `aud`는 우리의 클라이언트 ID이며, `azp`가 있으면 그것도 우리의 클라이언트 ID입니다. `exp`는 지금보다 뒤이고, `nonce`는 쿠키의 `nonce`와 같으며, `sub`와 `email`은 비어 있지 않습니다. 하나라도 어긋나면 로그인 실패입니다.

**사용자의 식별**

- `users`에 Google 계정의 식별자인 `sub`를 `google_sub` 컬럼(고유, 필수)으로 저장합니다.
- 처음 로그인할 때 이메일과 `sub`를 한 쌍으로 묶습니다. 그 뒤에 이메일은 기존 행과 같은데 `sub`가 다르거나, `sub`는 기존 행과 같은데 이메일이 다르면 로그인을 거부합니다. 이때 `LOGIN_FAILED`로 보내고 그 사실을 로그에 남깁니다. 바로잡아야 하면 백엔드 담당자가 SQL로 고칩니다.
- 허용 목록은 지금처럼 이메일로 확인합니다.

**임의의 값**

- 로그인 상태의 쿠키 값, `state`, `nonce`, `code_verifier`는 함수 하나에서 `secrets.token_urlsafe(32)`로 만듭니다. 256비트의 무작위 값이며, base64url 문자 43자입니다. `random` 모듈, `uuid`, 시각으로 만들지 않습니다.
- ruff의 규칙에 `S311`을 더해, `random` 모듈을 쓴 코드가 검사를 통과하지 못하게 합니다.

**`Secure`와 `FRONTEND_URL`**

- B안을 씁니다. `FRONTEND_URL`의 스킴이 `https`이면 두 쿠키에 `Secure`를 붙이고, `http`이면 붙이지 않습니다. `APP_ENV`는 없앱니다.
- `FRONTEND_URL`은 스킴, 호스트, 포트만 담아야 하며, 끝에 `/`를 붙이지 않습니다. 스킴이 `http`이면 호스트가 `localhost`나 `127.0.0.1`일 때만 받아들입니다. 이 조건에 맞지 않으면 서버가 시작되지 않습니다.
- 이 결정은 ADR-025 가운데 "`Secure`는 `APP_ENV`가 `production`일 때에만 붙인다"는 부분을 대체합니다. 쿠키의 다른 속성은 ADR-025 그대로입니다.

**출처 확인**

- B안을 씁니다. `GET`, `HEAD`, `OPTIONS`를 뺀 모든 요청에서, `Origin` 헤더의 출처(스킴, 호스트, 포트)가 `FRONTEND_URL`과 같은지 확인합니다. `Origin`이 없으면 `Referer`의 출처로 확인하고, 둘 다 없거나 `Origin`이 `null`이면 거절합니다. 거절할 때에는 `403 ORIGIN_MISMATCH`를 응답합니다.
- 출처 확인은 관문보다 먼저, 앱의 모든 경로에 한 번에 겁니다. 공개 경로인 로그아웃도 예외가 아니며, 출처 확인을 끄는 설정은 두지 않습니다.
- 상태를 바꾸는 경로를 `GET`으로 만들지 않습니다. 예외는 Google 로그인의 두 경로뿐이며, 이 둘은 `state`, `nonce`, PKCE로 보호합니다.
- 규칙의 세부는 [API.md 2.4절](API.md#24-상태를-바꾸는-요청의-출처-확인)에 있습니다.

**로그인 상태의 수명**

- A안을 씁니다. 만료 시각은 로그인할 때 로그인 시각에 `LOGIN_SESSION_TTL_HOURS`를 더해 정하고, 로그인 상태를 써도 늘리지 않습니다.
- 다시 로그인에 성공했을 때 요청에 옛 `diegesis_session` 쿠키가 붙어 있으면, 그 쿠키의 행을 지운 다음 새 로그인 상태를 만듭니다.
- 로그인에 성공하면 그 사용자의 만료된 로그인 상태를 함께 지웁니다. 따로 도는 정리 작업은 두지 않습니다.
- 관문은 허용 목록에 그 사람이 들어간 시각(`allowed_emails.created_at`)보다 먼저 만든 로그인 상태를 받아들이지 않고, `401 NOT_AUTHENTICATED`를 응답합니다. 그래서 허용 목록에서 뺐다가 다시 넣은 사람은 다시 로그인해야 합니다.
- README의 허용 목록 SQL은 사람을 뺄 때 그 사람의 로그인 상태도 같은 트랜잭션에서 지웁니다.
- 이 결정은 ADR-024의 근거 가운데 "로그인 상태를 끊는 기능을 따로 두지 않아도 된다"는 부분을 대체합니다. 요청마다 허용 목록을 확인한다는 ADR-024의 결정은 그대로입니다.

**받아들이는 위험**

- 쿠키 이름에 `__Host-` 접두사를 붙이지 않습니다. 같은 사이트의 다른 서브도메인이 같은 이름의 쿠키를 심어 덮어쓸 수 있다는 위험을 받아들이고, 문제가 생기면 고칩니다.
- 유휴 만료를 두지 않습니다. 로그아웃하지 않고 버려진 기기의 로그인 상태는 최대 `LOGIN_SESSION_TTL_HOURS` 동안 유효합니다.

각 엔드포인트의 형식과 동작 순서는 [API.md 2.2절, 2.4절, 4.2절](API.md#42-로그인과-로그아웃)에, 스키마와 로그인 상태의 수명은 [ARCHITECTURE.md 6절](ARCHITECTURE.md#6-데이터-모델)에, 설정값은 [CONFIGURATION.md 3.1절](CONFIGURATION.md#31-서버)에 있습니다.

### 근거

- 사용자(백엔드 담당자)가 검토 결과를 반영하기로 했습니다. 이때 TTL은 줄이지 않고, 로그인 상태의 수명은 A안으로 하며, `__Host-` 접두사가 없는 위험은 받아들이고, 이메일과 `sub` 가운데 하나만 맞는 경우는 두 방향 모두 거부하기로 정했습니다.
- RFC 9700의 2.1.1절은 비밀값을 가진 클라이언트에도 PKCE를 권합니다. `state`는 로그인 CSRF를 막지만, 다른 곳에서 새어 나온 `code`를 공격자가 자기 브라우저의 흐름에 끼워 넣는 것은 막지 못합니다. PKCE를 쓰면 `code`가 그 흐름을 시작한 브라우저의 `code_verifier`에 묶입니다. 그리고 `nonce`는 ID 토큰을 그 흐름에 묶습니다. (작성자 판단)
- 세 값을 쿠키 하나에 담으면, 로그인을 시작하는 데 데이터베이스가 여전히 필요 없고, 결과를 받을 때 지울 쿠키도 하나뿐입니다. 쿠키는 HttpOnly이므로 페이지의 스크립트가 읽지 못합니다. (작성자 판단)
- OpenID Connect Core 1.0의 3.1.3.7절은 토큰 엔드포인트에서 TLS로 직접 받은 ID 토큰에 대해 서명 대신 TLS 서버 확인을 써도 된다고 합니다. 그래도 `iss`, `aud`, `exp`, `nonce`의 확인은 요구합니다. 서명을 확인하지 않으면 Google의 공개키를 받아 오지 않아도 되므로, 테스트가 네트워크에 기대지 않습니다. (작성자 판단)
- Google은 이메일 대신 `sub`를 사용자의 고유한 식별자로 쓰라고 안내합니다([OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)). `sub`는 Google 계정마다 다르고 다시 쓰이지 않지만, 이메일은 바뀌거나 다른 계정에 다시 쓰일 수 있습니다. 둘 가운데 하나만 맞는 경우를 모두 거부하면, 규칙이 하나이고 두 방향이 대칭이어서 구현과 테스트가 단순합니다. 허용 목록이 열 명 남짓이므로 드물게 생기는 경우는 SQL로 바로잡아도 됩니다. (작성자 판단)
- OWASP는 로그인 상태를 식별하는 값에 최소 64비트, 권장 128비트 이상의 엔트로피를 요구합니다. `secrets.token_urlsafe(32)`는 256비트이며, 43자는 RFC 7636이 정한 `code_verifier`의 최소 길이도 맞춥니다. 값을 만드는 곳이 한 함수이면 테스트로 모든 경로가 그 함수를 쓰는지 확인할 수 있습니다. (작성자 판단)
- 보안 속성은 따로 기억해서 켜야 하는 설정이 아니라 실제 주소에서 나와야 합니다. 운영 주소는 https이므로 `FRONTEND_URL`만 맞으면 `Secure`가 빠질 수 없습니다. 그리고 http를 localhost에만 허용하면, 운영 주소를 http로 잘못 적은 경우에도 서버가 시작되지 않습니다. (작성자 판단)
- 프론트엔드와 백엔드가 같은 출처를 쓰므로, 상태를 바꾸는 요청의 `Origin`은 언제나 `FRONTEND_URL`이어야 합니다. 요즘 브라우저는 `GET`과 `HEAD`가 아닌 요청에 `Origin`을 붙이므로 프론트엔드가 할 일이 없습니다. CSRF 토큰은 프론트엔드의 일을 늘리고, Fetch Metadata는 오래된 브라우저가 보내지 않습니다. (작성자 판단)
- 출처 확인을 경로마다 걸면 나중에 더한 경로에서 빠지기 쉽습니다. 앱 전체에 한 번에 걸고 끄는 설정을 두지 않으면, 이후 Epic의 경로도 따로 신경 쓰지 않아도 보호됩니다. (작성자 판단)
- 허용 목록에 들어간 시각과 비교하면, SQL을 실행한 사람이 로그인 상태를 지우는 단계를 빠뜨려도 옛 쿠키가 되살아나지 않습니다. 역할을 바꾸는 SQL은 `created_at`을 바꾸지 않으므로 로그인 상태가 끊기지 않습니다. (작성자 판단)
- 다시 로그인할 때 옛 행을 지우고 만료된 행을 함께 지우면, 정리 작업 없이도 사용자마다 남는 행이 실제로 쓰는 기기의 수 정도로 유지됩니다. (작성자 판단)
- `__Host-` 접두사가 막는 공격은 같은 사이트의 다른 서브도메인을 공격자가 다룰 수 있어야 가능합니다. 지금 그런 서브도메인을 둘 계획이 없습니다. 그리고 유휴 만료는 테스터들이 자기 기기로 쓰는 실사용 테스트에서 얻는 것에 비해 불편과 관문의 쓰기가 늘어납니다. (작성자 판단)

### 재검토 조건

- 같은 사이트 아래에 사용자가 올린 내용을 보여 주는 서브도메인이 생기거나, 쿠키를 덮어쓰는 문제가 확인되면 `__Host-` 접두사를 붙입니다.
- 공용 기기에서 쓰는 사람이 생기거나 테스트의 범위가 넓어지면, 유휴 만료(B안)를 더합니다.
- 프론트엔드의 호스팅이 `/api` 요청을 넘길 때 `Origin`을 바꾸거나 지우면, 출처 확인의 방식을 다시 정합니다. 배포를 연결하는 Epic(E2)에서 운영 주소의 로그아웃이 통과하는지로 확인합니다.
- 프론트엔드와 백엔드가 같은 출처를 쓰지 않게 되면([ADR-023](#adr-023-배포-인프라)의 재검토 조건), 출처 확인과 쿠키의 속성을 다시 정합니다.
- ID 토큰을 토큰 엔드포인트가 아닌 곳에서 받게 되면, 서명을 확인합니다.

## ADR-028: Google과 통신하는 방법

### 맥락

[ADR-009](#adr-009-데이터베이스-접근-도구와-개발-도구)는 Google 로그인 연동 도구로 Authlib을 적었지만, 그때에는 로그인 흐름의 세부가 정해지지 않았습니다. Epic 1을 설계하면서 [ADR-025](#adr-025-google-로그인-흐름의-세부)와 [ADR-027](#adr-027-로그인-흐름과-로그인-상태의-보안-보강)이 세부를 정했고, 그에 따라 Google 어댑터가 하는 일은 다음 세 가지가 되었습니다.

- 인가 주소를 만듭니다. 주소에는 `state`, `nonce`, 그리고 PKCE의 `code_challenge`(`S256`)를 붙입니다.
- Google의 토큰 엔드포인트에 `code`와 `code_verifier`를 보내 ID 토큰을 받습니다.
- ID 토큰의 클레임을 모두 확인합니다. 서명은 확인하지 않습니다(ADR-027).

그리고 테스트는 실제 Google에 요청하지 않아야 합니다([Epic 1 문서](backlog/epic-1/E1-login-allowlist.md)의 "못 박을 것").

### 후보 비교

| 기준 | A. Authlib | B. httpx로 직접 통신 |
| --- | --- | --- |
| 인가 주소와 PKCE | 라이브러리가 만든다 | 직접 만든다. 표준 라이브러리(`hashlib`, `base64`, `urllib.parse`)로 충분하다 |
| ID 토큰의 확인 | 기본 동작이 Google의 공개키를 받아 서명을 확인하므로, 서명을 확인하지 않으려면 그 동작을 피해 가야 한다. ADR-027이 정한 클레임은 어느 쪽이든 직접 확인해야 한다 | 처음부터 직접 확인한다 |
| 테스트에서 Google을 대신하는 방법 | httpx 기반의 클라이언트를 쓰면 가짜 전송을 끼울 수 있다 | httpx의 `MockTransport`로 가짜 전송을 끼운다 |
| 새로 들이는 의존성 | Authlib과 httpx | httpx. 이미 테스트 클라이언트로 쓰고 있다 |

### 결정

- B안을 씁니다. Google 어댑터(`app/adapters/google.py`)는 httpx로 토큰 엔드포인트와 통신하며, 인가 주소, PKCE, ID 토큰의 클레임 확인은 표준 라이브러리로 직접 구현합니다. Authlib은 쓰지 않습니다.
- httpx를 런타임 의존성으로 옮깁니다. 서버의 이미지는 개발 의존성을 설치하지 않기 때문입니다.
- 클레임을 빠짐없이 확인하는지는 라이브러리에 맡기지 않고 Epic 1의 테스트 케이스(TC-1.2.1부터 TC-1.2.8까지)로 확인합니다.
- 이 결정은 ADR-009의 "Google 로그인 연동: Authlib"을 대체합니다. ADR-009의 나머지 도구는 그대로입니다.

### 근거

- 사용자(백엔드 담당자)가 B안을 골랐습니다.
- ADR-027에 따라 서명은 확인하지 않고 클레임은 모두 직접 확인하므로, Authlib이 대신해 주는 일은 인가 주소를 만들고 토큰을 교환하는 정도입니다. 둘 다 몇 줄이면 되는 반면, Authlib을 쓰면 ID 토큰을 확인하는 기본 동작을 피해 가야 합니다. 기본값을 끄고 쓰는 코드는 라이브러리를 올릴 때 기본값이 바뀌어도 알아채기 어렵습니다. (작성자 판단)
- 직접 구현하면 어댑터가 보내는 요청과 확인하는 클레임이 코드에 그대로 드러나므로, 테스트 케이스와 한 줄씩 대조할 수 있습니다. (작성자 판단)
- httpx의 `MockTransport`를 쓰면 네트워크 없이 Google의 정상 응답, 오류 응답, 형식이 틀린 응답을 흉내 낼 수 있습니다. (작성자 판단)

### 재검토 조건

- Google 말고 다른 로그인 수단을 더하게 되면, 여러 제공자를 함께 다루는 라이브러리를 다시 검토합니다.
- ID 토큰을 토큰 엔드포인트가 아닌 곳에서 받게 되어 서명을 확인해야 하면(ADR-027의 재검토 조건), 서명 확인은 직접 구현하지 않고 검증된 라이브러리를 씁니다.

## ADR-029: 공통 층과 기능 폴더의 의존 방향

### 맥락

[ARCHITECTURE.md](ARCHITECTURE.md) 8절은 기능 폴더 안의 의존 순서(`router`, `service`, `repository`)와 "`service`는 포트에만 의존한다"는 것은 적었지만, 공통 층(`app/core/`)과 기능 폴더 사이의 방향은 적지 않았습니다. Epic 1을 구현하면서 두 가지가 생겼습니다.

- 관문(`app/core/gate.py`)이 로그인 상태를 찾으려고 `app/auth/repository.py`의 `AuthRepository`와 레코드를 직접 import했습니다.
- `app/auth/service.py`가 레코드(`AllowedEmail`, `UserRecord`)를 `app/auth/repository.py`에서 가져와, `service`가 포트가 아니라 저장소의 구현에 기댔습니다.

관문은 앞으로 더할 기능 폴더(`books`, `music` 등)의 라우터가 모두 씁니다. 그래서 관문이 auth를 import하면 모든 기능 폴더가 공통 층을 거쳐 auth에 묶입니다. Epic 1의 1차 리뷰가 이 점을 지적했습니다(`phases/1-login-allowlist/review/review-1.md`의 ARC-4).

### 후보 비교

| 기준 | A. 포트로 바꾼다 | B. 지금 구조를 기록만 한다 | C. 관문을 `app/auth/`로 옮긴다 |
| --- | --- | --- | --- |
| 공통 층의 방향 | 기능 폴더를 import하지 않는다 | 관문만 auth를 import한다 | 공통 층은 깨끗하지만, 다른 기능 폴더의 라우터가 `app.auth`를 import한다 |
| `service`의 어긋남 | 레코드를 포트에 두므로 함께 풀린다 | 남는다 | 남는다 |
| 바꾸는 양 | 레코드와 포트를 옮기고 `create_app()`에서 잇는다 | 없다 | 관문과 그 테스트를 옮긴다 |

### 결정

- A안을 씁니다. 공통 층(`app/core/`)은 기능 폴더와 어댑터를 import하지 않습니다.
- 관문은 `LoginLookup` 포트(`app/core/ports.py`)로 로그인 상태를 찾습니다. 그 구현체는 `AuthRepository`이며, `create_app()`이 요청의 데이터베이스 세션으로 만드는 함수를 넣습니다(`set_login_lookup_factory`).
- 공통 층과 기능 폴더의 `service`가 함께 쓰는 저장소의 레코드(`AllowedEmail`, `UserRecord`, `ActiveLogin`)는 `app/core/ports.py`에 둡니다. `service`는 레코드도 포트에서 가져오며 `repository`를 import하지 않습니다.
- 이 방향은 테스트(`tests/core/test_dependency_direction.py`, `tests/auth/test_service.py`)로 확인합니다.

### 근거

- 사용자(백엔드 담당자)가 A안을 골랐습니다.
- 관문은 모든 기능 폴더가 쓰는 공통 부품이므로, 특정 기능 폴더에 기대지 않아야 기능 폴더 사이의 의존이 생기지 않습니다. (작성자 판단)
- 신원 제공자를 `set_identity_provider_factory`로 넣는 방식과 같은 방식이라, 조립을 아는 곳이 `app/main.py` 하나로 남습니다. (작성자 판단)

### 재검토 조건

- 로그인 상태를 데이터베이스가 아닌 곳(예: 전용 세션 저장소)에 두게 되면, `LoginLookup`의 구현체만 바꾸면 되는지 다시 확인합니다.

## ADR-030: 로그인 경로가 저장에 실패할 때와 쿠키를 지울 때의 응답

### 맥락

Epic 1의 1차 리뷰에서 문서와 구현이 어긋난 두 곳이 나왔습니다(`phases/1-login-allowlist/review/review-1.md`, `fix-1.md`).

- [Epic 1 문서](backlog/epic-1/E1-login-allowlist.md)의 S1.3은 로그인 결과 처리가 "어떤 경우에도 500으로 끝나지 않는다"고 적었습니다. 그런데 성공했을 때의 쓰기는 요청 하나의 트랜잭션이며 응답을 보내기 전에 커밋합니다. 그래서 데이터베이스 장애로 커밋이 실패하면 `500`으로 끝나고 로그인 상태의 쿠키를 심지 않습니다. 저장되지 않은 로그인 상태의 쿠키를 주면 사용자는 로그인한 줄 알지만 다음 요청에서 `401`을 받기 때문입니다. 같은 사람의 첫 로그인 두 개가 겹쳐 고유 제약에 부딪히는 경우는 리뷰의 처분에서 고쳐 `500`이 아니게 되었습니다.
- [API.md](API.md) 4.2절은 로그아웃이 쿠키를 지우는 헤더를 `diegesis_session=; Max-Age=0; Path=/`로 적었지만, 구현은 심을 때와 같은 속성(`HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=0`, `FRONTEND_URL`이 https이면 `Secure`)을 붙입니다. 브라우저는 이름과 경로가 같은 쿠키를 지우므로 두 표기의 동작은 같습니다.

### 후보 비교

| 문제 | 후보 | 비교 |
| --- | --- | --- |
| 커밋이 실패할 때 | A. `500`으로 끝내고 Epic 문서에 예외로 적는다 | 트랜잭션의 경계(`get_db_session`)를 그대로 둔다. 인프라의 장애가 오류로 드러난다 |
| | B. `/login?error=LOGIN_FAILED`로 보낸다 | 사용자는 날것의 오류 화면을 보지 않지만, 라우터가 커밋을 직접 해야 하고 장애가 로그인 실패와 섞인다 |
| 쿠키를 지우는 헤더 | A. API.md의 예시를 구현에 맞춘다 | 심을 때와 같은 속성으로 지우는 구현을 그대로 둔다. API.md가 바뀌므로 프론트엔드의 리뷰를 받는다 |
| | B. 구현을 예시대로 줄인다 | 프론트엔드의 리뷰가 필요 없지만, 구현과 테스트를 바꾼다 |

### 결정

- 로그인 결과 처리는 요청과 Google의 응답이 어떻든 성공, `NOT_ALLOWED`, `LOGIN_FAILED` 가운데 하나로 끝납니다. 예외는 데이터베이스에 닿지 못하거나 쓰기를 커밋하지 못한 경우 하나이며, 이때에는 `500 INTERNAL_ERROR`로 끝나고 로그인 상태의 쿠키를 심지 않습니다.
- 로그아웃은 로그인 상태의 쿠키를 심을 때와 같은 이름, 경로, 속성에 `Max-Age=0`을 붙여 지웁니다. API.md 4.2절의 로그아웃 예시를 이에 맞춥니다. `diegesis_oauth_state`를 지우는 헤더는 같은 절의 로그인 결과 처리 예시대로 둡니다.

### 근거

- 사용자(백엔드 담당자)가 두 문제 모두 A안을 골랐습니다.
- 데이터베이스의 장애는 사용자가 다시 시도해서 풀리는 로그인 실패와 다르므로, 오류로 드러나 로그에 남는 편이 원인을 찾기 쉽습니다. (작성자 판단)
- 쿠키를 심을 때와 같은 속성으로 지우면, 속성에 따라 쿠키를 구별하는 브라우저의 동작이 바뀌더라도 지우는 헤더가 심은 쿠키와 맞습니다. (작성자 판단)

### 재검토 조건

- 로그인 결과 처리에서 `500`이 실제로 자주 나면, 사용자에게 보여 줄 화면을 프론트엔드와 함께 다시 정합니다.
