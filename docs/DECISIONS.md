# DECISIONS

이 문서는 기술 선택이 아닌 결정, 곧 제품의 범위와 운영 방식에 관한 결정을 기록합니다. 기술적 결정은 [ADR.md](ADR.md)에 따로 기록하며, 낯선 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에 있습니다.

새 결정이 생기면 가장 아래에 날짜와 함께 추가합니다. 그리고 이전 결정을 뒤집을 때에는 기존 기록을 지우지 않고, 새 기록에 "어떤 결정을 대체하는지"를 적습니다.

## 2026-11-22: 백엔드 설계 인터뷰에서 정한 것

백엔드 아키텍처를 설계하면서 백엔드 담당자(강래우)가 내린 결정입니다. 팀 전체의 합의가 필요한 항목은 이 문서의 마지막 절에 따로 모아 두었습니다.

### 제품의 범위

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-01 | MVP에서 읽을 수 있는 책은 팀이 미리 준비한 책으로 한정합니다. 일반 사용자는 책을 올릴 수 없습니다. | 11월 17일 회의에서 테스트용 책을 『노르웨이의 숲』의 일부 챕터와 AI로 합성한 소설로 정했기 때문입니다. |
| D-02 | 팀원이 새 책과 음악을 추가할 수 있도록 관리자용 업로드 기능을 둡니다. 이때 올리는 것은 원본 책이 아니라 AI 레포가 분석을 마친 산출물 묶음입니다. | 서버에 AI 모델을 두지 않기 위해서입니다. 원본 책을 올리면 서버가 자동으로 분석하는 기능은 2차 마일스톤의 후보로 남깁니다. |
| D-03 | 같은 결정이 [ADR-005](ADR.md#adr-005-프론트엔드와의-api-연동-방식)에 있습니다. | 기술적 결정이어서 2026-11-24에 이 문서에서는 내용을 지웠습니다. |
| D-04 | 곡을 재생할 때에는 곡의 맨 앞이 아니라, 장면과 맞아떨어진 구간이 시작하는 위치부터 틉니다. | 음악을 구간으로 나누어 임베딩하고 저장하므로, 장면과 맞는다고 판단한 대상이 곡 전체가 아니라 그 구간이기 때문입니다. |
| D-44 | 1차 MVP에서는 적재한 곡을 골라서 비활성화하는 기능을 만들지 않습니다. 음악 묶음을 다시 올리는 동작([AI_CONTRACT.md 6절](AI_CONTRACT.md#6-같은-것을-다시-올릴-때))은 그대로 둡니다. | 백엔드 담당자가 2026-11-24에 1차 MVP의 범위에서 뺐습니다. 이전 설계에서는 곡을 지우는 대신 관리자 API로 비활성화하기로 했었습니다. |

| D-11 | 선곡 방식(무음, 무작위 선곡, 우리 선곡)과 임베딩 모델(MuQ-MuLan, LAION-CLAP)을 사용자가 설정 화면에서 직접 바꿔 가며 비교할 수 있게 합니다. (2026-11-24에 D-49가 대체했습니다.) | 리서치 문서들이 이 비교를 제안했고, 백엔드 담당자가 사용자가 직접 비교하는 방식을 제안했습니다. |
| D-12 | 사용자가 한 번 중단한 곡은 그 사용자에게 다시 나오지 않습니다. 반면에 이전에 이미 나온 곡은 따로 제외하지 않습니다. (앞 문장은 2026-11-24에 D-46이 대체했습니다.) | 앞의 내용은 PRD의 요구사항이고, 뒤의 내용은 백엔드 담당자의 결정입니다. |
| D-24 | 곡을 중단했을 때 시작되는 자동 재생 쉬는 시간은 사용자와 책의 쌍마다 따로 적용합니다. 한 책에서 중단하더라도 다른 책에는 영향을 주지 않습니다. (2026-11-24에 D-47이 대체했습니다.) | 백엔드 담당자가 정했습니다. |
| D-25 | MVP에서는 다음 세 가지를 만들지 않습니다. 만료된 음원 주소를 다시 발급하는 API, 임베딩 모델을 관리하는 관리자 API, 그리고 고를 수 있는 선곡 방식을 조회하는 API와 실제 이름을 가리는 표시 이름입니다. | 지금 단계에서는 꼭 필요한 것만 담기로 백엔드 담당자가 정했습니다. 임베딩 모델은 산출물 묶음을 적재할 때 자동으로 등록합니다. |

## 2026-11-22: 개발 절차에 관해 정한 것

구현을 시작하기 전에 작업하는 틀을 정하면서 백엔드 담당자(강래우)가 내린 결정입니다. 여기에는 결정과 이유만 적으며, 절차와 규칙의 내용은 [HARNESS.md](HARNESS.md)와 [DEVELOPMENT.md](DEVELOPMENT.md)에 있습니다.

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-26 | 구현은 harness로 진행합니다. harness는 OnlineFourCut 프로젝트에서 쓰던 것을 이 레포의 기술스택에 맞춰 옮긴 것입니다. | 백엔드 담당자가 이전 프로젝트에서 써 본 틀이기 때문입니다. 작업을 작게 나누고, 구현과 판정을 서로 다른 에이전트 세션에 맡기는 구조를 그대로 가져옵니다. |
| D-27 | 작업의 단위는 Epic이며, Epic 하나를 레포 안의 Epic 문서 하나와 GitHub 이슈 하나로 함께 관리합니다. | 팀은 GitHub 이슈와 주차별 마일스톤으로 일정을 보고, 에이전트와 리뷰는 레포 안의 문서를 근거로 삼기 때문입니다. |
| D-28 | harness로 돌리는 작업의 브랜치는 `feat-<phase 이름>`으로 짓습니다. `main`에는 PR로만 합치며, 합칠 때에는 merge commit 방식을 씁니다. | `main`에 합쳐지면 배포되므로([ADR-010](ADR.md#adr-010-배포-방식)) PR이 배포 앞의 관문이 됩니다. squash 방식을 쓰지 않는 이유는 테스트를 먼저 썼다는 증거인 RED 커밋을 `main`의 이력에 남기기 위해서입니다. OnlineFourCut에서 하던 로컬 머지와 태그 배포는 옮기지 않았습니다. |
| D-29 | 사람 없이 띄우는 에이전트 세션의 모델은 `claude-opus-5-5`로 하며, 환경 변수 `HARNESS_MODEL`로 바꿀 수 있게 합니다. | step의 수만큼 에이전트 세션이 뜨므로 비용에 직접 영향을 주는 값이어서 기록해 둡니다. |
| D-30 | 커밋 메시지는 `종류(범위): 설명`의 형태로 쓰고, harness가 만드는 커밋의 형식은 OnlineFourCut의 것을 그대로 씁니다. | 지금까지 이 레포에서 써 온 `종류: 한국어 설명`의 형태와 어긋나지 않고, harness의 실행기를 고치지 않아도 되기 때문입니다. |
| D-31 | harness를 옮기면서 검사 도구(uv, ruff, pyright, pytest)의 설정만 함께 만들었습니다. 서버의 코드, 데이터베이스, Docker, Alembic은 첫 Epic에서 harness로 만듭니다. | 가드와 검사 명령을 실제로 돌려 보려면 검사 도구가 있어야 하기 때문입니다. 쓰는 코드가 없는 의존성은 검증할 수 없으므로 넣지 않았습니다. 도구의 버전은 `pyproject.toml`과 `uv.lock`에 있습니다. |
| D-32 | 작업은 phase마다 Orca로 새로 만든 worktree에서 진행합니다. | 여러 작업이 서로 섞이지 않게 하고, 사람 없이 도는 작업이 어디에서 돌고 있는지를 Orca의 사이드패널에서 볼 수 있게 하기 위해서입니다. |
| D-33 | 리뷰가 찾은 결함의 처분은 리뷰에 이어서 사람 없이 진행합니다. 다만 검사를 느슨하게 만드는 것, 결정을 맡은 문서를 코드에 맞춰 고치는 것처럼 판단이 필요한 일은 사람에게 넘깁니다. | OnlineFourCut에서는 사람이 대화하며 처분했습니다. 이 과정을 자동으로 진행하도록 백엔드 담당자가 정했습니다. |
| D-34 | 사람이 직접 확인하는 항목(MANUAL 점검표)에는 사람만 확인할 수 있는 것만 적고, 테스트로 확인할 수 있는 것은 테스트로 만듭니다. | 백엔드 담당자가 정했습니다. 사람이 한 번 확인한 것은 다음 변경에서 다시 깨져도 알 수 없지만, 테스트는 매번 확인하기 때문입니다. |
| D-35 | `main` 브랜치에는 직접 push하지 않습니다. PR을 합치기 전에 필요한 승인 인원은 두지 않습니다. | 이 레포는 백엔드 담당자 혼자 관리하므로 승인해 줄 다른 사람이 없기 때문입니다. 그 대신 PR을 올리기 전의 점검과 리뷰가 관문의 역할을 합니다. |

## 2026-11-24: 프론트엔드와의 API·마일스톤 회의에서 정한 것

백엔드 담당자(강래우)와 프론트엔드 담당자가 회의에서 정한 결정과, 회의록에서 서로 어긋난 부분을 백엔드 담당자가 정리한 결정입니다. 회의록은 팀의 Confluence에 있으며, 회의에서 정한 결정은 회의록의 Decisions 절에 있습니다. 이 회의에서 나온 기술적 결정은 [ADR.md](ADR.md)의 ADR-020부터 ADR-023까지에 따로 기록했습니다.

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-45 | 1차 MVP의 실사용 테스트 일정을 정합니다. 2026-12-18(금)에 기능을 동결하고, 12월 19일부터 20일까지 내부 시험을 하여 20일까지 실데이터로 자체 테스트를 끝내며, 21일부터 27일까지 실사용 테스트를, 28일부터 29일까지 정리를 합니다. 날짜는 [PRD.md](PRD.md)의 마일스톤에 있습니다. | PRD의 1차 마일스톤 기간 안에서 테스트 기간을 확보하기 위해서입니다. 평가 자료를 내보내는 기능(E9)은 관리자만 쓰므로, 동결일 뒤에 만들어도 된다고 보았습니다. |
| D-46 | 재생 중인 곡에 좋아요와 싫어요 버튼을 둡니다. 싫어요를 누른 구간은 그 사용자에게 다시 나오지 않습니다. 싫어요를 눌러도 음악을 멈추지 않고 그 장면의 다른 후보를 틀며, 후보를 모두 싫어요로 넘기면 그 페이지에서는 음악을 틀지 않고 다음 페이지에서 다시 틉니다. 일시정지는 싫어요로 보지 않으며 기록하지도 않습니다. 이 결정은 D-07 가운데 중단에 관한 부분, D-08, 그리고 D-12의 앞 문장을 대체합니다. D-12의 뒤 문장(이미 나온 곡은 제외하지 않는다)은 그대로입니다. | 회의에서 "음악을 일시정지하는 것을 이 노래가 싫다는 표시로 볼 수는 없다"는 의견이 나와서, 싫다는 표시는 싫어요 버튼으로만 받기로 했습니다. 싫어요를 누르면 K개의 후보 가운데 다른 곡을 틀고, K번 모두 누르면 다음 위치 알림까지 틀지 않는다는 것도 회의에서 정했습니다. 제외하는 단위를 곡이 아니라 구간으로 정한 것은 회의록의 완료 조건("싫어요를 누른 음악 구간은 다음 샘플링에서 제외")을 따른 백엔드 담당자의 결정입니다. |
| D-47 | 자동 재생 쉬는 시간을 두지 않습니다. 이 결정은 D-24와, PRD의 "중단한 뒤 일정 시간 동안 자동으로 재생하지 않는다"를 대체합니다. | 싫어요를 누르면 다른 후보를 트는 방식(D-46)으로 바꾸면서 곡을 멈추고 기다리는 시간이 필요 없어졌습니다. 회의록의 일정표에는 쉬는 시간이 남아 있었지만, 같은 회의록의 결정 표가 "쉬는 시간은 없다"고 정했으므로 결정 표를 따랐습니다. |
| D-48 | 곡은 후보 구간의 시작부터 끝까지만 재생하고, 구간이 끝나면 멈춥니다. 그 뒤에는 다음 페이지에서 다시 곡이 나옵니다. | 회의에서 정했습니다. MVP 테스트 뒤에 개선이 필요하다고 판단되면, 곡을 끝까지 틀지, 장면과 비슷한 다른 구간을 이어서 틀지를 그때 정합니다. |
| D-49 | 선곡 방식은 장면에 맞춘 선곡(임베딩) 하나로 고정하고, 사용자는 설정 화면에서 등록된 임베딩 모델 가운데 하나만 고릅니다. 설정 화면(E8)은 MVP에 포함하며, 홈 화면에서 들어갑니다. 이 결정은 D-11을 대체합니다. | 회의에서 "E8에는 모델 설정만 남기고 선곡 방식의 설정은 주지 않는다. 모든 사용자에게 음악을 틀어 주되, 임베딩 모델의 차이만 둔다"고 정했습니다. 회의록의 일정표에는 E8이 "MVP에서 제외될 수도 있다"와 "밀려도 줄이지 않는다"가 함께 남아 있었지만, Decisions 절의 결정을 따릅니다. 무음과 무작위 선곡과의 비교는 MVP에서 하지 않고, 임베딩 모델끼리의 비교만 합니다. |
| D-50 | 관리자 화면은 프론트엔드가 꾸미지 않은 간단한 화면으로 만듭니다. 묶음 적재, 허용 목록, 평가 자료 내보내기를 이 화면에서 다룹니다. (허용 목록에 관한 부분은 2026-11-25에 D-54가 대체했습니다.) | 회의록의 결정 칸("MVP에서는 만들지 않고 Swagger UI와 curl로 다룬다")과 항목 칸("꾸미지 않은 간단한 UI로 만든다")이 서로 반대여서 백엔드 담당자가 정했습니다. 관리자 API는 그대로이므로 백엔드의 범위는 바뀌지 않습니다. |
| D-51 | 프론트엔드와의 협업 절차를 정합니다. API의 세부 계약과 내부 동작은 미리 모두 정해 두지 않고, 지금의 큰 틀 안에서 Epic마다 세부를 정하고 상의한 뒤 구현합니다. 기능 하나는 백엔드의 Epic과 프론트엔드의 이슈 한 쌍이고, API 계약은 [API.md](API.md)에만 적으며, 계약을 바꾸는 PR은 구현보다 먼저 올려 프론트엔드 담당자가 리뷰합니다. 절차의 내용은 [DEVELOPMENT.md](DEVELOPMENT.md#64-프론트엔드와의-협업) 6.4절에 있습니다. PR을 합칠 때 승인 인원을 두지 않는다는 D-35는 그대로입니다. | Epic마다 세부를 정한다는 것은 회의에서 정했습니다(애자일 원칙). 회의록은 계약을 Epic 문서와 API.md에 함께 적자고 했지만, 한 정보를 한 문서에만 적는다는 D-20에 맞추어 계약은 API.md에만 두고 Epic 문서는 그 절을 가리키기로 백엔드 담당자가 정했습니다. |
| D-52 | 산출물 묶음의 규격([AI_CONTRACT.md](AI_CONTRACT.md#7-ai팀과-합의할-것) 7절)은 2026-12-14까지 AI팀과 합의하고, 같은 날까지 실제 책 묶음과 음악 묶음을 받습니다. | 기능 동결(D-45) 전에 실제 묶음으로 적재와 선곡을 확인하기 위해서입니다. 그 전에는 프론트엔드 목에 있는 견본으로 만든 예시 묶음을 씁니다. |
| D-53 | Google 로그인의 테스터는 실사용 테스트 직전에 인원을 확정한 뒤 Google 콘솔에서 직접 등록합니다. 로그인은 배포를 연결하는 Epic(E2) 전에는 로컬에서, 그 뒤에는 로컬과 운영 주소에서 동작하게 합니다. 그리고 프론트엔드는 E2 전에는 로컬에서 docker compose로 띄운 백엔드와 예시 묶음을 쓰고, E2 뒤에는 배포된 백엔드도 씁니다.
