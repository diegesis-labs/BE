# DECISIONS

이 문서는 기술 선택이 아닌 결정, 곧 제품의 범위와 운영 방식에 관한 결정을 기록합니다. 기술적 결정은 [ADR.md](ADR.md)에 따로 기록하며, 낯선 용어의 뜻은 [GLOSSARY.md](GLOSSARY.md)에 있습니다.

새 결정이 생기면 가장 아래에 날짜와 함께 추가합니다. 그리고 이전 결정을 뒤집을 때에는 기존 기록을 지우지 않고, 새 기록에 "어떤 결정을 대체하는지"를 적습니다.

## 2026-11-22: 백엔드 설계 인터뷰에서 정한 것

백엔드 아키텍처를 설계하면서 백엔드 담당자(강래우)가 내린 결정입니다. 팀 전체의 합의가 필요한 항목은 이 문서의 마지막 절에 따로 모아 두었습니다.

### 제품의 범위

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-01 | MVP에서 읽을 수 있는 책은 팀이 미리 준비한 책으로 한정합니다. 일반 사용자는 책을 올릴 수 없습니다. | 11월 17일 회의에서 테스트용 책을 『노르웨이의 숲』의 일부 챕터와 AI로 합성한 소설로 정했기 때문입니다. |
| D-02 | 팀원이 새 책과 음악을 추가할 수 있도록 관리자용 업로드 기능을 둡니다. 이때 올리는 것은 원본 책이 아니라 AI 레포가 분석을 마친 산출물 묶음입니다. | 서버에 AI 모델을 두지 않기 위해서입니다. 원본 책을 올리면 서버가 자동으로 분석하는 기능은 2차 마일스톤의 후보로 남깁니다. |
| D-03 | 책의 본문은 EPUB 파일이 아니라 문장 번호가 붙은 구조화된 데이터로 제공합니다. | 테스트용 책의 원본이 사진 스캔본과 합성한 글이어서 EPUB이 아니고, 장면의 경계가 문장 단위로 정해지기 때문입니다. |
| D-04 | 곡을 재생할 때에는 곡의 맨 앞이 아니라, 장면과 맞아떨어진 구간이 시작하는 위치부터 틉니다. | 음악을 구간으로 나누어 임베딩하고 저장하므로, 장면과 맞는다고 판단한 대상이 곡 전체가 아니라 그 구간이기 때문입니다. |

### 접근 권한

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-05 | 사용자는 Google 계정으로 로그인합니다. | 백엔드 담당자가 선택했습니다. |
| D-06 | 허용 목록에 이메일이 등록된 사람만 서비스를 쓸 수 있습니다. | 테스트용 책에 저작권이 있는 소설이 포함되어 있어서, 아무나 본문을 볼 수 있어서는 안 되기 때문입니다. |

### 평가와 피드백

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-07 | 앱 안에서는 사용자의 행동 기록(어떤 장면에 어떤 곡이 나갔고 언제 중단했는지), 중단, 곡별 좋아요를 수집합니다. | PRD의 중단 버튼에 좋아요를 더한 범위입니다. |
| D-08 | "싫어요" 버튼은 따로 두지 않고, 중단을 싫어요로 간주합니다. | 독서 중에 조작해야 할 것을 늘리지 않기 위해서입니다. |
| D-09 | 몰입감이나 어울림에 관한 설문은 앱 밖에서 진행합니다. | 앱 안의 설문 기능은 MVP의 범위를 넘기 때문입니다. |
| D-10 | 앱 밖의 설문과 앱 안의 기록은 사용자의 Google 이메일로 연결합니다. 그러므로 설문에서도 같은 이메일을 받아야 합니다. | 설문 응답과 실제 청취 기록을 함께 분석하기 위해서입니다. (문서 작성자의 제안) |
| D-11 | 선곡 방식(무음, 무작위 선곡, 우리 선곡)과 임베딩 모델(MuQ-MuLan, LAION-CLAP)을 사용자가 설정 화면에서 직접 바꿔 가며 비교할 수 있게 합니다. | 리서치 문서들이 이 비교를 제안했고, 백엔드 담당자가 사용자가 직접 비교하는 방식을 제안했습니다. |
| D-12 | 사용자가 한 번 중단한 곡은 그 사용자에게 다시 나오지 않습니다. 반면에 이전에 이미 나온 곡은 따로 제외하지 않습니다. | 앞의 내용은 PRD의 요구사항이고, 뒤의 내용은 백엔드 담당자의 결정입니다. |
| D-24 | 곡을 중단했을 때 시작되는 자동 재생 쉬는 시간은 사용자와 책의 쌍마다 따로 적용합니다. 한 책에서 중단하더라도 다른 책에는 영향을 주지 않습니다. | 백엔드 담당자가 정했습니다. |
| D-25 | MVP에서는 다음 세 가지를 만들지 않습니다. 만료된 음원 주소를 다시 발급하는 API, 임베딩 모델을 관리하는 관리자 API, 그리고 고를 수 있는 선곡 방식을 조회하는 API와 실제 이름을 가리는 표시 이름입니다. | 지금 단계에서는 꼭 필요한 것만 담기로 백엔드 담당자가 정했습니다. 임베딩 모델은 산출물 묶음을 적재할 때 자동으로 등록합니다. |

### 프로젝트의 운영

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-13 | 이 프로젝트는 포트폴리오용이며, 현재 창업 계획은 없습니다. | 인프라 비용과 기술 선택의 기준이 되므로 기록해 둡니다. |
| D-14 | 백엔드는 Docker 컨테이너로 배포하며, 구체적인 인프라는 프론트엔드와 상의한 뒤에 정합니다. | 배포 환경은 프론트엔드와 함께 정해야 하기 때문입니다. GCP 무료 계정을 옮겨 가며 쓰는 방식이 후보로 언급됐습니다. |
| D-15 | 모델 학습에 관해서는 10월 18일 회의의 "오픈소스 모델을 우리 상황에 맞게 학습시킨다"보다 11월 17일 회의의 "학습은 MVP의 범위가 아니다"를 따릅니다. | 두 회의록의 내용이 서로 달라서, 더 최근의 결정을 기준으로 삼았습니다. |
| D-21 | 음원 파일은 백엔드가 미리 발급한 서명된 주소(presigned URL)로만 받을 수 있게 합니다. 오브젝트 저장소는 비공개로 둡니다. | 백엔드 담당자가 정했습니다. 음원의 라이선스나 다른 팀과의 협의와 관계없이 당연히 지켜야 하는 규칙으로 봅니다. |
| D-22 | 현재로서는 퍼블릭 도메인이거나 저작권의 제약이 없는 음원만 씁니다. | 백엔드 담당자가 밝힌 현재의 방침입니다. 방침이 바뀌면 이 항목을 고칩니다. |
| D-23 | 코드가 `main` 브랜치에 합쳐지면 자동으로 컨테이너 이미지를 만들어 배포하며, 이미지는 Docker Hub에 저장합니다. 아직 만들지는 않았습니다. | 백엔드 담당자가 정했습니다. |

## 2026-11-22: 개발 절차에 관해 정한 것

구현을 시작하기 전에 작업하는 틀을 정하면서 백엔드 담당자(강래우)가 내린 결정입니다. 여기에는 결정과 이유만 적으며, 절차와 규칙의 내용은 [HARNESS.md](HARNESS.md)와 [DEVELOPMENT.md](DEVELOPMENT.md)에 있습니다.

| 번호 | 결정 | 배경과 이유 |
| --- | --- | --- |
| D-26 | 구현은 harness로 진행합니다. harness는 OnlineFourCut 프로젝트에서 쓰던 것을 이 레포의 기술스택에 맞춰 옮긴 것입니다. | 백엔드 담당자가 이전 프로젝트에서 써 본 틀이기 때문입니다. 작업을 작게 나누고, 구현과 판정을 서로 다른 에이전트 세션에 맡기는 구조를 그대로 가져옵니다. |
| D-27 | 작업의 단위는 Epic이며, Epic 하나를 레포 안의 Epic 문서 하나와 GitHub 이슈 하나로 함께 관리합니다. | 팀은 GitHub 이슈와 주차별 마일스톤으로 일정을 보고, 에이전트와 리뷰는 레포 안의 문서를 근거로 삼기 때문입니다. |
| D-28 | harness로 돌리는 작업의 브랜치는 `feat-<phase 이름>`으로 짓습니다. `main`에는 PR로만 합치며, 합칠 때에는 merge commit 방식을 씁니다. | `main`에 합쳐지면 배포되므로(D-23) PR이 배포 앞의 관문이 됩니다. squash 방식을 쓰지 않는 이유는 테스트를 먼저 썼다는 증거인 RED 커밋을 `main`의 이력에 남기기 위해서입니다. OnlineFourCut에서 하던 로컬 머지와 태그 배포는 옮기지 않았습니다. |
| D-29 | 사람 없이 띄우는 에이전트 세션의 모델은 `claude-opus-5-5`로 하며, 환경 변수 `HARNESS_MODEL`로 바꿀 수 있게 합니다. | step의 수만큼 에이전트 세션이 뜨므로 비용에 직접 영향을 주는 값이어서 기록해 둡니다. |
| D-30 | 커밋 메시지는 `종류(범위): 설명`의 형태로 쓰고, harness가 만드는 커밋의 형식은 OnlineFourCut의 것을 그대로 씁니다. | 지금까지 이 레포에서 써 온 `종류: 한국어 설명`의 형태와 어긋나지 않고, harness의 실행기를 고치지 않아도 되기 때문입니다. |
| D-31 | harness를 옮기면서 검사 도구(uv, ruff, pyright, pytest)의 설정만 함께 만들었습니다. 서버의 코드, 데이터베이스, Docker, Alembic은 첫 Epic에서 harness로 만듭니다. | 가드와 검사 명령을 실제로 돌려 보려면 검사 도구가 있어야 하기 때문입니다. 쓰는 코드가 없는 의존성은 검증할 수 없으므로 넣지 않았습니다. 도구의 버전은 `pyproject.toml`과 `uv.lock`에 있습니다. |
| D-32 | 작업은 phase마다 Orca로 새로 만든 worktree에서 진행합니다. | 여러 작업이 서로 섞이지 않게 하고, 사람 없이 도는 작업이 어디에서 돌고 있는지를 Orca의 사이드패널에서 볼 수 있게 하기 위해서입니다. |
| D-33 | 리뷰가 찾은 결함의 처분은 리뷰에 이어서 사람 없이 진행합니다. 다만 검사를 느슨하게 만드는 것, 결정을 맡은 문서를 코드에 맞춰 고치는 것처럼 판단이 필요한 일은 사람에게 넘깁니다. | OnlineFourCut에서는 사람이 대화하며 처분했습니다. 이 과정을 자동으로 진행하도록 백엔드 담당자가 정했습니다. |
| D-34 | 사람이 직접 확인하는 항목(MANUAL 점검표)에는 사람만 확인할 수 있는 것만 적고, 테스트로 확인할 수 있는 것은 테스트로 만듭니다. | 백엔드 담당자가 정했습니다. 사람이 한 번 확인한 것은 다음 변경에서 다시 깨져도 알 수 없지만, 테스트는 매번 확인하기 때문입니다. |
| D-35 | `main` 브랜치에는 직접 push하지 않습니다. PR을 합치기 전에 필요한 승인 인원은 두지 않습니다. | 이 레포는 백엔드 담당자 혼자 관리하므로 승인해 줄 다른 사람이 없기 때문입니다. 그 대신 PR을 올리기 전의 점검과 리뷰가 관문의 역할을 합니다. |
