# Phase 리뷰

phase 하나가 끝났을 때 "다음 Epic이 이 위에 쌓여도 되는가"를 판정한다. 판정은 5개 차원으로 갈라 각각 sub-agent가 맡고, orchestrator는 **실측·오탐 기각·병합·리포트**를 든다.

이 스킬은 OnlineFourCut의 `phase-review`를 옮긴 것이다. 본문의 "Epic 0" 같은 사례는 원본 프로젝트에서 실제로 있었던 일이다.

차원을 가르는 이유: 한 세션이 2,800줄을 훑으며 버그·권한·구조·테스트·의도를 동시에 보면 전부 얕아진다. 각 차원은 자기 렌즈로만 diff 전체를 본다.

**orchestrator는 코드를 수정하지 않는다. sub-agent에게도 수정을 허용하지 않는다.** 리뷰와 수정이 한 세션에 섞이면 무엇이 판정이고 무엇이 변경인지 구분이 사라져, 리포트가 "고쳤으니 없는 문제"를 적게 된다. 산출물은 리포트 한 장뿐이다. 고치는 것은 `review-fix` 스킬의 일이고, 다른 세션에서 한다.

## 1. 대상 확정

**task 이름** — 인자로 받은 것 → 없으면 현재 브랜치 `feat-{task}`에서 유추 → `phases/index.json`에 그 `dir`이 있는지 확인.

**diff 범위** — `main...HEAD`.

```bash
git rev-parse --abbrev-ref HEAD
git diff --stat main...HEAD
git log --oneline main...HEAD
```

`main...HEAD`가 비어 있으면(이미 머지된 phase) 멈추고 사용자에게 범위를 묻는다. 추측한 범위로 리뷰하면 판정 대상이 실제 변경과 어긋난다.

**라운드 번호** — `phases/{task}/review/`의 `review-*.md` 중 최대값 + 1. 디렉터리가 없으면 1차.

```bash
ls phases/{task}/review/ 2>/dev/null
```

2차 이상이면 **이전 라운드의 리포트와 처분 기록(`fix-{N}.md`)을 먼저 읽는다.** 처분 기록은 고친 세션이 스스로 적은 것이라 그대로 믿지 않는다. "고쳤다"는 항목이 실제로 닫혔는지, "기각했다"는 항목의 근거가 맞는지 코드에서 확인하고, 리포트의 `## 이전 라운드 대조` 절에 `닫힘 / 미해결 / 다르게 터짐` 중 하나로 적는다. 이것을 빼면 라운드가 누적되는 의미가 없다.

## 2. 근거 문서 읽기

phase의 **범위**를 모르면 범위 밖을 결함으로 올린다. 원본 프로젝트의 Epic 0 리뷰에서 이 경계가 있었기에 계측 항목이 표를 오염시키지 않았다. 순서대로 직접 읽는다(sub-agent에 위임하지 마라 — orchestrator가 경계를 쥐어야 기각을 할 수 있다).

| 파일 | 여기서 얻는 것 |
|---|---|
| `docs/DEVELOPMENT.md` | "반드시 지킬 규칙"의 색인. 위반은 무조건 critical 후보. 규칙의 본문은 표가 가리키는 문서에 있다 |
| `docs/ARCHITECTURE.md` | 실패로 간주하는 두 가지(1절), 동작 흐름(3~5절), 데이터 모델(6절), 코드 구조와 포트(8절) |
| `docs/ADR.md` | 벗어나면 안 되는 기술 선택 |
| `docs/CONFIGURATION.md` | 설정값을 다루는 규칙(1절), 설정값의 뜻과 기본값(3절) |
| `docs/backlog/epic-{N}/E{N}-*.md` | 이 phase의 Story와 **"못 박을 것 (Epic 전역)"** |
| `docs/backlog/epic-{N}/testcase.md` | TC 목록과 **"이 Epic에서 판정하지 않는 것"** |
| `phases/{task}/index.json` | step별 `summary` — 실제로 무엇이 만들어졌다고 선언됐는지 |
| `phases/{task}/step*.md` | 각 step의 AC·**금지사항**·**반증 조건** |
| `phases/{task}/MANUAL.md` | 사람만 확인할 수 있는 항목. 여기 있는 것은 "테스트가 없다"로 올리지 않는다. 다만 테스트로 덮을 수 있는데 여기 적힌 항목은 test-coverage의 결함이다 |

`{N}`은 task 디렉터리 앞자리 숫자다 (`1-auth` → `epic-1`). 버그 수정 phase(`bugfix-{N}`)는 `docs/backlog/bugfix-{N}/`를 본다.

diff가 닿는 영역에 따라 `docs/API.md`(공통 규칙 2절, 엔드포인트별 형식 4절), `docs/AI_CONTRACT.md`(검증 5절, 재적재 6절), `docs/DECISIONS.md`(D-번호), `docs/GLOSSARY.md`를 덧붙인다. API.md는 크니 해당 절만 본다.

## 3. 실측

수치 없는 판정은 이 프로젝트에서 결과가 아니다(`docs/DEVELOPMENT.md`). 리포트에 넣을 값을 orchestrator가 직접 만든다.

```bash
scripts/check.sh --all
```

`--all`을 빼지 마라. 빼면 첫 실패에서 멈춘다. **하나가 실패해도 나머지를 돈다** — 실패 자체가 리포트의 1급 사실이고, 무엇이 어디까지 통과하는지가 결함의 심각도를 가른다. 네 명령(`ruff check`, `ruff format --check`, `pyright`, `pytest`) 각각의 exit code와 통과/실패 개수를 기록한다. pytest가 건너뛴 테스트(`skipped`, `xfailed`)의 수도 적는다 — 건너뛴 테스트는 통과가 아니다.

통합 테스트가 DB 같은 환경을 요구해 돌 수 없으면, **돌았다고 적지 말고** "실행 불가 — 사유"를 리포트에 적는다.

> **주의** — 이 레포의 Stop 훅이 턴을 끝낼 때 `scripts/check.sh`를 다시 돌리고, 실패하면 세션을 최대 3번 되돌린다. `scripts/harness-run.sh`가 띄운 헤드리스 리뷰 세션은 `HARNESS_REVIEW`로 이 훅을 건너뛰지만, 대화형으로 `/review`를 돌리면 훅이 걸린다. 그때도 **코드를 고치지 마라.** 리포트에 실패를 기록했음을 밝히고 턴을 끝내라. 리뷰가 대상을 바꿔 버리면 그 리포트는 이미 존재하지 않는 코드를 판정한 것이 된다.

## 4. 브리프 작성

5개 sub-agent가 각자 문서 1,000줄을 다시 읽으면 범위 해석이 5갈래로 갈린다. 범위는 orchestrator가 한 번 고정하고, 판정 근거는 sub-agent가 원문에서 직접 확인한다 — **브리프는 지도이지 문서의 대체물이 아니다.**

세션 스크래치패드 디렉터리에 `review-brief.md`로 쓴다. 담을 것:

- task, 브랜치, diff 범위, 파일 수와 `+/-` 줄 수
- 변경 파일 전체 목록 (`git diff --stat main...HEAD` 그대로)
- 커밋 목록 (`git log --oneline`)
- **이 phase의 범위** — Story 목록과 TC 번호, step별 한 줄 요약
- **범위 밖** — `testcase.md`의 "판정하지 않는 것", 다음 Epic으로 명시 유예된 것, `MANUAL.md` 항목
- **못 박을 것** — `docs/DEVELOPMENT.md`의 "반드시 지킬 규칙"과 E{N} 문서의 Epic 전역 제약
- §3의 실측 결과
- 2차 이상이면 이전 라운드의 미해결 항목

## 5. 모델 배정과 sub-agent 발사

**5개를 한 메시지에서 동시에 띄운다.** 순차로 띄우면 앞 차원의 판정이 뒤 차원에 새서 독립성이 사라지고, 벽시계 시간도 5배가 된다.

기본 배정 — 난이도는 *diff를 얼마나 상상해야 하는가*로 갈린다:

| 차원 | 모델 | 이유 |
|---|---|---|
| correctness | `opus` | 실패·경합·이탈 경로를 코드에 없는 상태로 상상해야 한다. 가장 어렵다 |
| behavioral | `opus` | 기획 문서와 코드를 대조해 "의도 vs 실제"를 판정. 독해량이 가장 크다 |
| test-coverage | `opus` | 핵심이 "어떤 가짜 구현이 이 테스트를 통과하는가"라서 적대적 추론이 필요하다 |
| security | `sonnet` | 표면이 좁고(접근 관문·서명된 주소·묶음 적재·시크릿) 대조할 목록이 뚜렷하다 |
| architecture | `sonnet` | 판정 기준이 문서에 명시돼 있어 대조 작업에 가깝다 |

배정을 바꾸는 조건:

- **security → `opus`** — diff가 로그인과 허용 목록, 본문이나 음원을 내주는 경로, 서명된 주소, zip 묶음 적재, 파일 경로 조립, SQL을 새로 건드릴 때. 이 표면은 한 줄 실수가 critical이 된다
- **architecture → `opus`** — diff가 `app/core/`의 포트 정의, `app/main.py`의 조립, `pyproject.toml`의 검사 설정을 바꿀 때. 레이어를 거스르는 import는 ruff·pyright 어디에도 걸리지 않는다
- **`sonnet`으로 내림** — 그 차원이 볼 표면이 diff에 사실상 없을 때(예: 순수 로직만 추가된 phase의 security). 표면이 없다고 차원을 빼지는 마라. "없음"도 판정이다
- diff가 1,000줄을 넘으면 내리지 않는다

`subagent_type`은 `general-purpose`를 쓴다.

각 sub-agent 프롬프트는 이렇게 조립한다:

```
너는 Diegesis BE의 {task} phase를 **{차원}** 차원으로만 리뷰한다.

브리프: {스크래치패드}/review-brief.md — 먼저 읽어라. 범위와 범위 밖이 여기 있다.
대상: git diff main...HEAD (브랜치 {branch})

{references/dimensions.md의 해당 차원 브리프 전문}

## 공통 규칙
- **레포 안의 어떤 파일도 쓰거나 고치지 마라.** 결함을 발견해도 고치지 마라 — 고치면 다른 차원이 이미 없는 코드를 리뷰한다. 메모가 필요하면 스크래치패드에만 써라. 반환값이 유일한 산출물이다
- **브리프에 적힌 근거 문서는 네가 직접 읽어라.** 브리프는 어디를 볼지 알려 주는 지도이고, 판정 근거는 원문에 있다
- 브리프의 "범위 밖"에 있는 것은 결함으로 올리지 마라
- 근거 없는 지적은 올리지 마라. 모든 결함에 `파일:줄`이 있어야 하고, 없으면 그 항목은 버린다
- 심각도를 올려 잡지 마라. critical이 흔해지면 표가 쓸모없어진다
- 확신이 없으면 버리지 말고 심각도를 낮춰 근거에 "추정"을 적어라. orchestrator가 재확인한다
- 문제 없는 것도 한 줄로 적어라 (`## 확인했고 문제 없는 것`)
- 결함이 없으면 없다고 말해라. 표를 채우려고 만들어 내지 마라

## 결과를 보내는 방법 — 이걸 빼면 리뷰가 도착하지 않는다
**너의 평문 출력은 orchestrator에게 보이지 않는다.** 다 끝냈으면 반드시:

`SendMessage({to: "main", summary: "{차원} 결과 — major {n}·minor {m}", message: "<아래 형식 전문>"})`

`"main"`이 안 닿으면 `"team-lead"`로, 그것도 안 되면 `ListAgents`로 이름을 찾아 보내라. 길어서 잘릴 것 같으면 두 번에 나눠 보내라(1/2 결함 목록, 2/2 확인 목록). **보내기 전에 턴을 끝내지 마라** — 평문으로 끝내면 네가 한 리뷰가 통째로 사라진다.

`SendMessage` 도구가 아예 없으면, 마지막 응답에 아래 형식 전문을 그대로 적고 끝내라.

## 출력 형식
각 결함:
### {ID}
- 심각도: critical | major | minor
- 위치: path:line (여러 곳이면 쉼표)
- 위반 대상: DEVELOPMENT.md 반드시 지킬 규칙 / ARCHITECTURE §x / ADR-00x / API §x / AI_CONTRACT §x / D-xx / TC-x.x.x / step{N}.md 금지사항 / 없음
- 근거: 실측 | 코드 판독 — 무엇을 보고 그렇게 판정했는지 한 줄
- 문제점: 한 줄
- 해결 제안: 한 줄

ID는 {접두어}-1, {접두어}-2 … 순번이다.
```

ID 접두어: correctness `COR`, security `SEC`, architecture `ARC`, test-coverage `TST`, behavioral `BEH`.

차원별 브리프 전문은 **`references/dimensions.md`** 에 있다. 프롬프트를 조립하기 전에 읽어라.

> **의존** — 결과를 `SendMessage`로 받는 방식은 Claude Code의 에이전트 팀 기능에 기댄다. 이 기능은 환경 변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 켠다(`docs/HARNESS.md`의 환경 변수와 의존). 꺼져 있으면 sub-agent의 결과는 Agent 도구의 반환값으로 온다 — 그 경우에도 아래 절차는 같다.

**차원이 끝났다는 신호(idle)는 왔는데 결과가 안 오면, 그 agent가 평문으로 답한 것이다.** 다시 띄우지 말고 `SendMessage`로 형식과 전달 방법을 명시해 재요청하라 — 리뷰 자체는 이미 끝나 있어서 재실행은 같은 일을 두 번 시키는 것이다.

sub-agent가 빈 결과를 내거나 죽으면 한 번 다시 띄운다. 두 번째도 실패하면 리포트의 그 차원 칸을 `미완`으로 적고 사유를 남긴다 — 안 돈 차원을 "결함 없음"으로 적으면 다음 라운드가 그 차원을 검증된 것으로 오해한다.

## 6. 오탐 기각과 병합

sub-agent 판정을 그대로 표에 옮기면 리포트가 "그럴듯하지만 틀린 것"을 사람에게 떠넘긴다. 올라온 결함 하나하나에 대해:

1. **근거 확인** — 인용된 `파일:줄`을 직접 읽는다. 코드가 그렇게 안 돼 있으면 **기각**한다. 진술이 과장된 경우(예: "참조하는 테스트가 하나도 없다"인데 실은 있고 *조합*만 안 봤다)는 기각하지 말고 **문구를 정정해** 싣는다 — 결함은 진짜인데 근거 한 줄이 틀린 것이 가장 흔하다
2. **범위 확인** — 브리프의 "범위 밖", `MANUAL.md`, 다음 Epic 유예에 걸리면 **기각**하고 리포트의 `## 이 리뷰가 판정하지 않은 것`에 한 줄로 남긴다. **인용 위치가 diff에 아예 없는 경우**(`git diff --stat main...HEAD -- <path>`가 비었다)도 여기다 — 다만 지적 자체가 유효하면 어느 Epic이 그 코드를 다시 열 때 볼 것인지 함께 적어라
3. **중복 병합** — 같은 결함을 여러 차원이 다르게 부르는 일이 흔하다(예: 실패 경로 침묵 = correctness의 버그 + behavioral의 FR 미달). **가장 잘 설명하는 차원 하나에 두고**, 다른 차원은 `연관` 칸에 ID만 남긴다. 같은 결함이 표에 두 번 있으면 개수 집계가 거짓이 된다
4. **심각도 재판정** — 5개 agent가 각자 기준으로 붙인 값이라 서로 어긋난다. 아래 정의로 orchestrator가 통일한다. **sub-agent는 낮춰 잡는 쪽으로 치우친다** — "심각도를 올려 잡지 마라"를 받았기 때문이다. 특히 이 두 유형을 minor로 올려 보내니 **올려 잡아라**: (a) 테스트가 초록인데 그 TC·AC가 요구한 것이 실제로는 안 지켜지는 자리 (b) 사람이 겪는 결과가 큰데 발동 조건이 좁아 보이는 자리 — 발동 조건이 이 phase가 방금 만든 경로(예: 묶음 재적재, 로그인 만료, 배포·재시작)면 좁은 것이 아니다

심각도 정의 — **사람이 겪는 결과**로 가른다:

| 등급 | 뜻 |
|---|---|
| **critical** | 사용자가 실제로 겪는 기능 파괴·데이터 유실·보안 구멍이거나, `docs/DEVELOPMENT.md`의 "반드시 지킬 규칙"·ADR을 정면으로 깬 것. `docs/ARCHITECTURE.md` 1절의 두 가지(저작권이 있는 본문이 허용 목록 밖에 보이는 것, 평가 기록이 빠지거나 선곡 방식이 남지 않는 것)는 발동 조건이 좁아도 critical이다. 그대로 두면 다음 Epic이 이 위에 쌓인다 |
| **major** | 특정 경로(실패·경합·재시도·재적재)에서 재현되는 결함, 또는 이 phase의 AC·TC가 요구한 것을 실제로는 보장하지 않는 테스트(가짜 초록). phase를 닫기 전에 고친다 |
| **minor** | 정확성엔 영향 없지만 다음 사람이 밟는 것 — 죽은 코드, 어긋난 이름, 누락된 로그, 문서와 코드 불일치 |

기각한 개수를 세어 둔다. 리포트 맨 아래에 적는다 — 리뷰가 얼마나 걸러졌는지가 다음 라운드의 신뢰도를 정한다.

## 7. 리포트 작성

`phases/{task}/review/review-{라운드}.md` **한 장**에 쓴다. 디렉터리가 없으면 만든다. 아래 골격을 지킨다.

````markdown
# Epic {N} 코드 리뷰 — {라운드}차

대상 `{branch}` · `main...HEAD` ({파일수}파일, +{추가}/-{삭제}) · 커밋 `{첫}..{끝}`
리뷰 일시 {YYYY-MM-DD} · 차원별 모델 {correctness=opus, …}
근거 문서: `docs/backlog/epic-{N}/` · `docs/DEVELOPMENT.md` · `docs/ARCHITECTURE.md` · `docs/ADR.md` · `phases/{task}/step*.md`

## 종합 판정

| 차원 | critical | major | minor | 판정 |
|---|---|---|---|---|
| correctness | 1 | 3 | 2 | ❌ |
| security | 0 | 1 | 0 | ⚠️ |
| architecture | 0 | 0 | 2 | ✅ |
| test coverage | 0 | 2 | 1 | ⚠️ |
| behavioral | 1 | 0 | 1 | ❌ |
| **합계** | **2** | **6** | **6** | |

판정: critical 있으면 ❌ · major만 있으면 ⚠️ · minor 이하면 ✅ · 차원이 안 돌았으면 `미완`

**phase를 닫아도 되는가**: {가능 / critical {n}건을 닫은 뒤 가능}

## 실측

| 명령 | 결과 |
|---|---|
| `ruff check` | exit 0 — 위반 0 |
| `ruff format --check` | exit 0 |
| `pyright` | exit 0 — 오류 0 |
| `pytest` | exit 0 — {n}개 통과, 건너뜀 {k}개 ({초}s) |

## 결함

### correctness

| ID | 심각도 | 위치 | 위반 | 문제점 | 해결 제안 | 연관 |
|---|---|---|---|---|---|---|
| COR-1 | critical | `app/books/service.py:42` | ARCHITECTURE §1 | {한 줄} | {한 줄} | BEH-2 |

(차원마다 같은 표. 심각도 critical → major → minor 순. 결함이 없으면 "결함 없음"만 적는다)

## 수정 우선순위

| # | 결함 | ID | 규모 |
|---|---|---|---|
| 1 | {한 줄} | COR-1 | {한 줄 수준의 규모 추정} |

## 이전 라운드 대조

(2차 이상만) 이전 라운드 항목별 `닫힘 / 미해결 / 다르게 터짐`

## 잘 된 것 (재검증 불필요)

- {한 줄}

## 이 리뷰가 판정하지 않은 것

- {범위 밖 항목과 근거 — `testcase.md` "판정하지 않는 것", `MANUAL.md`, 다음 Epic 유예}
- 기각한 sub-agent 지적 {n}건 (근거 불일치 {a} · 범위 밖 {b} · 중복 {c})

<!-- verdict: critical={합계} major={합계} minor={합계} -->
````

**마지막 줄은 형식 그대로 쓴다.** `scripts/harness-run.sh`가 이 줄에서 숫자를 읽어 처분 세션을 띄울지, 다시 리뷰할지를 정한다. 숫자는 "종합 판정" 표의 합계 줄과 같아야 한다. 결함이 없으면 셋 다 0으로 쓴다. 줄이 없거나 형식이 다르면 harness가 멈춘다. `미완`인 차원이 있으면 그 차원의 결함 수는 알 수 없으므로, 리포트 본문에 그 사실을 적고 숫자는 확인된 것만 센다.

`문제점`·`해결 제안`은 **각각 한 줄**이다. 표에 문단을 넣으면 읽히지 않는다. 한 줄로 안 되는 결함은 표 아래에 `### COR-1 상세`로 몇 줄 덧붙인다.

근거가 코드로 확정되지 않고 추정으로 남은 항목은 `문제점` 끝에 **`(추정)`**을 붙인다. 실측으로 확인한 것과 읽어서 판단한 것을 섞으면, 고치는 사람이 어디부터 재현해야 할지 모른다.

## 8. 보고

사용자에게 리포트 경로와 함께 세 줄로 요약한다: critical/major 개수, 가장 먼저 고칠 것 하나, phase를 닫아도 되는지 여부. 리포트 내용을 터미널에 다시 쏟지 마라.

결함이 있으면 다음은 처분이다(`/review-fix`, `review-fix` 스킬). `scripts/harness-run.sh`로 돌고 있으면 harness가 이어서 띄운다. 이 세션에서 이어서 고치지 마라.

---

## 하지 말 것

- **결함을 고치지 마라.** 고치는 것은 `review-fix` 스킬이 다른 세션에서 한다. 리뷰 커밋에 코드 변경이 섞이면 판정과 변경의 경계가 사라진다
- **차원을 빼지 마라.** 볼 표면이 없어 보이는 차원도 "확인했고 없음"을 남겨야 다음 라운드가 무엇이 미검증인지 안다
- **기준을 낮춰 통과시키지 마라**(`docs/DEVELOPMENT.md`). critical을 major로 내려 ⚠️를 만들지 마라
- **`docs/`·`phases/`의 다른 파일을 고치지 마라.** 리포트 한 장만 쓴다
- **감각·계측 항목을 추정으로 판정하지 마라.** 선곡이 장면에 어울리는지, 응답 시간, 부하는 `MANUAL.md`와 `measure` 항목의 것이다. 안 본 것을 봤다고 적으면 리뷰 전체가 무의미해진다
