# 리뷰 처분

리뷰 리포트 한 장을 받아 결함을 하나씩 닫는다. 리뷰는 판정만 하고 고치지 않았다(`phase-review` 스킬). 고치는 것이 이 스킬의 일이다.

이 절차는 OnlineFourCut에서 사람이 대화형 세션으로 하던 관례(`fix-{N}.md`, RED → fix → docs 커밋 순서)를 옮겨 적은 것이다. 여기서는 `scripts/harness-run.sh`가 무인으로도 돌린다.

**처분도 자기 채점이다.** 고치는 세션이 "고쳤다"와 "기각한다"를 스스로 적는다. 그래서 세 가지를 지킨다: 고친 것은 재현 테스트가 증거이고, 기각한 것은 `파일:줄`이나 실행 결과가 증거이고, 판단이 필요한 것은 닫지 않고 사람에게 넘긴다. 다음 라운드의 리뷰가 이 기록을 다시 판정한다.

---

## 1. 대상 확정

**task 이름** — 인자로 받은 것 → 없으면 현재 브랜치 `feat-{task}`에서 유추 → `phases/{task}/` 폴더가 있는지 확인.

**리포트** — `phases/{task}/review/review-*.md` 가운데 번호가 가장 큰 것. 그 번호가 이번 처분의 `{N}`이다.

```bash
git rev-parse --abbrev-ref HEAD
ls phases/{task}/review/
git status --short
```

멈추는 경우:

- 리포트가 없다 → 처분할 것이 없다고 알리고 끝낸다.
- `fix-{N}.md`가 이미 있다 → 그 라운드는 처분이 끝났다. 덮어쓰지 말고 알린 뒤 끝낸다.
- 워킹트리에 `phases/` 밖의 커밋되지 않은 변경이 있다 → 그 변경이 처분 커밋에 섞인다. 무엇이 남았는지 알리고 끝낸다.

## 2. 근거 읽기

리포트를 처음부터 끝까지 읽는다. 표의 한 줄만 보고 고치면 리뷰가 본 것과 다른 것을 고치게 된다.

이어서 판정의 근거가 되는 문서를 직접 읽는다. 무엇이 맞는 동작인지는 리포트가 아니라 문서가 정한다.

| 파일 | 여기서 얻는 것 |
|---|---|
| `phases/{task}/review/review-{N}.md` | 결함 목록, 실측, 수정 우선순위, "이 리뷰가 판정하지 않은 것" |
| `phases/{task}/review/fix-*.md`, 이전 `review-*.md` | 2차 이상일 때. 앞 라운드에서 무엇을 어떻게 닫았고 무엇을 기각했는지 |
| `docs/DEVELOPMENT.md` | 반드시 지킬 규칙, 테스트 규칙, 커밋 형식 |
| `docs/backlog/epic-{N}/E{N}-*.md`, `testcase.md` | 이 phase의 범위, TC가 요구한 것 |
| `phases/{task}/step*.md` | 각 step의 AC, 금지사항, 반증 조건 |
| 결함의 `위반` 칸이 가리키는 문서의 절 | 그 결함의 기준 원문 |

## 3. 결함 대조

결함 하나하나에 대해 인용된 `파일:줄`을 직접 연다. 셋 중 하나로 가른다.

| 처분 | 조건 | 남기는 증거 |
|---|---|---|
| **고친다** | 코드나 문서가 실제로 리포트가 말한 대로다 | 재현 테스트와 수정 커밋 |
| **기각한다** | 코드가 리포트가 말한 대로가 아니다, 또는 이 phase의 범위 밖이다 | 반대 증거가 되는 `파일:줄`이나 실행 결과 |
| **사람 판단 필요** | 아래 "무인 처분이 하지 않는 것"에 걸린다, 또는 어느 쪽이 맞는 동작인지 문서로 정해지지 않는다 | 무엇을 정해야 하는지와 선택지 |

기각의 기준은 높다. "고치기 번거롭다", "영향이 작아 보인다", "나중에 고치면 된다"는 기각 사유가 아니다. 영향이 작으면 작은 대로 고친다. minor도 처분 대상이다 — 리뷰가 올린 것은 전부 닫거나, 닫지 않는 이유를 적는다.

리포트의 진술이 일부만 맞으면 기각하지 말고 맞는 부분을 고치고, 기록에 무엇이 달랐는지 적는다.

`(추정)`이 붙은 결함은 먼저 재현한다. 재현되면 고치고, 재현되지 않으면 무엇을 해 봤는지 적고 기각한다.

## 4. 고치기

순서를 지킨다. 순서가 증거다.

1. **재현 테스트를 먼저 쓴다.** 코드 결함마다, 그 결함이 있을 때 빨갛고 없을 때 초록인 테스트를 쓴다. 위치는 `docs/DEVELOPMENT.md`의 테스트 규칙을 따른다.
2. **빨간 것을 눈으로 확인한다.** 방금 쓴 테스트만 돌려 실패하는지, 그리고 **기대한 이유로** 실패하는지 본다. import 오류로 빨간 것은 재현이 아니다.
3. **RED를 커밋한다.** `test({task}): RED — {N}차 리뷰 COR-1·TST-2 …`. 이 커밋이 "테스트가 먼저였다"의 유일한 증거다. 구현과 함께 커밋하면 나중에 맞춰 쓴 테스트와 구별되지 않는다.
4. **고친다.** 결함을 닫는 가장 작은 변경으로. 리포트에 없는 것을 함께 고치지 마라 — 처분 커밋이 리뷰가 보지 않은 변경을 싣게 된다. 눈에 띄는 다른 문제는 기록의 "새로 발견한 것"에 적는다.
5. **초록을 확인하고 커밋한다.** `fix({task}): {N}차 리뷰 COR-1·TST-2 — {한 줄}`.
6. **문서 결함은 따로 커밋한다.** `docs({task}): {N}차 리뷰 BEH-3·ARC-1 — {한 줄}`. 문서만 고치는 결함에는 RED가 없다.

테스트 결함(가짜 초록)을 고칠 때는 순서가 조금 다르다. 테스트를 강하게 고친 뒤, 리포트가 말한 가짜 구현을 잠깐 넣어 그 테스트가 빨개지는지 확인하고 되돌린다(돌연변이 반증). 무엇을 넣어 봤는지 기록에 적는다.

재현 테스트를 쓸 수 없는 결함(스크립트 흐름, 설정)은 실행으로 확인하고, 무엇을 실행해 무엇을 봤는지 적는다.

Stop 훅이 턴을 끝낼 때 `scripts/check.sh`를 돌린다. RED 커밋 직후에는 테스트가 빨갛다 — 턴을 끝내지 말고 같은 턴에서 수정까지 이어 가라.

## 5. 무인 처분이 하지 않는 것

아래에 걸리는 결함은 고치지 않고 **사람 판단 필요**로 넘긴다. 대화형 세션에서 사용자가 직접 지시하면 그때 한다.

- **검사를 느슨하게 만들어 닫는 것.** 테스트를 지우거나 `skip`·`xfail`을 다는 것, 단언을 약하게 고치는 것, `# type: ignore`·`# noqa`를 다는 것, ruff·pyright·pytest 설정을 완화하는 것. 이유: 결함이 닫힌 것이 아니라 보이지 않게 된 것이다.
- **가드와 훅을 고치는 것.** `scripts/hooks/`, `scripts/check.sh`, `.claude/settings.json`. 무인 실행에서는 가드가 막는다.
- **결정을 맡은 문서를 코드에 맞춰 고치는 것.** `docs/PRD.md`, `docs/ADR.md`, `docs/DECISIONS.md`, `docs/API.md`, `docs/AI_CONTRACT.md`, `docs/ARCHITECTURE.md`, `docs/CONFIGURATION.md`의 규칙과 규격. 이유: 코드와 문서가 어긋났을 때 어느 쪽이 맞는지는 결정이다. 문서가 맞으면 코드를 고치면 되고, 문서를 바꿔야 한다면 그것은 사람과 다른 팀이 정한다. 오타, 죽은 링크, 코드의 이름이 바뀌어 낡은 경로처럼 규칙이 바뀌지 않는 수정은 해도 된다.
- **`MANUAL.md`의 항목을 체크하는 것.** 사람이 직접 본 것만 체크한다. 리뷰가 "이 항목은 테스트로 덮을 수 있다"고 올렸으면 테스트를 쓰고, 기록에 "MANUAL의 그 항목을 지워도 된다"고 적어 사람이 지우게 한다.
- **닫힌 step 파일(`phases/{task}/step*.md`)의 AC나 금지사항을 고치는 것.** 이유: 이미 실행된 지시의 기록이다. 경로 오타 같은 사실 정정만 한다.
- **의존성을 더하거나 빼는 것, 마이그레이션을 고쳐 쓰는 것.** 이미 커밋된 마이그레이션 파일을 수정하지 않는다. 필요하면 새 마이그레이션이 맞는지부터 사람이 정한다.
- **push, PR, 이슈.** 커밋까지만 한다.

넘길 때는 사람이 바로 정할 수 있게 쓴다: 무엇이 어긋나 있는지, 선택지가 무엇인지, 각 선택지가 무엇을 바꾸는지.

## 6. 검증

```bash
scripts/check.sh --all
```

넷 다 돈 결과를 기록에 적는다. 하나라도 실패하면 고친다. 이번 처분과 무관하게 원래 빨갛던 것이라면(리포트의 실측과 대조한다) 그 사실을 적는다 — 빨간 것을 초록이라고 적지 마라.

통합 테스트가 DB 같은 환경을 요구해 돌 수 없으면 "실행 불가 — 사유"로 적는다.

## 7. 처분 기록

`phases/{task}/review/fix-{N}.md` **한 장**에 쓴다. 아래 골격을 지킨다.

````markdown
# {task} 리뷰 처분 — {N}차

> `review-{N}.md`의 결함 {합계}건(critical {a} · major {b} · minor {c})에 대한 처분. {YYYY-MM-DD}.
> 고친 것 {x}건, 기각 {y}건, 사람 판단 필요 {z}건.

## 고쳤다

| ID | 심각도 | 처분 | 커밋 |
|---|---|---|---|
| COR-1 | major | {무엇을 어떻게 고쳤는지 한 줄. 재현 테스트의 위치} | `abc1234` |

## 기각했다

| ID | 심각도 | 근거 |
|---|---|---|
| ARC-2 | minor | {리포트의 진술과 다른 사실. `파일:줄`이나 실행 결과} |

(없으면 "없음"만 적는다)

## 사람 판단 필요

| ID | 심각도 | 무엇을 정해야 하는가 | 선택지 |
|---|---|---|---|
| BEH-4 | major | {무엇이 어긋나 있는지} | {A: … / B: …} |

(없으면 "없음"만 적는다)

## 커밋

`abc1234` RED(COR-1 · TST-2) · `def5678` 코드(COR-1 · TST-2) · `9abcdef` 문서(BEH-3)

## 검증

| 명령 | 결과 |
|---|---|
| `ruff check` | exit 0 |
| `ruff format --check` | exit 0 |
| `pyright` | exit 0 — 오류 0 |
| `pytest` | {n}개 통과 (처분 전 {m}개) |

- 돌연변이 반증: {가짜 구현을 넣어 빨개진 것을 확인한 테스트. 없으면 "없음"}
- 실행으로 확인한 것: {테스트로 못 잰 결함을 무엇으로 확인했는지. 없으면 "없음"}

## 새로 발견한 것

- {처분하다가 본, 리포트에 없는 문제. 고치지 않았다. 없으면 "없음"}

<!-- disposition: fixed={x} rejected={y} needs-human={z} -->
````

**마지막 줄은 형식 그대로 쓴다.** `scripts/harness-run.sh`가 이 줄에서 숫자를 읽어 다음에 무엇을 할지 정한다. 세 숫자의 합은 리포트의 결함 수와 같아야 한다. 줄이 없거나 형식이 다르면 harness가 멈춘다.

`처분`과 `근거`는 **각각 한 줄**이다. 한 줄로 안 되면 표 아래에 `### COR-1 상세`로 덧붙인다.

## 8. 전례 남기기

이번 라운드에서 **실제로 뚫린** 유형을 `.claude/skills/phase-review/references/dimensions.md`의 해당 차원 "전례"에 한 줄 더한다. 다음 리뷰가 같은 종류를 먼저 찾게 하려는 것이다.

- 기각한 결함은 전례가 아니다. 고친 것만 더한다.
- 이 프로젝트에 고유한 사실로 쓴다: 무엇을 믿었다가 무엇이 틀렸는지. "테스트가 부족했다" 같은 일반론은 쓰지 마라.
- 같은 유형이 이미 있으면 더하지 않는다.
- critical과 major만 더한다. minor를 전부 더하면 목록이 읽히지 않는다.

## 9. 커밋과 보고

처분 기록과 전례를 커밋한다: `docs({task}): {N}차 리뷰 {합계}건의 처분`.

워킹트리를 깨끗하게 남긴다. 커밋하지 않은 변경이 남으면 harness가 멈춘다.

사용자에게 기록 경로와 함께 세 줄로 요약한다: 고친 것·기각·사람 판단 필요의 개수, 사람이 정해야 할 것(있으면 가장 급한 것 하나), 다음에 할 일. 다음에 할 일은 이렇게 정한다.

- 이번 라운드에 critical이나 major가 있었다 → 고친 결과를 `/review`로 다시 판정받는다. harness로 돌고 있으면 harness가 알아서 다시 리뷰한다.
- minor뿐이었다 → 처분으로 닫는다.
- 사람 판단 필요가 있다 → 그것이 정해질 때까지 phase를 닫지 않는다.

## 하지 말 것

- **근거 없이 기각하지 마라.** 기각은 리뷰가 틀렸다는 주장이다. 주장에는 증거가 붙는다.
- **테스트를 구현에 맞춰 약하게 고치지 마라.** 테스트가 틀렸다고 판단되면 그 이유를 기록에 적고, 테스트가 반증해야 할 것을 더 정확히 반증하게 고친다.
- **RED 커밋을 건너뛰지 마라.** 급해 보여도 순서를 지킨다. 순서를 지켰는지는 커밋 이력으로만 확인된다.
- **리포트를 고치지 마라.** `review-{N}.md`는 그때의 판정 기록이다. 리포트가 틀렸으면 처분 기록에 적는다.
- **범위를 넓히지 마라.** 리포트에 없는 리팩터링, 이름 바꾸기, 정리를 하지 않는다.
- **안 한 것을 했다고 적지 마라.** 돌리지 못한 검사는 "실행 불가"로, 확인하지 못한 수정은 "확인하지 못했다"로 적는다.
